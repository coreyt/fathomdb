# EARP foundation — plan

**Revision 2** — revised 2026-08-06 after an independent code-grounded design
review and HITL rulings D-1…D-6 (`dev/notes/earp-hitl-decisions.md`). The prior
draft's slice order is superseded; § "What changed and why" records the
reasoning. Status stays `PROPOSED`: the revision resolves the review's
findings, but nothing here authorizes implementation.

## Objective

Build a durable EARP foundation that runs declared FathomDB configurations
against pinned corpus and gold inputs and writes structured, honest evidence.
It is a developer-side harness (D-1), it never gates FathomDB (D-2), and its
integrity rests entirely on its own discipline because nothing downstream
depends on it.

## Scope and boundaries

- EVAL-ONLY Python tooling under `src/python/eval/earp/`, off-wheel by
  construction (`src/python/pyproject.toml:80-81`), following the existing
  `m1_*` / `r2_parity_eval` harness convention.
- No production SDK, schema, query-path, or CI-gate change. Where the SDK is
  insufficient (D-5 fanout control), the gap is named and commissioned
  separately — never worked around inside EARP.
- Metric semantics are **ported from IR-B with a pinned parity test**, not
  "reused" — IR-B exists only as Rust test-support
  (`src/rust/crates/fathomdb-engine/tests/support/ir_eval.rs`) with no Python
  surface. See S2.
- Gold is the IR-C reuse tier under D-6's four conditions. No gold is
  generated by EARP.
- `EngineConfig` fields are catalogued by whether a concrete SDK call path
  exists, not by dataclass membership (see S3 and D-5).

## Sequencing principle

The prior draft front-loaded the SDK-touching runner and deferred the durable
writer behind it, which produced a dependency inversion (the Slice-2 runner
was required to emit artifacts that Slice 3 delivered). The revised order
follows two rules:

1. **Trustworthy inputs and pure logic first.** Gold validation and the metric
   port have no SDK and no database dependency, are the highest risk of being
   *silently wrong*, and are cheap to test in isolation. They come before
   anything that opens an engine.
2. **Nothing emits a number before there is somewhere honest to put it.** The
   writer precedes the runner, so no slice has to invent a temporary output
   path it later discards.

## Per-slice governance

Every slice below carries the same four gates. A slice is not closed until all
four are satisfied, and no slice may begin implementation before its design is
reviewed.

1. **Design.** `dev/design/earp-slice-<n>-design.md`, following the existing
   `dev/design/slice-*-design.md` convention. It states the contract the slice
   implements, the concrete call paths and witnesses it touches, and what it
   deliberately does not do.
2. **Design review.** An independent, code-grounded review recorded in the
   design under a `## Review` section: findings, severity, remedy, and the
   verdict. Reviews verify against source, not against architecture — the
   review of this plan found that three of four claimed reuse targets were not
   reusable from Python, which no architecture-level read would have caught.
3. **Requirements and acceptance criteria.** Stated per slice, testable, and
   written before the tests. Requirements say what must be true; acceptance
   criteria say how it is demonstrated.
4. **TDD, RED then GREEN.** Every behaviour lands as a failing test first. The
   RED and GREEN evidence is recorded in the slice's closure notes and in the
   `tdd_evidence` field the shared record already carries
   (`experiments/_lib.py:104`). A test that passes on first write is not
   evidence; it is a test that was never proven to fail.

Slice 0 satisfies these by construction: its design is `dev/design/earp.md`,
its review is the code-grounded review recorded in this revision, its
requirements are the acceptance criteria below, and its deliverable is
declarative schema with no behaviour to test.

Slices 1 and 2 are independent of each other and may run in parallel.

### S1 · Gold basis

Enforces D-6's four conditions as executable preconditions, not prose. Pins
`data/corpus-data/eval/ir_gold/all.gold.json` by SHA-256; asserts its
`corpus_hash` equals `tests/corpus/snapshot.json`'s; **refuses
`qrels_version: ir-c-reused-v1` as a typed blocker** and requires
regeneration to `ir-c-reused-v2` via `tests/corpus/scripts/build_ir_gold.py`.
Records the snapshot hash as the GoldSet's identity and
`tests/corpus/scripts/manifest.json` as raw-corpus provenance — separately,
never conflated. The corpus/gold root is an explicit configurable path: the
data is gitignored, so a worktree-launched run cannot see it, and its absence
is a typed blocker rather than a silent empty gold set.

### S2 · Metric port with pinned parity

Pure functions, no SDK, no database. Ports `evidence_recall_at_k`,
`negative_abstained`, and the eligibility rules from `ir_eval.rs:385-411`.
Parity is asserted against the committed fixture
`src/rust/crates/fathomdb-engine/tests/fixtures/ir_gold/synthetic_gold.json`
(committed, so it survives into worktrees) plus a checked-in Rust-produced
expectations file.

**No divergence — parity is full.** An earlier revision of this plan carved
`supporting_coverage` out of the parity assertion, because the Rust reference
returned `0.0` for an empty supporting set while EARP's own rules require
`not_applicable`. That was resolved upstream instead (branch
`integrate/0.8.22-eval-supporting-coverage-20260806`):
`PerQueryRecall.supporting_coverage` is now `Option<f64>`, `ClassAgg` tracks
`supporting_query_n` and averages over support-bearing queries rather than all
queries, and `experiment_to_json` emits `null` for the unavailable case. EARP
ports it faithfully — `null` → `not_applicable`, `supporting_query_n` carried
into the sidecar — and the parity test asserts **every field, no exclusions**.

**Dependency:** that fix is not yet merged to `main`. S2's parity test must be
written against it, so S2 cannot close until the branch lands.

Also lands the mode-aware depth rules (D-5): FTS-only admits @20/@50;
vector-only and hybrid reject above 10 with a typed `metric_not_measurable`
naming `SEARCH_RERANK_LIMIT` and the D-5.2 fanout slice.

### S3 · Resolver and catalog

Strict `earp.v1`: unknown, missing, invalid, and unused keys are hard errors.
Adds the per-campaign **decision-rule block** required by D-4 — predeclared
before the run, persisted into the resolved config, absent means metrics may
be reported but no better-than claim may be made. Declares the run's
worst-case cost estimate for D-3.

The knob catalog is keyed on **"does a concrete SDK call path exist"**, never
on dataclass membership. Each of `EngineConfig`'s five fields gets an
individual verdict; `slow_threshold_ms` is **supported** (`runtime`, path
`Engine.set_slow_threshold_ms`, `engine.py:748-749`), and
`Engine.set_profiling` (`:745-746`) joins the candidate list. The catalog
records that `Engine.open` never forwards `EngineConfig` to native
(`engine.py:171-173`) as an observed finding.

### S4 · Durable writer

`_lib.write_record` performs materialize-and-append in one call
(`experiments/_lib.py:457-493`) with no hook between them, so the required
stage → materialize → append-last ordering is only achievable by pre-deriving
the run identity: `config_sha256` (`:182`) → `make_run_id` (`:201`) →
`runs/<run_id>/`, stage and validate sidecars there, then call `write_record`
with a byte-identical `config_obj` and the same `ts` so it recomputes the same
id. That contract is locked in S0 and tested here.

`run_id` is minute-resolution (`_lib.py:193-194`), so two runs with the same
resolved config in the same minute collide and the second silently overwrites
the first while producing one index row. The collision policy — refuse when a
run directory already exists with a differing sidecar — is part of this slice.

### S5 · Diagnostic runner

The `diagnostic` campaign kind, which the prior plan declared but no slice
delivered. Runs the small human-authored fixture against a fresh temporary
database through the real Python SDK, exercising the whole machinery with no
gold and therefore no retrieval-quality claim. The fixture must carry
`source_id` on every canonical item — `Engine.write` makes it mandatory
(`engine.py:186-187`). Names one of the three real search entry points
(`search` `:443`, `search_projected_text` `:543`, `search_text_only` `:577`)
rather than the symbolic `operation: search`.

Embedder-cache evidence is **post-hoc**, not preflight: there is no Python
cache-status API and the Rust cache path derives from `pub(crate)` constants,
so a preflight would require duplicating a model revision into Python and
drifting from it. The run records `OpenReport.embedder_download_ms` and
`embedder_events` and blocker-marks a run that fetched.

### S6 · Corpus-scale characterization and replay

The first real quality campaign: frozen snapshot + regenerated v2 gold,
Evidence Recall@{5,10} strict and graded, abstention correctness on the 125
negatives, per-query outcomes. `ndcg` is `not_applicable` — no graded
relevance exists in any gold set in this repo. Claims stay scoped to
reuse-tier, document/body-level evidence gold per D-6 condition 4.

`replay` lands here rather than earlier because it needs a prior record worth
replaying: re-resolve a stored config, recompute the run identity through
`_lib.make_run_id`, and report drift against the prior record's environment and
code deltas. Deterministic `run_id` (S4) is the mechanism; a real campaign (S6)
is the first thing that makes it meaningful.

## Acceptance criteria

- A strict `earp.v1` loader rejects unknown, missing, invalid, and unused
  fields, and rejects a metric ladder its retrieval mode cannot measure.
- Gold is pinned by SHA-256, its `corpus_hash` matches the frozen snapshot,
  and `ir-c-reused-v1` is refused as a typed blocker.
- Ported metrics are byte-parity with the Rust reference on the pinned
  fixture, with no excluded fields.
- A resolved run creates a fresh database, ingests through the real Python
  SDK, runs a named search operation, and emits durable artifacts with
  integrity and `open_report` witnesses.
- Results distinguish success, skip, blocker, and typed failure; none is
  scored as an ordinary retrieval miss, and no inapplicable metric is emitted
  as zero.
- The knob catalog accounts for every maintained candidate with a
  classification, concrete call path, witness, and reason, keyed on call-path
  existence rather than reflection or dataclass membership.
- Sidecars are staged and validated before the shared record is materialized
  and the index appended last; a partial run cannot appear complete, and a
  run-id collision is refused rather than silently overwritten.
- Priced arms are individually opt-in, visibly skip by default, and are
  refused when projected cumulative spend exceeds the D-3 authorization.

## Per-slice requirements and acceptance criteria

| Slice | Requirement | Acceptance criterion |
| ---: | --- | --- |
| 1 | Gold is trustworthy before it is measured against | Pinned SHA-256 matches; `corpus_hash` equals the snapshot hash; `ir-c-reused-v1` refused as `gold_stale_qrels_version`; absent root refused as `corpus_root_absent`; snapshot and manifest recorded separately |
| 2 | Ported metrics are the reference's metrics | Byte-parity with Rust output on `synthetic_gold.json`, no excluded fields, including `null` supporting coverage and `supporting_query_n`; depth rules refuse K>10 for vector/hybrid and admit it for FTS-only |
| 3 | A config cannot express a run that cannot be honestly executed | Unknown, missing, invalid, and unused keys rejected; unmeasurable K rejected; ineligible metric rejected or `not_applicable`; decision rule predeclared or absent; every catalog entry has a call path and witness |
| 4 | A partial run can never appear complete | Sidecar staged and validated before the index line exists; run id pre-derived and stable across `write_record`; colliding run dir with differing sidecar refused; blocked runs indexed only with a blocked verdict |
| 5 | The machinery works end to end without a quality claim | Fresh DB, real SDK ingest with `source_id`, named search call, integrity and `open_report` witnesses, typed blockers; no metric emitted that gold cannot support |
| 6 | Corpus-scale numbers are real and scoped | Evidence Recall@{5,10} strict and graded plus abstention over the 125 negatives; `ndcg` reported `not_applicable`; fanout recorded; replay reproduces the run identity and reports drift |
| 7 | Projection state is read from its true source | `vector_dense_readiness` polled, `vector_unsupported_kinds` from the delta, `dense_disabled` from `open_report`; `None` readiness disambiguated from "not declared" |
| 8 | A comparative claim is earned, not assumed | Arms differ only at `changed_knobs`; pairing on immutable query ids; CI method, seed, and power rule fixed before running; `UNDERPOWERED` emitted against the declared rule |
| 9 | Spend is bounded and visible | Every priced arm opt-in and visibly skipped by default; projected cumulative spend over the D-3 authorization refused as `budget_exceeded`; cost recorded per run |

## Test-first sequence

1. Gold pin, `corpus_hash` mismatch, and `ir-c-reused-v1` refusal tests before
   the gold loader.
2. Rust-parity vectors — including the unavailable-`supporting_coverage` and
   `supporting_query_n` cases — before the metric port.
3. Malformed-config, unknown-knob, mode-aware-depth, and metric-eligibility
   tests before the resolver.
4. Sidecar-schema, writer-ordering (sidecar exists *before* the index line),
   and run-id-collision tests before the writer.
5. Fixture ingest and typed-blocker tests before the diagnostic runner.
6. Projection-readiness typed-outcome tests, split by real source, before the
   matrix.
7. Exact one-knob-difference, pair/strata, and fixed-seed tests before
   comparison mode.
8. Opt-in, blocked-arm, and budget-refusal tests before every priced adapter.

## What changed and why

- **Writer moved ahead of the runner** (was S3, now S4 before S5) — removes
  the inversion where the runner's acceptance criteria required artifacts a
  later slice delivered.
- **Metric port promoted to S2** — it is the component most likely to be
  silently wrong and has no dependencies; burying it inside the runner made it
  untestable in isolation.
- **Gold basis promoted to S1** — D-6 makes input validity a hard
  precondition, and the stale-cache trap is real.
- **`diagnostic` given an owning slice (S5)** — it was a declared campaign
  kind that no slice delivered.
- **Fixture and corpus reconciled rather than chosen between** — the fixture
  backs the fast, network-free diagnostic slice; the frozen corpus backs the
  quality campaign. The prior draft's "one human-authored fixture" v1 scope
  conflicted with its own gold-required acceptance criterion.
- **Cache preflight replaced with post-hoc open evidence** — a preflight has
  no Python surface and would require duplicating a `pub(crate)` model
  revision, creating exactly the drift hazard the Rust code avoids.
- **"Reuse IR-B" reworded to "port with pinned parity"** — IR-B is Rust
  test-support; every EARP metric is necessarily a port, and Python already
  contains at least six ad-hoc forks of recall/MRR/nDCG.

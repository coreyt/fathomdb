## 1. What was actually wrong

Local `main` was 21 commits ahead of `origin/main`. Three of the five 0.8.21
slices had never reached the remote:

| Slice | Commit | Was on `origin/main` |
| ---: | --- | --- |
| 0 | `2ea2c884` | NO |
| 5 | `a6cf2bbe` | yes (PR #176) |
| 10 | `f94275e1` | yes (PR #176) |
| 15 | `19d8f072` | NO |
| 20 | `354ee9b4` | NO |

Meanwhile `dev/plans/plan-0.8.21.md` rendered them as
"**LANDED on `origin/main`, in full**".

**Root cause is tooling, not authorship.**
`scripts/check-release-state-views.sh` hard-codes the literal string
``LANDED on `origin/main` `` at two call sites — `render_master_ladder_progress`
(line 203) and `render_plan_landed_roll_up` (line 463) — and renders the slice
list from `release-state-*.json`'s `landed` array. Neither renderer ever asks
Git whether those SHAs are reachable from `origin/main`. A slice is therefore
declared remotely landed the moment it is written to the state file, which is
local-commit time. The board could not have caught this drift; it was
structurally incapable of reporting it.

Additional finding: `main` is now **branch-protected** on GitHub ("Changes must
be made through a pull request"). Direct steward pushes to `main` no longer
work. Prior program notes to the contrary are stale.

## 5. The durable fix — as built

**The approach changed during implementation, and the original proposal was
wrong.** It said to render a distinct `LANDED LOCALLY, NOT PUSHED` string for
unpushed SHAs. That cannot work: this script's contract is that committed
Markdown equals generated Markdown, so a rendered string that varied with local
push state would differ between a steward's checkout and CI, and **every**
in-flight slice would report a spurious view mismatch. The render must stay
deterministic over the state file.

Built instead as a **separate verification alongside the render**, in
`scripts/check-release-state-views.sh`:

- `check_remote_landing()` resolves each `landed` SHA with
  `git merge-base --is-ancestor <sha> origin/main`, and also catches a SHA that
  is not a commit in the repository at all.
- **Hard failure on `main`**; **advisory elsewhere**. A PR branch legitimately
  carries a landed SHA the remote lacks — that is what the PR is for, and
  hard-failing would block the merge that resolves it. On `main` the same
  condition is exactly this drift.
- **Advisory under `--write`.** `--write` regenerates; it does not assert.
  Hard-failing it would make the views unregenerable precisely while a slice is
  unpushed, so the steward could not repair the document without first
  defeating the check.
- Absent `origin/main` (fresh or detached clone) the claim is *unverifiable,
  not false*, and the guard stays silent.

Five red-first arms in `scripts/tests/test_check_release_state_views.sh`
(arm R, R2, R3, R4). Verified red-first: with the guard neutered to `return`,
four arms fail; restored, all pass. Arm R4 exists because the **first**
implementation keyed enablement off a state-file key that does not exist
(`slices` rather than `ladder`), so it ran on nothing and every other arm would
have passed against a no-op — the same vacuous-pass failure this file's TC-37
guard already covers for blocks.

Run against the real repository on the sync branch, the guard named exactly
slices 0, 15 and 20 — independently reproducing the hand analysis in §1.

Under a protected `main` the local/remote gap is now the normal state during
every slice, so this guard will be exercised constantly.

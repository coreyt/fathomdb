branch-to-branch push carries no tag (`push.followTags` is unset). Do not balk at pushing to `main` at

### 4.5 B5 — OOS-18

`test-python` can SIGBUS (exit 135) at `_vector_kind_registered` in
`src/python/tests/test_slice20c_flush_barrier.py`, from a stdlib `sqlite3` `mode=ro` connection against
a database the engine is actively writing. Recorded in-repo as OOS-18, "a HARNESS hazard, not an engine
defect", at 5/30 and 3/30; a probe measured 3 of 4 against a debug build. ⚠ CI's `verify` does **not**
set `FATHOMDB_SKIP_NETWORK_TESTS`, so it is live on the gate path.

#### 4.5.1 The mechanism

`fathomdb-engine/Cargo.toml` declares `rusqlite = { version = "0.31", features = ["bundled"] }`, so the
engine links its own statically-bundled SQLite; Python's `sqlite3` links the system `libsqlite3`
(3.45.1 on this box). SQLite's WAL concurrency contract is defined over **processes**, and its
workaround for POSIX advisory locks — where `close()` of any fd on an inode drops that process's locks
— lives in a per-library-copy inode cache the two copies do not share. Two copies in one process
therefore steal each other's locks and invalidate each other's `-shm` mappings.

Measured — same test body, same SQL, same `mode=ro`, only the probe relocated:

| arm | SIGBUS | n |
|---|---|---|
| raw `sqlite3` probe in-process (status quo) | 25 | 60 |
| identical probe in a child process | 0 | 60 |

`P(0 of 60 | p=25/60) ≈ 9e-15`. The process boundary is the whole story.

⛔ **`mode=ro` is not the cause and `immutable=1` is not the fix.** `mode=ro` is the repo's sanctioned
pattern and this test already uses it correctly: `src/python/eval/verify_embed_db.py` documents that a
verifier must see committed-but-not-yet-checkpointed rows in the `-wal`, and that `immutable=1` reads
only the main DB and would report an empty DB — a note that recurs across six engine test files.
Switching to `immutable=1` would make the late-enrolment assertion fail deterministically.
`STATUS-0.8.1.md` records that exact scar.

#### 4.5.2 The fix — one Python file, no Rust, no rebuild

In `src/python/tests/test_slice20c_flush_barrier.py`, funnel the read-only raw-SQL oracles through one
helper that executes the query in a **child OS process** — same `sqlite3` module, same
`file:{path}?mode=ro` URI, same SQL, same parameters, same tables, same point in the test.

The functions that open their own raw connection are these eight:

`_query` · `_leaf_rows_of_kind_without_vectors` · `_vector_kind_registered` · `_active_cursor` ·
`_terminal_state` · `_fts_row_exists` · `_active_edge_cursor` · `_pending_node_rows_below`

⚠ **Re-derive this list at commission** (`grep -n 'mode=ro'`, map each hit to its enclosing `def`)
rather than trusting these eight names. `_projection_failure_rows` delegates to `_query` and
`_leaf_rows_without_vectors` opens no connection of its own, so both are covered transitively — they
are not separate work.

- ⛔ **Use `subprocess`, not `multiprocessing`.** `multiprocessing`'s default `fork` on Linux would fork
  a process holding live SQLite handles *and* a running Rust embed-worker thread — a different, real
  hazard. `subprocess.run` (fork+exec) runs no Python in the forked image; the child inherits fds but
  not locks.
- ⚠ `_terminal_state` returns `str | None` and `_fts_row_exists` returns `bool` — the child must
  distinguish "no row" from a value. Do not force every oracle through an `int` return; that would
  silently convert a missing row into a value and weaken the oracle.
- Leave the two read-write injector connections alone — both run after `engine.close()`, outside the
  hazard class.
- Cost: ~54–58 helper call sites × ~35 ms interpreter start ≈ 2 s added to a ~150 s file.

**Why this eliminates rather than narrows:** it removes the foreign SQLite copy from the engine's
process entirely. What remains — a separate process reading a live-WAL DB `mode=ro` — is exactly what
SQLite's WAL design supports and what `src/python/eval/verify_embed_db.py` already relies on as a live
post-drain gate.

**Why it does not weaken the oracle:** the file's docstring is explicit that the raw-table read is
load-bearing *because it is independent of the engine's own view* — "a harness that only reads
readiness back PASSES against the defect". The child probe is the same stdlib reader running the same
SQL; only the address space changes. Confirmed empirically: the session-1 assertions that read
never-checkpointed rows passed on all 60 child-process runs.

#### 4.5.3 CI's exposure is ~4× worse than the record says

`conftest.py`'s sanctioned rebuild runs `maturin develop` **without `--release`**, so CI tests the debug
binding. OOS-18's recorded 5/30 and 3/30 (≈10–17 %) came from a release wheel. Measured on debug: 16/40
(40 %) isolated and 25/60 (42 %) standalone. ⚠ Once `verify` reaches its test stage, expect this to red
roughly 2 runs in 5, not 1 in 10. Plan the BASE clock accordingly.

#### 4.5.4 Verification bar

⚠ **Report exit codes, not pass counts.** SIGBUS is `rc=135` and a trailing `echo` will launder it —
this repo has that exact scar. Capture `rc=$?` on the line immediately after pytest.

1. **60 consecutive green isolated-node runs** (~4 s each ≈ 4 min). At the measured `p=0.417` that is
   `0.583^60 ≈ 9e-15`; even at the pessimistic wheel rate `p=0.10` it is `0.9^60 = 0.0018`.
2. **3 consecutive green whole-file runs** (~150 s each ≈ 8 min) for cross-test interaction.

⚠ Narrowing the race window is not fixing it. A gate that fails 3 % of the time still launders.

#### 4.5.5 Two findings handed forward — not this slice's to fix

- ⚠ **The trap is product-facing, not just a harness quirk.** Any Python program opening a stdlib
  `sqlite3` connection to the DB file while a FathomDB `Engine` is open *in the same process* is in the
  identical two-copies configuration. Reading from a separate process is fine. Classifying OOS-18 as a
  harness hazard is right about the *test*, but the underlying constraint is a consumer-facing
  documentation gap. **Tracked as TC-143 — report it, do not fix it here.**
- The TS mirror already states the discipline the Python test lost: `src/ts/tests/`'s slice20c mirror
  declares in its header that `node:sqlite` is used "only as a READ oracle on a CLOSED database" — a
  third independent SQLite copy, deliberately kept outside the hazard. The Python file has no
  equivalent rule. Latent siblings exist (other Python tests take in-process raw `mode=ro` probes but
  open no live-embedder engine, so nothing triggers). Converting them prophylactically is not in this
  slice.

### 4.6 B6 — TC-139

## 9. Why the CI rehearsal is last, after landing

This ordering is not discretionary:

1. **`verify-release-gates.sh` check 3 requires HEAD to be reachable from `main`.** It resolves
   `refs/heads/main` and runs `git merge-base --is-ancestor "$head_sha" "$main_ref"`, dying if HEAD is
   not an ancestor. A dispatch from a slice branch therefore dies at the `verify-release` job, before
   it proves anything about the publish path.
2. **`workflow_dispatch` inputs are read from the default branch only.** The PHASE 0b confirmation
   input is not dispatchable until after the land. ⚠ A pre-land dispatch that does not offer the new
   input is **not** evidence the guard is broken — it is evidence the input is not on `main` yet.

**Consequence:** land first, rehearse second. Do not let a failed pre-land dispatch trigger a fix round

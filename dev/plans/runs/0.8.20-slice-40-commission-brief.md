### 1e.1 ⛔ The cause is NOT `mode=ro` — the Steward's own hypothesis was WRONG

The Steward briefed the probe toward a `mode=ro` vs `immutable=1` hypothesis. **The probe disconfirmed it,
and the record is corrected here rather than quietly dropped.** `mode=ro` is the repo's **sanctioned**
pattern and this test is **already using it correctly**: `verify_embed_db.py` documents that a verifier
must see *committed-but-not-yet-checkpointed* rows in the `-wal`, and that **`immutable=1` reads only the
main DB and would report an empty DB** — the same note recurs across six engine test files.
⛔ **Switching to `immutable=1` is not a narrower fix, it is a WRONG one**: it would make the
late-enrolment assertion fail **deterministically**. `STATUS-0.8.1.md` records that exact scar.

### 1e.2 The real mechanism — TWO independently-linked SQLite copies in ONE process

**Steward-verified:** `fathomdb-engine/Cargo.toml` declares `rusqlite = { version = "0.31", features =
["bundled"] }`, so the engine links its **own statically-bundled** SQLite; Python's `sqlite3` links the
**system** `libsqlite3` (3.45.1 on this box). SQLite's WAL concurrency contract is defined over
**processes**, and its workaround for POSIX advisory locks — where `close()` of *any* fd on an inode drops
that process's locks — lives in a per-library-copy inode cache **the two copies do not share.** Two copies
in one process therefore steal each other's locks and invalidate each other's `-shm` mappings.

**Measured decisively — same test body, same SQL, same `mode=ro`, only the probe relocated:**

| arm | SIGBUS | n |
|---|---|---|
| raw `sqlite3` probe **in-process** (status quo) | **25** | 60 |
| identical probe **in a child process** | **0** | 60 |

`P(0 of 60 \| p=25/60) ≈ 9e-15`. **The process boundary is the whole story.**

### 1e.3 The fix — one Python file, no Rust, no rebuild

In `src/python/tests/test_slice20c_flush_barrier.py`, funnel the read-only raw-SQL oracles
(`_query`, `_vector_kind_registered`, `_leaf_rows_without_vectors`, `_leaf_rows_of_kind_without_vectors`,
`_active_cursor`, `_terminal_state`, `_fts_row_exists`, `_projection_failure_rows`) through **one helper
that executes the query in a CHILD OS PROCESS** — same `sqlite3` module, same `file:{path}?mode=ro` URI,
same SQL, same parameters, same tables, same point in the test.

- ⛔ **Use `subprocess`, NOT `multiprocessing`.** `multiprocessing`'s default `fork` on Linux would fork a
  process holding live SQLite handles **and a running Rust embed-worker thread** — a *different*, real
  hazard. `subprocess.run` (fork+exec) runs no Python in the forked image; the child inherits fds but
  **not** locks.
- ⚠ **`_terminal_state` returns `str | None` and `_fts_row_exists` returns `bool`** — the child must
  distinguish "no row" from a value. **Do not force every oracle through an `int` return**; that would
  silently convert a missing row into a value and **weaken the oracle**.
- **Leave the two read-WRITE injector connections alone** — both run after `engine.close()`, outside the
  hazard class.
- Cost: ~64 call sites × ~35 ms interpreter start ≈ **2 s** added to a ~150 s file.

**Why this ELIMINATES rather than narrows:** it removes the foreign SQLite copy from the engine's process
entirely. What remains — a separate process reading a live-WAL DB `mode=ro` — is exactly what SQLite's WAL
design supports and what `verify_embed_db.py` already relies on as a live post-drain gate.

**Why it does not weaken the oracle:** the file's docstring is explicit that the raw-table read is
load-bearing *because it is independent of the engine's own view* — "a harness that only reads readiness
back PASSES against the defect". The child probe is the same stdlib reader, same SQL. Only the address

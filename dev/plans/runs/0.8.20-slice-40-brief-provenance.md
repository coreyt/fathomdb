## 1. Why the brief carries a verification legend

Three consecutive Steward briefs for this slice shipped confidently-worded factual assertions nobody
measured (`seq-195`, `seq-196`, `seq-197`, `seq-205`). One of them would have deleted an idempotency
guard one step from an irreversible three-registry publish. The v4 brief's stated base was `1f85ca2a`,
four commits behind v5's base, so every `file:line` it carried was suspect.

The standing rule that came out of it: state the symptom and the determination duty; do not name a fix
you have not measured.

The brief broke that rule twice in its own authoritative table (§3 and §4 below), which is why it now
also carries a claim-confidence section rather than presenting every number as equally witnessed.

## 3. Retracted: "refresh the stale `git_blob_sha1` provenance"

A diagnosis agent reported that only the provenance claim in `scripts/governed-surface-pin.json` was
stale. The Steward propagated that into the brief's BASE table without opening the pin file. The
instruction as written was to edit the signed pin — the forbidden action under "escalate a pin trip,
never clear it" — and it was also wrong on the facts.

Measured at HEAD:

- `scripts/governed-surface-pin.json`'s `git_blob_sha1` is `140c0f63…`
- `git rev-parse HEAD:src/conformance/governed-surface-allowlist.json` is the same `140c0f63…`
- `bash scripts/check-governed-surface-pin.sh` exits 0

The pin is correct. The stale artifact is the test, which hardcodes the superseded commit `427d2712`
in its provenance arm. The brief now says to fix the test.

This is the `seq-195` shape — an instruction that satisfies a gate by weakening it — appearing inside
the document written to prevent it. The adversarial review caught it.

## 4. Retracted: "quote `$PRUNE_EXPR`" (TC-139)

A diagnosis agent proposed quoting the variable in `scripts/repo-prune/bin/context-clarity.sh` and the
Steward wrote it into the BASE table without running it. It does not work. `PRUNE_EXPR` holds a
sequence of `find` predicates (`-path */target -o -path */node_modules …`), so `find` requires
word-splitting to see them as separate arguments; quoting hands `find` one giant argument.

| form | result |
|---|---|
| `find . \( "$PRUNE_EXPR" \) …` (the proposed fix) | `Unknown argument` — the script dies |
| `find . \( $PRUNE_EXPR \) …` with globbing on (status quo) | prunes leak — `b/target` survives |
| `find . \( $PRUNE_EXPR \) …` with globbing off (`set -f`) | correct — both `target` dirs pruned |

The defect is glob expansion, not word-splitting. Both `set -f` and a bash-array form were measured to
work; the brief leaves the choice to the slice.

Together with §3, this is the same discipline failure twice: an agent's diagnosis was sound, its
proposed fix was wrong, and the fix was propagated unmeasured. Verify the fix, not just the diagnosis.

## 5. Retracted: "push the branch and open CI"

An earlier draft's BASE-2 gate said to push and observe CI. That is unsatisfiable. `.github/workflows/ci.yml`
triggers on `push: branches: [main]` and `pull_request` only — no `workflow_dispatch`, no wildcard
branch push. Pushing a feature branch produces no CI run at all, so the gate would have had nothing to
observe. The brief now requires a pull request, which is what Slice 39.5 did (its CI baseline came from
PR #167).

## 6. Retracted: a `DRY_RUN` read-out that cannot fail

An earlier draft required reading the resolved `DRY_RUN` out of the run log before any
`publish-rust-t*` job started, without establishing that the value is printed anywhere.
`grep -n DRY_RUN .github/workflows/release.yml` returns the workflow-level `env` assignment and nine
`if [ "${DRY_RUN}" = "true" ]` shell tests — nothing that prints it. GitHub does not render
workflow-level `env` in the run log, so the earliest observable point was inside a `publish-rust-t*`
step, after the job the check was supposed to precede.

As written it was a measurement that cannot fail: an orchestrator could look, find nothing, and report
the check satisfied without ever observing the value — on the compensating control for the second
irreversible publish path. The brief now makes emitting that line PHASE 0b work.

## 7. Retracted and corrected: the OOS-18 record

**The `mode=ro` hypothesis was the Steward's own, and the probe disconfirmed it.** The Steward briefed
the probe toward a `mode=ro` vs `immutable=1` comparison. `mode=ro` turned out to be the repo's
sanctioned pattern, already used correctly: `src/python/eval/verify_embed_db.py` documents that a
verifier must see committed-but-not-yet-checkpointed rows in the `-wal`, and that `immutable=1` reads
only the main DB and would report an empty DB — a note that recurs across six engine test files.
Switching to `immutable=1` would not have been a narrower fix; it would have made the late-enrolment
assertion fail deterministically. `STATUS-0.8.1.md` records that exact scar.

The real cause is two independently-linked SQLite copies in one process. It is recorded in the brief.

**The oracle inventory was wrong in both directions.** An earlier draft's list of functions opening
their own raw connection omitted `_active_edge_cursor` and `_pending_node_rows_below` — both called
inside a live-`Engine` block, the exact hazard configuration — and listed `_projection_failure_rows`
and `_leaf_rows_without_vectors`, which open no connection of their own. Following it literally would
have fixed six of eight and left two live, with the verification bar unlikely to catch the difference.
The brief now carries eight names and an instruction to re-derive them.

**The call-site count moved.** An earlier draft said "~64" helper call sites. Two independent counts
give 54 and 58 depending on the regex. It is a cost estimate, not a gate; either way the added cost is
about 2 s on a ~150 s file.

## 8. Corrected twice: the actionlint fixture loop

v5 said the tier loop in `scripts/tests/test_actionlint_fixture.sh` exits 1 on the first failure, so
only one defect surfaces and defect 2 is masked. Fix-round 1 said 39.5's conversion made both visible.
Both are wrong.

Measured: the loop does accumulate — it increments `TIER_FAILED` and reports all seven tiers, and
there is no `exit 1` inside the loop (the only one is at end of file). But defect 2 still does not
surface, for a different reason: the loop's only tier assertion greps each job block for the
`cargo publish --dry-run -p ` literal, and nothing asserts the job block exists. A misnamed tier
produces an empty block from `awk`, the grep fails, and it emits the identical defect-1 message.
Observed: 7 FAIL lines, all defect-1-shaped, none naming the swap.

The swap is invisible to the suite by construction, not by masking. The consequence the brief now
carries: making the suite green is satisfiable without ever noticing the swapped names, so the
determination must add a job-block-exists assertion.

A related retraction: v5's DoD required proving "the loop no longer masks a later tier". At HEAD the
loop already reports every failing tier, so that clause was satisfiable with zero change. It was
dropped.

## 9. Retracted: three counterfactual or dead findings

**The AWAITING-SIGN-OFF board item.** v5 told the slice to report that the allowlist `_comment` still
contained the literal `AWAITING HITL SIGN-OFF, NOT SIGNED`. `grep -c` for that literal in
`src/conformance/governed-surface-allowlist.json` is 0, and the board had already been corrected by
the `seq-207`/`seq-208` reconcile — the surviving board occurrences are the quoted superseded text plus
its correction. The `_comment` re-pin is done (`seq-208`, `c239908b`), not owed. Reporting it again
would have re-opened a closed item and burned a fix round. v5 inherited it from hand-off `-A`, which
`seq-216` lists as superseded.

**The "run suites individually" trap.** v5's trap list said `agent-test.sh`'s aggregate exit is
vacuous, that it aborts at `agent-test.sh:73`, and instructed running suites individually. 39.5
converted the harness to collect-all-then-report; the cited anchor moved and `run_capped` is no longer
the call form. The instruction contradicted the brief's own BASE exit criterion. What survives is
narrower: the harness's non-zero exit must still be honoured, and each suite's `rc` must still be
quoted — collect-all reports them all in one run.

**The suite-count argument.** v5 argued the correct figure was 31 `run_capped` call sites against a
hand-off claiming 35. 39.5's conversion replaced the call form entirely: at HEAD
`grep -c '^run_capped' scripts/agent-test.sh` is 0 and `grep -c '^run_suite' scripts/agent-test.sh` is
32. Every count in that argument — 31, 34 and 35 alike — is now wrong. Only the shape of the
disagreement is worth remembering: anchored versus unanchored grep.

brief fact-checker, ruled to 0.8.21) is the durable fix. The brief now states the anchors-are-hints
rule once and prefers greppable symbols.

## 12. Claim classing at v6

Two agent inferences were checked and one was overturned: an agent reported the pyright gate "red since
0.8.18" as established; the defensible statement is red on every run where `verify` executed in the
retained window, with the drift dated to `f2f843ed`.

**Steward-re-verified from source** — opened directly, not taken from a report:

1. `TransactionBehavior::Immediate` has exactly one call site in `fathomdb-engine/src/lib.rs`, in
   `commit_batch`; `commit_projection_outcomes` opens a plain `connection.transaction()`; the worker
   commit error is discarded at two `let _ = commit_projection_outcomes(...)` sites. An earlier draft
   said the symbol "occurs exactly once" — `grep` returns two hits, the call plus a comment referencing
   it elsewhere. One call site, two occurrences. The distinction matters because the claim sat in the
   class readers are told they need not re-check.
2. `release.yml` contains `cargo publish --dry-run -p` zero times.
3. `default-embedder-tests` runs only two named test targets, so there is no full-workspace
   `cargo test` on Linux anywhere in `ci.yml` (→ TC-141, ruled to 0.8.21).
4. `_fathomdb.pyi` is hand-maintained — its own docstring says so and no generator exists in
   `scripts/`. "Regenerate the stub" named an action that does not exist; it is a manual sync.
5. `agent-verify.sh` is four stages, not the three an earlier Steward brief stated.
6. `_fathomdb.abi3.so` is gitignored (`git check-ignore -v`), so the sanctioned rebuild dirtied nothing
   tracked.

**Agent-measured and relayed** — the Steward verified the mechanism but did not independently reproduce
the arithmetic:

- `83/92 = 90.2 %` `rust-windows` failure, and the `repeat_embeds` distribution (min 205 / median 370)
- `105–119` Linux `repeat_embeds` over 200 rows, and the `taskset` core-count control
- governed-surface-pin arms. Earlier drafts said `46/46` and `45 of 46`; Steward-measured is 89 arms,
  88 PASS / 1 FAIL. The `46` was never right.
- `863 passed, 6 skipped` for `test-python` post-rebuild
- `8 of 9` security gates passing, and the `STRICT=1` vs `AC037_LIVE_OPTIONAL=1` rc split
- `6 of 7` pyright errors cleared by a stub-only edit, measured in a scratch copy
- all of the OOS-18 rates — `25/60` in-process vs `0/60` child-process, `16/40` isolated, the ~40 %
  debug-build rate, and the `9e-15` probability. "Steward-verified" in that section applies only to the
  static facts: the `rusqlite` bundled feature, the sanctioned `mode=ro` pattern, the oracle inventory,

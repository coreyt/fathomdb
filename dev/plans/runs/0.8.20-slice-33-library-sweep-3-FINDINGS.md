### 2.3 The decomposition that bounds the work — method, not just result

**28 direct dependencies are behind. Only 11 of them need a judgement.** The step that gets from 28 to 11
costs nothing and is worth stating as method, because it is the behaviour the three-slice tool investment
was supposed to produce: **reduce the work with data before spending tokens on judgement.**

The question is mechanical — *does the constraint we have ALREADY DECLARED admit `latest`?* It is computed
from `declared_in[].constraint` and `latest_version`, two fields REQ-14 put in the report precisely so
Slice 33 re-derives nothing, evaluated with each ecosystem's own comparator (semver for cargo/npm, PEP 440
for pypi). **0 of 28 constraints were unparseable.** Where the answer is *yes*, the upgrade needs **zero
SLOC of manifest change** — a re-lock lands it — and no changelog needs reading to say so.

### 3.5 `jsonschema` 0.18.3 → 0.49.2 — SURGICAL-LIKELY (~2 SLOC)

**31 minors on a pre-1.0 crate, and it is still surgical — because the repo's surface is two lines.**

**The change:**
1. `src/rust/crates/fathomdb-engine/src/lib.rs:31` — `use jsonschema::JSONSchema;` → drop, or

2. `src/rust/crates/fathomdb-engine/src/lib.rs:16513` — `JSONSchema::compile(&schema)` →

`lib.rs:16514` (`compiled.validate(&payload).map_err(|_| …)`) needs **no** change: 0.26 changed

> This engine compiles **arbitrary user-supplied schemas**. In-repo fixtures are draft-agnostic

> ⚠ **`--output-dir .` is the one a reviewer would miss, and omitting it breaks the release silently.**
> v2 placed the artifact relative to `process.cwd()` — i.e. `src/ts/`. v3 defaults the output to the
> **crate** directory instead. Without the flag the `.node` lands in `src/rust/crates/fathomdb-napi/`, and

> **uploads nothing, without failing.**

**What does NOT need changing, contrary to the published migration guide.** The guide lists
`napi.name → napi.binaryName` and `napi.triples → napi.targets` as breaking. In the actual v3 config loader
both old keys are still honoured as *deprecated-with-warning*, not removed, so the `"napi"` block at
`src/ts/package.json:30-36` can stay as-is (it will emit two deprecation lines). **That is what keeps this
at ~3 SLOC instead of ~9** — and it is a case where reading the source beat reading the migration guide.

#### The napi coupling — the most decision-relevant fact in this survey

**The CLI bump can land alone, and it is a one-way prerequisite for 0.8.22's `napi` 2→3 Rust migration.**
The coupling is **asymmetric**:

- **CLI 3 + `napi`/`napi-derive` crate 2 — works.** v3 sets `NAPI_TYPE_DEF_TMP_FOLDER`; napi-derive **2**
  reads only `TYPE_DEF_TMP_PATH`, so no intermediate type-defs are written and the CLI emits a header-only
  `index.d.ts`. **Inert in this repo:** `src/ts/index.d.ts` is gitignored (`.gitignore:59`), sits outside
  both tsconfig `include` globs, and nothing consumes it — `src/ts/src/binding.ts` and `platform.ts`
  implement their own `.node` loader, and the build already runs with the JS generator off. Only cost: a
  forced cargo rebuild each run.
- **The reverse is a HARD FAILURE.** napi-derive **3** *panics at proc-macro expansion* when
  `TYPE_DEF_TMP_PATH` is set — and CLI **2** is exactly what sets it. The panic message is explicit:
  *"missing environment variables. please upgrade `@napi-rs/cli` to the latest version."* So
  **`napi = "3"` with `@napi-rs/cli@2` will not compile.**

**Consequence for 0.8.22 sequencing:** the Rust half cannot move without the CLI bump already in place.
Either land the CLI first, or move both in one commit. **This survey found the ordering constraint that
`seq-151`'s `napi 2→3` item did not record.**

*Two things to check at merge, neither SLOC:* `@napi-rs/cli@3.8.0` declares
`engines.node: ^20.17.0 || ^22.13.0 || >=23.5.0`; CI pins `node-version: "22"`
(`release.yml:151`, `:497`), which satisfies it but is now a **floor** rather than a free choice. And the
permissive direction above is **source-level inference** — upstream never states the compatibility policy.
**One `npm run build:native` against `@napi-rs/cli@3.8.0` with the Rust side untouched, checking that
`src/ts/fathomdb.linux-x64-gnu.node` appears and loads, settles it.** That was not run here.

### 3.9 `typescript` 6.0.3 → 7.0.2 — **UNDETERMINED**

**The edit is 1 SLOC and is known.** `src/ts/package.json:28`, `^6.0.3` → `^7.0.2`. **No `tsconfig` key
needs to change** — both `src/ts/tsconfig.json` and `tsconfig.build.json` were checked against 7.0's full
removal/default list and clear it: no `target: es5`, no `downlevelIteration`, no `moduleResolution:
node/node10/classic`, no `module: amd/umd/systemjs/none`, no `baseUrl`; `esModuleInterop` and `strict`
already `true`; `types`, `rootDir`, `module` and `target` all already explicit; and there are **no
side-effect imports** anywhere in `src/` or `tests/`, so the new `noUncheckedSideEffectImports` default
cannot bite.

**So why UNDETERMINED rather than SURGICAL-LIKELY?** Because the question is whether the change would
*likely land*, not whether the diff is small — and TypeScript 7.0 is **the completed Go-native compiler
port**, shipped under the ordinary `typescript` package and the normal `tsc` command. **Swapping the
compiler implementation is not a version bump in the sense the other ten rows are**, and this one is in the
**shipped emit path, not a dev-only type-check**: `scripts.build` and `.github/workflows/release.yml:502`
run `npx tsc -p tsconfig.build.json` to emit `dist/`, and `dist/` is what is published (`files: ["dist"]`,
`main: dist/index.js`, `types: dist/index.d.ts`). `tsc` produces both the published JS and the published
`.d.ts`.

**I am deliberately down-grading the researcher's `SURGICAL-LIKELY` here.** The 1-SLOC finding is solid and
is recorded above so 0.8.22 need not re-derive it; but whether a different compiler emits zero new
diagnostics across 6 source and 44 test files **cannot be told cheaply, and was not tested.** Labelling it
SURGICAL-LIKELY would invite 0.8.22 to schedule it as a quick win. **It is not one.**

**The named tripwire, so the check is cheap when someone does run it:** six `@ts-expect-error` directives —
`tests/functional-graph-arm.test.ts:70,75`, `tests/embedder-event-narrowing.test.ts:54,58,62`,
`tests/exp-obs-explain.test.ts:174`. Each becomes an **unused-directive error** if the Go checker declines
to report an error at that exact site. `tests/embedder-event-narrowing.test.ts:7-47` is explicitly built
around that mechanism and is the file most likely to break.

**One risk that does NOT bite here:** 7.0 ships without a stable programmatic API, blocking typescript-eslint
and framework language services until 7.1. This repo has **no TS linting at all** — `scripts/agent-lint.sh:34`
is literally `skip_notice lint-ts "ESLint not configured"` — and `tsc` is only ever invoked as a CLI.
Secondary: `npm ci` will begin pulling `tsc` as a per-platform native binary.

**What would settle it:** `npm run typecheck` and `npm test` under 7.0.2.

## 5. Unknowns — every `status="unknown"` row, with its reason

13 rows of 774 (**1.7%**) are `unknown`. **None is a registry outage.** Every one falls into one of two
structural classes, and both were diagnosed here rather than left as "unknown".

**REQ-10 holds throughout: not one row is falsely reported `current`.** That is the failure this tool most
had to avoid, and it did.

### Class 1 — the dependency has no stable release (2 rows)

| row | locked | crates.io says |
|---|---|---|
| `ort` (**shipped**, cargo, **direct**) | `2.0.0-rc.10` | `max_stable_version: null`, `max_version: 2.0.0-rc.13` |
| `ort-sys` (shipped, cargo, transitive) | `2.0.0-rc.10` | same |

`HttpRegistrySource.latest()` reads `payload["crate"]["max_stable_version"]`
(`scripts/sbom-survey/sbom_survey/registry.py:92`). `ort` — the ONNX Runtime binding adopted at 0.8.16 —
has never published a stable version, so that field is `null`, the lookup returns `None` without raising,
and the row degrades to `unknown` **with no `lookup_error` to explain it**.

⚠ **This is the one unknown whose consequence is substantive — but it is NOT neglect, and must not be read
as such.** The `=2.0.0-rc.10` pin is **exact and ruled**: `fathomdb-embedder/Cargo.toml:39-44` records
`RC PIN ACCEPTED BY HITL 2026-07-08`, notes that the `ort` 2.0 line publishes **only** release candidates
(1.x being EOL), and states that `rc.10` is deliberately the newest RC that builds cleanly in the offline
envelope — **`rc.12` carries an `ort`/`ort-sys` VitisAI EP mismatch.** The eventual 2.0-STABLE bump is
already tracked as **TC-9**. `ort` is additionally `optional = true` behind an `onnx-embedder` feature with
`default = []`.

**The finding is about the tool, not the dependency (TC-119):** when TC-9 comes due, **this survey cannot
help with it.** It can neither see `rc.10`→`rc.13` nor say whether `rc.13` resolves the very defect that is
the stated reason for the pin. A dependency-hygiene tool is blind on precisely the dependency that carries
an open hygiene todo. The behaviour remains *honest* — never `current` — but it is a permanent blind spot
for any dependency living on pre-releases by design, and this repo has exactly one, deliberately.

### Class 2 — no locked version is reachable, so there is nothing to compare (8 rows)

| rows | declaring manifest | why there is no locked version |

For all eight, `latest_version` **was** resolved successfully from PyPI — only the left-hand side of the

### The 13th row

`packaging` (dev-tooling, pypi, direct) is the **only** row whose `lookup_error` is populated *and*
explanatory: the tool declares `packaging>=24.0,<26.0`, `src/python/uv.lock` locks `26.2`, and the
constraint admits none of the locked builds — so the declaration attaches to nothing and no locked version
is recorded. This is the Slice-32 fix-1 constraint-matching rule behaving exactly as designed, and it has
surfaced a genuine cross-project skew: **the tool's own upper bound `<26.0` is behind the `packaging` the
rest of the repo resolves.** Low priority — the projects are isolated so they never share an environment —
but it is real and belongs in §4.

### The reporting gap this exposes — TC-117

**10 of the 13 unknown rows carry `lookup_error = null`.** Design §5.8 states that `lookup_error` records
*"why a row is `unknown`, so §5 of the findings doc writes itself"*. It does not: for 77% of the unknown
set this section had to be written by hand, from the source and from a direct crates.io probe. The cause is
structural — `lookup_error` is populated from a **raised exception**, and neither `max_stable_version: null`
nor "no locked version" raises anything.

This is a **reporting gap, not a correctness gap**: REQ-10's hard guarantee (never falsely `current`) is
intact. **NOTED, NOT FIXED** — the sbom-survey implementation and its suite are frozen in this slice.

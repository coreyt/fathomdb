# Slice 40 epoch orchestration control

**Status: HITL-directed operational plan (2026-07-31).** This control changes
how Slice 40 is coordinated; it does not change the slice's requirements,
release-state facts, acceptance criteria, or final publish gate.

## Purpose

Slice 40 is one indivisible release slice, but its BASE work, CI observation,
release mechanics, acceptance work, and rehearsal are too broad for one
long-lived orchestrator transcript. Treat **orchestrator** as a role that is
handed over at bounded checkpoints, not as one indefinitely running agent.

Only one Slice 40 orchestrator is active at a time. The Steward verifies the
prior epoch's receipt from Git and CI before commissioning the next fresh
orchestrator.

## Authority and boundaries

```text
HITL → direction, schedule/record changes, and publish approval
Steward → commission, receipt verification, reconciliation, HITL escalation
Orchestrator → one epoch's task graph, isolated implementers, reviews, receipt
Implementer → one bounded patch in one isolated worktree
Reviewer → independent verdict; never the patch author
```

The existing Slice 40 brief remains authoritative for technical scope and all
stops. In particular, no epoch may create a tag, trigger a non-dry-run
dispatch, or publish. Explicit HITL approval is still required after gate (i)
is satisfied.

## Epochs

| Epoch | Scope | Completion receipt must prove |
| --- | --- | --- |
| E0 | Regenerate manifest, verify `{{MANDATE}}`, and independently review the manifest/brief pair | commission control is clean; no implementation begins on an actionable review finding |
| E1 | BASE: coordinate B1–B10/B8b, integrate the one BASE push, and observe its CI run | exact branch/base/head, commits, local exit codes, CI run and job conclusions |
| E2 | BASE remediation and the five-consecutive `rust-windows` accrual | BASE gate is green or a bounded, evidenced blocker is escalated |
| E3 | Phases 0–3: determination, versioning, dry-run mechanics, and smoke work | checkpoint C evidence, including the fixed smoke `source_id` defect |
| E4 | Phases 4–6: acceptance, cut obligations, and explicit known-gap reporting | checkpoint E obligations discharged or reported exactly as ruled |
| E5 | Phase 7 landing/rehearsal evidence | landing CI evidence; hard stop before tag/publish |

E1 groups B1+B2 and B8+B8b because each pair shares a gate and/or workflow
surface. It starts with one canary implementer. After the canary is verified,
at most three non-overlapping implementers may run concurrently, each in a
pre-created worktree from `origin/main`.

## Epoch handoff protocol

The Steward sends each fresh orchestrator a brief containing only the relevant
Slice 40 sections, the manifest, the preceding receipt, the immutable base
SHA, and the next hard stop. An orchestrator must not carry work past its epoch
boundary.

The departing orchestrator returns this receipt, with no raw-log dump:

```text
epoch / base_sha / branch / head_sha
implemented units and commit SHAs
focused and full verification commands with real exit codes
CI run IDs and per-job conclusions
independent review verdict and transcript path
open blocker, decision owner, and exact next action
```

The Steward rechecks branch ancestry, changed paths, command outcomes, and CI
before sending the next brief. A stale receipt or a silent agent is not a pass:
the Steward polls Git and task activity and commissions a fresh agent instead
of reviving a cold, bloated one.

## Harness capability preflight

This plan requires actual role-enforced orchestrator and implementer agents,
isolated worktrees whose Git metadata is writable, and bidirectional messages.
The current collaboration harness can spawn generic agents with role prompts,
but cannot set the repository's `subagent_type`; it is therefore a simulation,
not enforcement. The companion `dev/experiments/s40-epoch-handshake/` project
tests the message and receipt protocol only. Do not begin E1 until the real
role/worktree capability is available or the HITL explicitly accepts the
simulation for that epoch.

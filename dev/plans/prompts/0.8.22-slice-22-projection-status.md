# Slice 22 — PROJ-STATUS

## Mandate

Add a governed, pure-read projection-status API so a caller can observe current
runtime availability, per-projection dense readiness, and unsupported vector
kinds without re-applying a caller-owned declaration. This is a new public verb
in Rust, Python, and TypeScript; it requires a fresh governed-surface decision
and conformance update before implementation.

## API contract

The proposed spellings are:

- Rust: `Engine::read_projection_status()`;
- Python: `fathomdb.read.projection_status(engine)`; and
- TypeScript: `read.projectionStatus()`.

It returns one explicitly new status type containing:

- `runtime_embedder_available: bool`, which means that this session has an
  embedder accepted by the existing identity and vector-equivalence safeguards;
- `runtime_unavailability_reason: "none" | "no_runtime" |
  "vector_equivalence_disabled"`, a lowercase wire contract that is `"none"`
  exactly when the runtime is available and otherwise tells the caller why this
  session cannot retrieve densely;
- one entry per declared projection, each with
  `not_declared | unavailable | embedding | ready` (`not_declared` applies when
  that declared projection has no vector arm); and
- the current sorted `vector_unsupported_kinds` report, which is `[]` when no
  projection declares a vector arm.

The status call is pure: it must not configure projections, schedule work,
write storage, or require a writable database handle. Its readiness remains
corpus-wide under the current shared dense pipeline; per-projection entries
therefore repeat the same runtime state for every declared vector projection.

## Gate and boundaries

Before RED tests, record the new C5 governed-read verb in the allowlist/signing
process. A changed allowlist without a matching explicit decision is a halt,
not a documentation cleanup. This slice does not add `raise_for_unsupported`,
change `ProjectionSpec`, persist status, introduce per-attribute vector
readiness, or rename `ProjectionDelta` lists.

## TDD sequence

1. Read and review `dev/design/0.8.22-slice-22-projection-status.md`.
2. Commit RED engine tests for each status value, both runtime-unavailability
   reasons, mixed committable and unsupported kinds, `[]` without a vector
   declaration, sorted deterministic output, and a no-mutation proof.
3. Commit RED Python and TypeScript functional/conformance tests for exact
   lowercase wire spellings, Rust-enum mapping, and cross-binding parity
   against one real database.
4. Implement the engine type/read method, bindings, type declarations,
   allowlist/signature artifact, and interface documentation until green.
5. Refactor only after green and obtain independent review before landing.

## Acceptance criteria

| ID | Requirement | Falsifiable acceptance signal |
| --- | --- | --- |
| S22-AC1 | The status API is pure and current. | Raw-table/no-mutation fixture proves no configuration or scheduler write; repeated calls reflect current durable/runtime facts. |
| S22-AC2 | Every declared projection reports an unambiguous state. | Fixtures cover a non-vector declaration (`not_declared`) plus vector declarations in `unavailable`, `embedding`, and `ready`. |
| S22-AC3 | Dense unavailability is explainable. | Fixtures distinguish `"no_runtime"` from `"vector_equivalence_disabled"`; the reason is `"none"` exactly when the runtime is available, with a tested Rust-enum mapping. |
| S22-AC4 | Unsupported-kind reporting is current and honest. | A mixed-kind fixture returns the sorted, deduplicated noncommittable kinds without requiring a re-apply; a no-vector fixture returns `[]`. |
| S22-AC5 | SDK parity is complete. | Rust, Python, and TypeScript functional tests obtain equivalent status from the same real database. |
| S22-AC6 | The governed surface is signed and consistent. | Allowlist, interface docs, Python/TS surface tests, and the explicit decision artifact agree on the new verb. |
| S22-AC7 | Release verification remains clean. | `./scripts/agent-verify.sh` and full-workspace clippy/check with `--all-targets` exit 0. |

## Required review

Independent review must verify that the new method is a status read rather
than a configuration echo, that runtime availability and its reason have no
overloaded meaning, and that it does not claim per-attribute readiness the
engine cannot currently observe.

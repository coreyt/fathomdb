# B5 trusted test-only verification design

## 1. Decision and purpose

This is the bounded successor design authorized by HITL ruling `seq-235` for
0.8.20 Slice 40 B5. It does not authorize implementation, integration, CI
dispatch, a release-record change, or E2.

B5 must demonstrate that moving OOS-18's live raw-SQL oracle into a child
process removes the mixed-SQLite in-process SIGBUS without weakening the
independent oracle. The required bar remains exactly the Slice-40 brief's
60 consecutive isolated runs and 3 consecutive whole-file runs, with each
pytest exit status captured immediately.

The earlier B5 candidate is permanently excluded. Its trust claim rested on a
repository-controlled workflow plus a source-level workflow guard. Three
independent reviews found distinct, actionlint-valid containment bypasses; the
last accepted `permissions: write-all` at job scope. This design must therefore
not add a B5 GitHub workflow, B5 CI runner, CI/source-route guard, or a repair
to any of those files.

## 2. Chosen boundary: a capability-confined test appliance

The evidence route is a pre-provisioned, rootless, test-only appliance owned by
the release operator, outside the repository and outside GitHub Actions. The
operator uses an approved immutable appliance image and a trusted supervisor.
The repository supplies only the reviewed source tree; it cannot grant the
running test any credentials or authority.

Before an appliance may run B5, a versioned, pre-approved supervisor/appliance
policy artifact must be published outside the candidate source tree at an
immutable, reviewer-resolvable identifier. The artifact fixes the supervisor
version, image digest, exact commands and pytest targets, feature list,
confinement settings, receipt schema, attestation signing-key identity and
verification material, and capability-probe commands. The Steward and an
independent reviewer approve that immutable policy identifier before it is used.
A source commit, a mutable container tag, a free-form operator command, or an
unversioned runbook is not a policy artifact.

The supervisor must create a fresh, disposable execution directory from the
reviewed commit and run the following fixed sequence. The sequence is part of
the approved policy artifact, not a script, workflow, or command string read
from the source tree.

1. Verify a clean, detached source tree at the reviewed candidate SHA and copy
   it to an appliance-local scratch directory.
2. Create a new appliance-local virtual environment and build the canonical
   editable `fathomdb._fathomdb` binding there with
   `pyo3/extension-module,test-hooks,default-embedder,default-reranker`.
3. Probe all three symbols defined by
   `src/python/tests/_test_hooks_gate.py`: `Engine._configure_vector_kind_for_test`,
   `Engine._write_vector_for_test`, and `force_panic_for_test`. A missing symbol
   fails the run before pytest begins.
4. Run the reviewed B5 isolated target 60 times consecutively, then the
   reviewed `test_slice20c_flush_barrier.py` file 3 times consecutively. Capture
   the real exit status directly after every pytest invocation and stop on the
   first nonzero status.
5. Emit a supervisor-owned, cryptographically authenticated receipt only after
   all 63 invocations exit zero.

The editable build is canonical for the Python test suite: it uses the same
`maturin develop` feature path that `tests/conftest.py` recognizes, but in a
new virtual environment that belongs only to the appliance's scratch source
tree. It neither modifies a developer environment nor changes a shipping wheel.

## 3. Non-negotiable appliance properties

The operator must verify these capabilities before treating any receipt as B5
evidence:

| Property | Required control |
| --- | --- |
| No credentials | No GitHub token, registry credential, SSH agent, cloud credential, or mounted host secret is available to the appliance. |
| No network | The test process has no network namespace route or egress capability. Package tools and build inputs are pre-provisioned in the immutable image. |
| No host authority | Rootless execution; no Docker/Podman socket, privileged mode, host PID namespace, device mounts, or writable host mount. |
| No repository mutation | The reviewed source is copied to scratch. The source input is read-only and the original checkout is never mounted writable. |
| No durable artifact | Build products, virtual environment, databases, and scratch source are destroyed after the run. The only retained output is the supervisor receipt. |
| Receipt integrity | The untrusted test process cannot write the receipt path. The supervisor signs a receipt that binds the candidate SHA, policy identifier and digest, image digest, fixed command set, and every immediate exit event. |
| Probe reproducibility | The policy fixes probes for uid/user namespace, network namespace and routing, mounts, effective environment, and credential/secret absence; their raw output is attached to and hashed into the receipt. |

These controls are capability controls, not a syntactic allow-list. The signed
receipt has a reviewer-resolvable signing-key identity, and its signature must
validate before an independent reviewer reads the evidence. Even if a
future source change caused arbitrary code to run during its own build or test,
it has no network, credential, repository-write, host-control, publication, or
release-record capability. That is the material separation from the rejected
CI/source-route design.

## 4. Threat model

### In scope

- A source-controlled workflow or helper gaining a credential, upload, publish,
  arbitrary setup, or job-permission path.
- A test-hooks build rebinding a shared developer virtual environment.
- A test run reporting a pass while the canonical binding lacks the complete
  dev-only hook surface.
- A SIGBUS or any other nonzero pytest exit being hidden by later shell output.
- A receipt that cannot identify the exact source and appliance used.

### Out of scope, but explicitly checked by review

The reviewed source can always change what its tests assert; no sandbox can
make a dishonest test meaningful. The existing TDD and independent adversarial
review gates remain responsible for confirming the child-process oracle is the
same SQL, parameters, and result semantics as the prior in-process oracle.
The appliance protects the host and release authority; review protects test
meaning.

## 5. Required acceptance evidence

An independently reviewed B5 receipt is acceptable only when it contains all
of the following, with real exit statuses rather than inferred pass counts:

1. The detached candidate SHA, clean-tree proof, and the reviewed base ancestry.
2. The pre-approved, reviewer-resolvable policy identifier and digest. Its
   content must fix the supervisor version, image digest, commands, targets,
   feature list, confinement, receipt schema, signing-key identity and
   verification material, and probe commands.
3. A cryptographically authenticated supervisor receipt whose valid signature
   binds the candidate SHA, policy identifier/digest, image digest, fixed
   command set, and all 63 immediate exit events. The reviewer must resolve the
   signing-key identity and verify the signature independently.
4. The appliance image digest and supervisor version/configuration digest.
5. The fixed feature list and a successful three-symbol hook probe from the
   virtual environment that pytest uses.
6. Hashes of the B5 test file and relevant Python test-hook gate files before
   execution, so the reviewer can match them to the reviewed source diff.
7. Sixty ordered isolated-run records and three ordered whole-file records,
   each giving target, ordinal, and immediate pytest `rc=0`.
8. Proof that no invocation was retried, skipped, deselected, or continued after
   a nonzero exit; any such event is a failed accrual, not a partial pass.
9. Attached, reproducible raw probe output for the following, each hashed into
   the signed receipt: effective uid and uid map; user-namespace identity;
   network-namespace identity plus route table; complete mount table; effective
   environment against the policy allow-list; and absence of credential/secret
   environment variables, agent sockets, credential files, and secret mounts.
   The policy must make the expected output and failure conditions explicit.
10. The appliance capability attestation from section 3 and destruction of its
    scratch directory after receipt emission.
11. An independent review of both the B5 implementation patch and this receipt.

No CI badge, workflow log, source-level workflow test, or local shared-venv
run may substitute for this evidence.

## 6. Rejected-design exclusion

The next implementer must not touch any of the following as part of B5:

- `.github/workflows/b5-oos18-accrual.yml` or any new B5 workflow;
- `scripts/b5-oos18-accrual.sh` or any source-controlled B5 accrual launcher;
- `scripts/tests/test_b5_oos18_ci_route.sh` or any successor workflow guard;
- `.github/workflows/ci.yml`, `.github/workflows/release.yml`, CI permissions,
  workflow dispatch, artifact handling, registry setup, or release automation.

The rejected candidates and their containment model remain forbidden even if a
new source-level parser or a larger negative-fixture suite could address a
known bypass. Such a repair would violate `seq-235`'s materially-different
requirement and the fix-round circuit breaker.

## 7. Implementation boundary and proposed narrow next scope

The proposed next implementer receives one isolated worktree and may change
only the OOS-18 Python test/oracle implementation and its directly associated
human-authored regression tests. The patch must be RED first, must preserve the
raw `mode=ro` SQL oracle's semantics, and must use `subprocess` rather than
`multiprocessing` so a live engine process is never forked.

It may not build or install a binding, run the 60/3 accrual, configure the
appliance, create a workflow, modify a release record, integrate, push,
dispatch CI, tag, or publish. Its receipt must stop after local static/test
evidence and independent review.

After that patch passes independent review, a separate operator-provisioning
task may instantiate this design's appliance and another independent reviewer
must review the resulting receipt. Only the Steward may then decide whether
the E1 receipt is complete; E2 remains hard-stopped until that decision.

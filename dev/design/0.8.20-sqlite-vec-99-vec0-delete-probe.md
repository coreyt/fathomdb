# sqlite-vec `#99` — `vec0` `DELETE` with >12-byte TEXT metadata: FINDING

**Slice 22 (R-20-VC), leg 4.** Commissioned as a characterization probe ("does
`#99` bite us?"), with a written finding required either way.

- **Verdict:** it **REPRODUCES**, and it is **live in FathomDB** — the 0.8.20
  Slice-15e `filterable` attribute columns reach it. Both `erase_source` and
  `purge` returned `Err(EngineError::Storage)` and left the `vec0` row at rest.
- **Baseline:** `fe85337fb7327b5c09349964ba2d1db6b64c5124` (branch `orch-0.8.20-s22`)
- **Probe / regression test:** `src/rust/crates/fathomdb-engine/tests/tc76_vec0_long_metadata_delete.rs`
- **Dependency, exactly:** `sqlite-vec = "=0.1.7"`
  (`src/rust/crates/fathomdb-engine/Cargo.toml:19`,
  `src/rust/crates/fathomdb-schema/Cargo.toml:27`; `Cargo.lock` `version = "0.1.7"`,
  `checksum 76b546e18bc6c1ee5154218bd9a7a8a6807b7cbe7d377923ff76a0b6b399c4d5`)
- **Remediation landed in this slice:** engine-side, `delete_vector_partition_row`
  (`fathomdb-engine/src/lib.rs`). See §6.
- **TC-76 recommendation:** **YES — promote.** See §7.

## 1. The upstream mechanism, read from source

A `vec0` plain-TEXT metadata column stores a fixed **16-byte inline view** per row
(`VEC0_METADATA_TEXT_VIEW_BUFFER_LENGTH`, `sqlite-vec.c:3489`): a 4-byte length
followed by the value's first **12 bytes** (`VEC0_METADATA_TEXT_VIEW_DATA_LENGTH`,
`sqlite-vec.c:3490`). A value **longer than 12 bytes** additionally gets a row in
the `<tbl>_metadatatext<NN>` shadow table (`sqlite-vec.c:8273-8299`).

`vec0Update_Delete_ClearMetadata` (`sqlite-vec.c:8888`) is the delete-side twin.
For `VEC0_METADATA_COLUMN_KIND_TEXT` with `n > 12` it deletes the shadow row
(`sqlite-vec.c:8934-8952`):

```c
rc = sqlite3_step(stmt);
if(rc != SQLITE_DONE) { rc = SQLITE_ERROR; goto done; }
sqlite3_finalize(stmt);
```

On **success** `sqlite3_step` returns `SQLITE_DONE` (101), the guard does not
fire, and `rc` is **never reset to `SQLITE_OK`**. The function's epilogue
(`sqlite-vec.c:8956-8962`) returns `rc` verbatim, so `vec0Update_Delete`
(`sqlite-vec.c:9027-9030`) sees `101 != SQLITE_OK` and **aborts the entire
`DELETE`**.

The INSERT/UPDATE twin of the same code (`sqlite-vec.c:8258-8320`) has the
identical `rc = SQLITE_DONE` leak, but is rescued by an unconditional
`rc = sqlite3_blob_close(blobValue);` after the switch (`sqlite-vec.c:8327`).
**That asymmetry is why only `DELETE` carries the defect — and it is what makes
the workaround in §6 sound rather than the same bug by another name.**

## 2. What was exercised, and what was measured

All measurements are from real engines / real SQLite in
`tests/tc76_vec0_long_metadata_delete.rs`; no mocking.

### 2.1 Bare `vec0` table — the boundary

`CREATE VIRTUAL TABLE t USING vec0(embedding float[4], m TEXT)`, one row inserted
per value length, then `DELETE FROM t WHERE rowid = ?`:

| value bytes | `INSERT` | `DELETE` | row left behind |
| --- | --- | --- | --- |
| 1 | Ok | `Ok(1)` | 0 |
| 11 | Ok | `Ok(1)` | 0 |
| **12** | Ok | `Ok(1)` | 0 |
| **13** | Ok | `Err(SqliteFailure(code: Unknown, extended_code: 101), "no more rows available")` | **1** |
| 64 | Ok | same `Err` | **1** |
| 1024 | Ok | same `Err` | **1** |

The boundary is exactly `> VEC0_METADATA_TEXT_VIEW_DATA_LENGTH` (12 bytes). The
surfaced error is `SQLITE_DONE` (101) leaking through rusqlite as an
`extended_code`. `INSERT` is unaffected at every length.

### 2.2 Real engine — `erase_source`, boundary in RAW caller bytes

One `filterable` projection (`priority`), one `doc` node whose body carries that
attribute, drained to `vector_default`, then `erase_source`:

| raw attribute value bytes | stored bytes in `vec0` | `erase_source` | `vector_default` rows left |
| --- | --- | --- | --- |
| 10 | 11 | `Ok` | 0 |
| **11** | **12** | `Ok` | 0 |
| **12** | **13** | **`Err(Storage)`** | **1** |
| 13 | 14 | `Err(Storage)` | 1 |

The raw→stored shift of **+1** is Slice 15e's present-marker encoding: a present
value is stored as `\x01 || V` (disjoint from the `''`-absent sentinel). So the
**caller-visible** threshold is a raw attribute value of **12 or more UTF-8
bytes**.

### 2.3 Real engine — `purge`

Same shape, value 1024 bytes, `transition(Deleted)` then `purge`: `Err(Storage)`,
`vector_default` row left behind. Identical mechanism — `purge_inner` and
`excise_source_inner` both funnel through `erase_row_projections`, which renders
`DELETE FROM vector_default WHERE rowid = ?1`.

Note the erasure verb reachable from the governed SDK is **`erase_source`**;
`excise_source` is the `operator`-feature-gated operator spelling and shares one
engine path with it (`Engine::erase_source_shared`). The probe drives
`erase_source`, so it covers both.

### 2.4 Severity: loud, not silent

The failure is a **returned typed error with the transaction rolled back**, not a
silent partial erasure. So it is an **erasure-availability / liveness** defect,
not a data-at-rest leak of the `search_index_v2` class: a caller who asks to
erase a record with a long filterable attribute value **cannot**, and gets
`StorageError` with no actionable message. For a GDPR-erasure verb that is still
serious, and it is unconditional — retrying never succeeds.

## 3. What is UNREACHABLE, and why

### 3.1 `kind` — unreachable

`kind TEXT` is a plain-TEXT `vec0` metadata column carrying the raw caller kind,
and `PreparedWrite::Node` accepts **any** non-empty kind. But **every** door into
`vector_default` is gated on `kind_is_vector_committable` (`lib.rs:15530`), which
delegates to `resolve_source_type` (`lib.rs:15484`) whose entire accepted key set
is `{email, article, paper, meeting, note, todo, doc, edge_fact}` — **max 9
bytes**. The gates:

- `Engine::vector_kind_needs_enrolment` (`lib.rs:4920`) — the write-path late
  enrolment;
- `enqueue_declared_vector_backfill` (`lib.rs:17538`) — the declare-time backfill;
- and finally `commit_projection_outcomes`, which resolves `kind -> source_type`
  through `resolve_source_type` and returns `Err` before recording a terminal.

Measured (test 5): a node of kind `quarterly_report_supplement` (27 bytes) written
alongside a `doc` node produces exactly one `vec0` row, whose `kind` is `doc`;
`SELECT COUNT(*) FROM vector_default WHERE length(kind) > 12` is `0`.

**No `#[doc(hidden)]` test hook was added to force an unreachable shape into the
shipped test.** The direct evidence for the mechanism is the bare-`vec0` probe in
§2.1, which exercises the same code path without pretending the engine can reach
it.

### 3.2 `source_type` — unreachable, and a different mechanism anyway

`source_type` is the `vec0` **partition key** (`vector_partition_create_sql`,
`lib.rs:14617`), stored via the partition machinery, not the TEXT metadata
inline-view machinery — so `#99` does not apply to it at all. Its domain is
`resolve_source_type`'s output, max 9 bytes (`edge_fact`).

### 3.3 `status` — unreachable

`status TEXT` ships the `''` empty-string sentinel only (`vec0` TEXT metadata is
not NULL-able; see the comment at `lib.rs:9622`). Zero bytes, no exposure.

### 3.4 The attribute COLUMN-NAME axis is a red herring — state this plainly

`attr_vec0_column` (`lib.rs:14653`) renders `"attr_" + lowercase hex of the UTF-8
name`, so **any attribute name of ≥ 4 characters already produces a column
identifier longer than 12 characters** — e.g. `priority` → `attr_7072696f72697479`
(20 chars). That shape is exercised by the shipped Slice-15e corpus today and has
never failed. Measured (test 4): a 20-char column identifier with a 5-byte stored
value deletes cleanly at the pre-fix baseline.

**`#99` is about the stored VALUE's byte length, not the column identifier's.**

### 3.5 The one genuinely reachable exposure

`attr_*` **values**: caller-supplied JSON scalars, unbounded, marker-encoded to
`\x01 || V`. This is the whole of FathomDB's exposure to `#99`.

## 4. Blast radius before the fix

Six by-rowid `DELETE FROM vector_default` sites existed, all identically exposed:

| site | path |
| --- | --- |
| `prune_edge_projection_shadows` | edge re-projection |
| `run_pin_and_requantize_pass` | EU-5b mean-vec pin DELETE+INSERT |
| open-path orphan sweep | `Engine::open` integrity reconciliation |
| G0 `logical_id` edge supersession | write path |
| G11 `(from,to,kind)` edge supersession | write path |
| `erase_row_projections` | `purge` + `erase_source` (the registry primitive) |

`truncate_row_projections_in` renders an **unqualified** `DELETE FROM
vector_default`, which still dispatches `vec0`'s per-row delete and therefore
fails on the first over-length row — so rebuild was exposed too.

## 6. The remediation that landed (engine-side, not a dependency change)

`delete_vector_partition_row` is now the single by-rowid `vec0` delete primitive;
all six sites route through it, and `truncate_row_projections_in` gets the
table-wide equivalent. It blanks the `attr_<hex>` columns **first**, then deletes:

```sql
UPDATE vector_default SET attr_<hex>='' [, ...] WHERE rowid = ?1;
DELETE FROM vector_default WHERE rowid = ?1;
```

The `UPDATE` takes `vec0`'s `n <= 12 && prev_n > 12` branch
(`sqlite-vec.c:8300-8319`), which **deletes the `_metadatatext<NN>` shadow row
AND returns `SQLITE_OK`** — the delete-side branch that `#99` breaks is then never
reached, because the value no longer spills the inline view.

Measured properties of the neutralizing `UPDATE` (bare-`vec0` probe):

- `embedding` blob bytes are **byte-identical** across it;
- other metadata columns are preserved verbatim;
- `SELECT COUNT(*)` on the `_metadatatext<NN>` shadow is **0** afterwards.

So it is **erasure-complete**, not error-suppressing: the long value is gone from
the shadow table as well as from the row. Test 3 asserts this directly against
every `vector_default_metadatatext%` shadow table after a `purge`.

It is a **no-op when no `filterable` projection is declared** — i.e. for every
corpus that predates Slice 15e, the shipped delete paths issue exactly the
statements they always did.

`SCHEMA_VERSION` is untouched (24). No migration step. No governed surface added.

**Tripwire.** `bare_vec0_delete_pins_the_upstream_length_boundary` asserts the
upstream defect is **still present**. When `sqlite-vec` is bumped past a release
that fixes `#99`, that test goes red **on purpose**, and that is the signal to
delete the neutralize step. This is deliberate: the workaround must not outlive
its cause silently.

## 7. Recommendation for TC-76 — **PROMOTE, yes**

**`sqlite-vec` must come OUT of the Slice 31 dependency-hygiene sweep and be
handled as a correctness item for 0.8.20.**

Why:

1. **It is a defect in a GDPR-erasure verb, not hygiene.** `erase_source` and
   `purge` are the two erasure verbs; both were unconditionally broken for any
   record carrying a `filterable` attribute value of ≥ 12 bytes. "Dependency
   hygiene, sequenced late, no requirement id" is the wrong bucket for that.
2. **It is scheduled to ship in 0.8.20, not before.** `attr_<hex>` columns only
   exist once a `filterable` projection is declared, which is 0.8.20 Slice 15e —
   **unreleased**. So no shipped FathomDB release is affected, and there is
   nothing to hot-fix. But 0.8.20 must not ship `filterable` on top of a
   dependency whose delete path is known-broken for exactly the values that
   feature makes reachable.
3. **The engine-side fix is a workaround, and it is load-bearing.** §6 is correct
   and tested, but it is a papering-over of an upstream `rc` leak, it costs a
   `sqlite_master` read plus a `vec0` `UPDATE` on every vector-row delete once any
   `filterable` projection exists, and it will drift. The durable fix is upstream:
   a one-line `rc = SQLITE_OK;` (or `rc = sqlite3_blob_close(...)` mirroring the
   insert path) in `vec0Update_Delete_ClearMetadata`.
4. **Slice 31's remit is version bumps, and there may be no version to bump to.**
   `0.1.7` is the pin. Whether a fixed `sqlite-vec` release exists was **NOT**
   determined here (no network access in this worktree; not in scope). TC-76 must
   answer that first, because the answer selects the remedy: *bump* if a fixed
   release exists; otherwise *vendor a patched `sqlite-vec.c`*, *upstream a PR*,
   or *keep the §6 workaround and pin the tripwire* — three materially different
   decisions, none of them "sweep".

**Concretely, TC-76 should be re-opened to answer, in order:** (a) does a
`sqlite-vec` release ≥ 0.1.8 exist and does it fix `#99`? (b) if not, is upstream
patching / vendoring acceptable for 0.8.20, or does the §6 workaround stand as
the 0.8.20 answer with a tracked follow-up? A **decision is required before
0.8.20 signs the `filterable` surface**; it is not a Slice-31 sweep item.

## 8. Open follow-ups (flagged, not done here)

- **Cost.** `delete_vector_partition_row` calls `actual_vector_attr_columns`
  (a `sqlite_master` read) per deleted row. Negligible when no `filterable`
  projection exists (single query, empty result, no `UPDATE`), but it is on the
  open-path orphan sweep and the rebuild loop. Not benchmarked here; `perf_gates`
  is unchanged and green.
- **`erase_source` error message.** The caller of a failed erasure sees a bare
  `StorageError` with no message. That is the same message-less-error debt raised
  by decision #18 for `WriteValidation`.

# TC-68 — caching the vector-equivalence probe on an embedder-identity fingerprint

**Slice 22 (R-20-VC), leg 2.** Per `dev/plans/plan-0.8.20.md` §3 row `R-20-VC`:
*"cache the 0.8.18 equivalence probe against an **embedder-identity fingerprint**
so `Engine::open` cost is constant again, preserving the guarantee rather than
weakening it."*

- **Baseline:** `94bb33ef24dade5e0972e8aa0442a711995cd9ed`
- **Harness:** `src/rust/crates/fathomdb-engine/tests/tc68_probe_fingerprint_cache.rs`
- **The thing being cached:** `dev/design/0.8.18-slice-5-vector-equivalence-probe.md`
  and `dev/adr/ADR-0.8.18-vector-equivalence-self-check.md` (ACCEPTED, HITL-SIGNED)
- **Ledger:** TC-68

> **Read §6 before signing anything off.** This change **narrows** an HITL-signed
> guarantee. That narrowing is the ruled trade, not an accident, and §6 states
> exactly what stops being caught. **§8 is the threat model** — what the probe is
> and, more importantly, what it is not.

---

## 0. Headline, and the correction to the plan's DoD sentence

The plan's acceptance signal reads *"open cost independent of enrolled-kind count,
with the probe still running on an identity change."*

**The first half was already true at `94bb33ef`, vacuously.** The probe gates on

```sql
SELECT EXISTS(SELECT 1 FROM _fathomdb_vector_kinds)
```

(`lib.rs`, `run_vector_equivalence_probe`) — an `EXISTS`, not a `COUNT` — and the
probe body never iterates enrolled kinds. A test that opens with 1 versus N
enrolled kinds and compares embed counts passes with **zero code change**.

The real cost, and the real target, is a **flat 45 embeds on every open, forever**,
once any vector kind is enrolled.

---

## 1. Measured baseline

Method: a counting `Embedder` whose `embed` increments an `AtomicU64`, snapshotted
across `Engine::open` (before/after, engine closed between opens, no rows written
so no projection work can pollute the count). Reproduced by
`measured_zero_enrolled_kinds_costs_zero_probe_embeds` and
`measured_population_open_cost_is_flat_in_the_enrolled_kind_count`.

| workspace state             | open 1 | open 2 | open 3 |
| --------------------------- | -----: | -----: | -----: |
| zero enrolled vector kinds  |      0 |      0 |      — |
| ONE enrolled kind           | **90** | **45** | **45** |
| SIX enrolled kinds          | **90** | **45** | **45** |

### 1.1 The ledger says 90; the fixture says 45 — both are right

`VECTOR_EQUIVALENCE_PROBE_FIXTURE` holds **45** probes, and:

- the **one-time population open** costs **90** — `probe_populate_baseline`
  embeds 45 to persist the un-centered f32 references, and
  `probe_populate_or_check` then immediately calls `probe_check_against_baseline`,
  which re-embeds all 45 again. That second pass is the 0.8.18 **fix-2**
  "confirm the just-written baseline before enabling dense" guard;
- **every open thereafter** costs **45** — the check path alone.

So "90 synchronous embeds" describes the population open and "45" describes the
steady state. Neither figure was wrong; they were being quoted about different
opens.

### 1.2 The population open is deliberately left at 90

TC-68 does not shrink it. The second 45 is tautological *for a deterministic
embedder* — but it is the 0.8.18 fix-2 guard that a just-written baseline
round-trips through the **live** embedder, and it happens once per workspace.
Removing it would trade a signed guarantee for a one-off saving. Out of scope, and
the wrong direction.

## 2. The fingerprint

`probe_verification_fingerprint` is a SHA-256 over length-prefixed fields (the
`u64` length prefix makes the concatenation unambiguous, so no two distinct input
tuples can collide by sliding a delimiter).

| input | why it is in |
| --- | --- |
| recipe tag `"fathomdb-veq-verdict-v1"` | bumping it invalidates every cached verdict in the field at once |
| `identity.name`, `identity.revision`, `identity.dimension` | the nominal embedder — **defence in depth only**, see §2.1 |
| whether mean-centering applies, plus the live pinned `mean_vec` bytes | **load-bearing**, see §2.2 |
| `VECTOR_EQUIVALENCE_PROBE_FIXTURE` | a verdict computed over a different probe set means nothing, see §2.3 |
| `VECTOR_EQUIVALENCE_P1_FLIP_FLOOR`, `VECTOR_EQUIVALENCE_L2_EPSILON` | a verdict that passed under a loose ε must not be inherited by a build that tightened it |
| the stored baseline rows, **reference blobs included** | see §2.4 |

### 2.1 Identity is unreachable, and that is fine

`EmbedderIdentity` is only `{ name, revision, dimension }` — no build id, no
backend descriptor. It is in the fingerprint for completeness, but it can never be
observed to change *here*: `check_embedder_profile` runs earlier in the open path
and **refuses the open outright** with `EmbedderIdentityMismatch` /
`EmbedderDimensionMismatch` on any drift of the triple. So the plan's "with the
probe still running on an identity change" is satisfied a fortiori — an identity
change never gets as far as a cached verdict.

### 2.2 `mean_vec` is not optional

P1 compares `vec_quantize_binary(sign(x − mean_vec))` against the stored
un-centered references. **Rewriting the pinned mean changes the verdict for the
same embedder and the same baseline.** `mean_vec` lives on
`_fathomdb_embedder_profiles` and is rewritten by open-time mean-recovery /
requantize and by the operator `recompute_mean` verb.

A cache keyed on the identity **triple alone** would therefore be stale by
construction, and would keep vouching for a P1 answer computed against a mean that
no longer exists. It is in the fingerprint, and
`a_rewritten_pinned_mean_reruns_the_full_probe` pins it end to end.

### 2.3 The fixture digest, and why the drift test does not make it redundant

`tests/vector_equivalence_probe_fixture_drift.rs` pins the engine's copy of the
fixture equal to the embedder crate's copy. That guards **copy** drift between two
committed files — it does **not** pin the fixture's content across releases, so a
release that legitimately edits both copies would leave cached verdicts computed
over the old probe set.

Separately, the fix-2 completeness validation compares each stored `probe_text`
against the live fixture on **every** open and fails **closed** on a mismatch — so
a fixture edit would in fact be caught before the cache is consulted (by degrading
every existing workspace, which is pre-existing 0.8.18 behaviour, not something
TC-68 introduces).

**Decision: keep the fixture digest anyway.** It costs one hash of a ~3 KB
compiled-in constant, it makes the fingerprint a self-contained statement of what
the verdict depended on, and it does not rely on a *second* mechanism happening to
fail closed first.

### 2.4 The stored baseline blobs — closing a regression before it opens

The fix-2 completeness validation pins each stored row's **shape**: row count,
contiguous 0-based ordinals, `probe_text` equal to the fixture, `reference_vec`
length `4 * dim`, and the stored identity triple. It does **not** pin the blob's
**content** — that was caught implicitly, by the re-embed comparison diverging.

Cache the re-embed away and that closure would silently re-open: an external edit
that flipped the bytes of a reference vector (preserving its length) would be
waved through. Hashing the 45 blobs — ~69 KB of SHA-256 against 45 model
invocations — keeps it intact. `a_tampered_reference_baseline_reruns_the_probe_and_refuses_dense`
pins it.

## 3. Where the gate sits, and what still runs every open

Inside `probe_check_against_baseline_inner`, in order:

1. resolve the live mean (fail-SAFE: unreadable ⇒ refuse dense);
2. read the stored baseline;
3. **fix-2 completeness validation** — count, ordinals, texts, blob lengths,
   identity;
4. ← **the TC-68 cache gate**;
5. the 45 re-embeds + P1 flip count + P2 L2;
6. record the fingerprint.

Steps 1–3 are cheap (SQL reads and string compares, no model invocation) and are
**deliberately left running on every open**. A short, non-contiguous,
re-attributed, text-mismatched or wrong-length baseline still fails closed
immediately. Only step 5 — the 45 model invocations, i.e. essentially all of the
cost — is skipped.

## 4. Storage — no `SCHEMA_VERSION` bump, no migration step, no new table

The marker is one row in **`_fathomdb_open_state(key TEXT PRIMARY KEY, value TEXT
NOT NULL)`**, created by migration **step 1** and already the engine's home for
open-time durable markers: `projection_cursor`,
`search_index_tokenizer_reproject_complete` (0.8.0 G1 fix-1),
`tc33_edge_vector_prune_complete` (0.8.20 TC-33 fix-6) and
`tc33_reserved_write_cursor` (schema step 23) all live there.

Key: `vector_equivalence_verified_fingerprint`. Value: the lowercase hex digest.

This is why TC-68 needs **no** engine-side `CREATE TABLE IF NOT EXISTS` at open
either (the `ensure_vector_partition` precedent was available but is not needed):
the table already exists on every migrated DB. A workspace that predates TC-68
simply has no row, misses, runs the probe once, and records the verdict.

**No schema-drift assertion is affected.** The schema crate's step tests assert
per-step DDL and index shape; none enumerates `_fathomdb_open_state`'s *rows*.
`cargo test -p fathomdb-schema` is green.

## 5. Fail-SAFE (`R-VEQ-4`) in the cache path

`R-VEQ-4` — *any inability to run or verify yields `dense_disabled = true`, never
skip-and-serve* — is HITL-signed and is **not** weakened. It is a guarantee about
**accident** — corruption, truncation, a half-written file, a workspace that
predates the cache — not about a hostile writer; §8 draws that line. In the cache
path:

- **an unreadable cache reads as a MISS, never as a pass.**
  `probe_verification_is_cached` answers `false` for every failure mode: missing
  `_fathomdb_open_state` table, absent row, non-TEXT value, garbled or truncated
  value, a stale fingerprint, any SQL error.

  A `true` means **the fingerprint inputs are unchanged since *some* engine
  recorded a pass** — not "this engine verified this backend". The engine cannot
  tell its own marker from an identical one written by anything else. §8 states
  what that costs: not fixable by construction (§8.2), materially **cheaper** to
  forge than the pre-slice route (§8.4), and bounded by the ruled residual (§8.5).
  (`an_unreadable_cache_entry_falls_back_to_running_the_probe`,
  `a_missing_cache_entry_falls_back_to_running_the_probe`);
- **a failing verdict is never cached**, and every `Err` path of the check
  **clears** any prior marker — so a workspace that could not be verified never
  leaves one behind for a later open to match
  (`a_divergence_on_a_rerun_still_disables_dense`);
- **a divergence found on a re-run still disables dense.** The cache narrows *when*
  the probe runs, never *what it concludes when it does*;
- **a cache WRITE failure is swallowed** rather than turned into a refusal. The arm
  has just been verified, so refusing dense because a marker could not be persisted
  (read-only file, disk full) would be a false refusal — and the consequence of the
  missing marker is that the next open re-runs the probe. More work, never less.

## 6. THE RESIDUAL — what is no longer caught on every open

**Same-identity backend drift is no longer caught per-open.**

The 0.8.18 probe exists to catch a backend that changed *without* changing the
declared identity: candle CPU↔CUDA, a library or driver upgrade, a rebuilt ONNX
runtime. None of those move any fingerprint input — the identity triple is
unchanged (and would refuse the open if it were not), the mean is unchanged, the
fixture is unchanged, the stored baseline is unchanged. So the cache **hits**, the
drifted backend is never asked to embed anything, and the drift is not detected.

It is detected only at the next open whose fingerprint *does* change — a rewritten
`mean_vec`, a fixture edit, a mutated baseline, or a recipe-tag bump. By
definition, a pure backend swap is not one of those.

Before TC-68 this drift was caught at the very next open. **After TC-68 it may
never be caught.** That is a real narrowing of
`dev/adr/ADR-0.8.18-vector-equivalence-self-check.md`, and it is the ruled trade
(`dev/plans/plan-0.8.20.md` §3 `R-20-VC`).

It is asserted as an executable fact by
`residual_same_identity_backend_drift_is_not_caught_on_a_cached_open`, so nobody
can later read "preserving the guarantee" off the plan and assume it was preserved.

**fix-2:** this residual is *also* what bounds the forged-marker finding — the same
drifted backend is served off an honestly recorded marker, with no forgery involved.
See §8.5.

### 6.1 What IS still caught, on every open

- **cross-vendor / identity drift** — refused at open by `check_embedder_profile`,
  which is and remains the PRIMARY gate (`R-VEQ-5`: the probe is additive);
- **a partial, non-contiguous, re-attributed, text-mismatched or wrong-length
  stored baseline** — the fix-2 completeness validation runs before the cache gate;
- **a mutated reference blob** — via the fingerprint (§2.4);
- **a rewritten `mean_vec`** — via the fingerprint (§2.2);
- **an un-runnable embedder** (panics, errors, wrong dimension) on any open that
  actually runs the probe;
- **the first-ever verification** of a workspace — population always runs the full
  check before dense is enabled.

### 6.2 Mitigations considered and rejected

- **Re-run the probe every Nth open, or on a wall-clock TTL.** Rejected: it makes
  open cost non-deterministic and unexplainable ("why was *this* open slow?"),
  restores only a fraction of the coverage, and needs a durable counter/clock that
  is itself a new correctness surface. It converts a clean "cached ⇒ 0" contract
  into a probabilistic one. (fix-2 re-weighed the same mechanism from the *threat*
  side, where it is the one candidate that buys real coverage — see §8.7. It is
  still not taken here, and the trade is written down there for a later slice.)
- **Cache only the P2 (L2) half and keep re-running P1.** Rejected: both halves
  need the same 45 embeds, so this saves nothing.
- **Sample k of the 45 probes per open.** Rejected: the D4 floors are calibrated on
  the full 45-probe set (P1 floor is exact-zero over all of them), so a sampled run
  is not the signed check, and `dense_disabled` would stop meaning what the ADR says
  it means.
- **Widen `EmbedderIdentity` (or the `Embedder` trait) with a runtime
  backend/device descriptor** — e.g. `candle-cuda:driver=12.4` — and fold it into
  the fingerprint. **This is the fix that would genuinely retire the residual**, and
  it is deliberately NOT implemented here: it is public-surface work on a governed
  type, it needs HITL sign-off, and it belongs with the batched governed-surface
  decision the plan places after Slice 22. Recorded for that decision, not taken.

## 7. Consumer-visible effect

No public surface changes — no new type, field, method, or error. Two behavioural
changes a consumer can observe:

1. **`Engine::open` gets cheaper.** A workspace with an enrolled vector kind and a
   live embedder stops paying 45 embeds per open. With the default bge-small
   embedder on CPU that is the dominant open cost.
2. **`OpenReport.dense_disabled` changes meaning slightly.** It used to mean "the
   probe re-verified the dense arm at *this* open". It now means "the dense arm was
   verified at the last open whose fingerprint differed, and nothing in the
   fingerprint has changed since". A caller relying on open-time re-verification to
   detect a backend swap must force a re-run (rewrite the pinned mean, or clear
   `_fathomdb_open_state.vector_equivalence_verified_fingerprint`) — or wait for
   §6.2's descriptor input to be signed.

Neither is reachable from a **default** Python/TypeScript session: without
`use_default_embedder` / `useDefaultEmbedder` there is no live embedder, so the
probe is inert and no SDK-level assertion about it is possible. The X1 SDK suites
(`src/python/tests/test_vector_equivalence_probe.py`,
`src/ts/tests/vector-equivalence-probe.test.ts`) are, by their own docstrings,
**surface-parity only** — they pin the error leaf, the `OpenReport` fields and the
FTS-only path, and defer divergence behaviour to the Rust engine suite. TC-68 adds
no surface for them to pin, so **no SDK test was added**: a mirror would have been
green without exercising anything.

## 8. THREAT MODEL — the probe is a self-check, not an integrity boundary

**Added by fix-1**, closing the codex §9 targeted-round-2 `[P1]`
(`dev/plans/runs/codex/0.8.20/slice-22-review-round2-targeted-20260729T004445Z.log`).
**§8.4 and §8.5 were added by fix-2**, which withdrew fix-1's equivalence
conclusion after the re-review
(`dev/plans/runs/codex/0.8.20/slice-22-fix-1-rereview-20260729T011134Z.log`)
rejected it. Read §8.4 before quoting §8.3 at anyone.

### 8.1 The finding, accepted

> `probe_verification_is_cached` trusts any `_fathomdb_open_state.value` exactly
> equal to the freshly computed SHA-256. That is fail-safe for absent, corrupt,
> truncated, non-TEXT or stale values because they miss and run the probe. It is
> not fail-safe for an attacker-modified row: the fingerprint inputs are
> deterministic, public DB and build inputs, not a secret or an engine-authenticated
> marker, so a writer can forge the current digest and force the early
> `return Ok(())` before the 45-probe verification runs.

**True, and accepted.** `a_marker_matching_the_current_state_serves_a_drifted_backend`
states it as an executable fact: on one workspace, with the marker absent the
drifted backend is caught (45 embeds, `dense_disabled`); with the same digest
written back it is served with 0 embeds.

**§5's original wording was an over-claim and has been corrected.** It read *"the
only `true` is an exact match against a value **this engine wrote after a
verification it performed itself**"*. The engine cannot distinguish its own marker
from an identical one written by anything else. What a `true` actually means is:
**the fingerprint inputs are unchanged since *some* engine recorded a pass.**

### 8.2 Why the remedy is prose, not cryptography

There is nothing to authenticate the marker *with*. Every fingerprint input —
identity triple, pinned `mean_vec`, compiled-in fixture, the two floors, the stored
baseline blobs — is readable from the database file or the shipped binary. A salt
or MAC key would live in the same file or the same binary and be read by the same
actor. An embedded local-first engine has no key custodian, no separate trust
domain and no privileged process. Any construction here would raise the bar for a
*naive* editor only: the same actor reads the salt out of the same file or the same
binary, and still has §8.3's route besides. Security theatre.

### 8.3 The measurement: the pre-slice path is forgeable too

`a_forged_stored_baseline_defeats_the_probe_even_when_it_fully_runs`:

1. seed a verified workspace, then rewrite **every** `_fathomdb_embed_probe.reference_vec`
   to the *drifted* backend's own output. Ordinals, `probe_text`, the identity
   triple and the blob lengths are untouched, so the 0.8.18 fix-2 completeness
   validation — which pins row *shape*, never blob *content* — sees nothing;
2. **delete the cache marker**, so the cache demonstrably plays no part;
3. open with the drifted backend. All **45** embeds run, and the probe **passes**:
   it has verified the drifted backend against a baseline the drifted backend
   itself supplied. Dense stays enabled; `search` does not refuse.

The control leg — identical drifted backend, **un-forged** baseline, marker cleared
— is caught and refuses dense, so the forgery is what does it.

The code exercised in step 3 is the check body **as shipped at the slice baseline
`fe85337f`**: `git diff fe85337f a39b865e -- src/rust/crates/fathomdb-engine/src/lib.rs`
shows the only changes inside `probe_check_against_baseline_inner` are the doc
comment, a type alias, the cache gate and the `record_probe_verification` call. The
comparison logic is byte-identical.

What this establishes, and all it establishes: **the same actor already had a route
that defeats the probe while it runs in full.** It does *not* establish that the two
routes cost the same — see §8.4, which is where fix-1 went wrong.

### 8.4 The cost asymmetry, CONCEDED: the cache is a cheaper bypass

**Added by fix-2.** fix-1 concluded from §8.3 that *"the cache adds no new attack
surface"*. The codex fix-1 re-review accepted the measurement and rejected that
conclusion — *"Same DB-write actor, yes; same difficulty/availability, no.
Re-baselining requires target backend outputs; marker forgery does not."* It is
right, and the sentence is **STRUCK**. What is true instead:

- forging the **marker** needs DB write access plus a digest that is **publicly
  computable** from inputs the actor can already read (identity triple, pinned
  `mean_vec`, the compiled-in fixture, the two floors, the stored baseline rows) —
  and on a workspace that has ever been verified under the current fingerprint the
  digest is simply *sitting in the row*, so nothing need be computed at all;
- defeating the **baseline** needs DB write access **plus the target backend's 45
  exact probe embeddings**, LE-f32 encoded into all 45 rows with the ordinals,
  texts, identity triple and blob lengths preserved. The actor must be able to
  *run* the drifted backend over the fixture, not merely to read the file.

**That is a materially higher bar. The cache therefore DOES introduce a cheaper
bypass path for an actor who can write the database file.** §8.3 shows the two
routes are open to the same actor; it never showed they cost the same, and fix-1
read it as if it had.

### 8.5 What the cheaper path is actually worth — the bound

**Added by fix-2.** §8.4 is about cost. This is about **outcome**, and it bounds the
finding rather than dismissing it.

The attack's payoff is *a drifted backend served without verification*. The ruled
residual (§6) already hands an attacker exactly that payoff **with no forgery at
all**: a same-identity backend drift moves **no** fingerprint input — the identity
triple is unchanged by the definition of "same-identity drift" (and any change to it
refuses the open outright, §2.1); the pinned `mean_vec`, the compiled-in fixture,
the two floors and the stored baseline blobs are all untouched by a mere backend
swap. So a marker **legitimately recorded by an honest earlier open** still matches,
the probe is still skipped, and the drifted backend is still served.

That is asserted end to end by
`residual_same_identity_backend_drift_is_not_caught_on_a_cached_open`, which as of
fix-2 also asserts explicitly that the marker in play is the one **the engine itself
wrote** at the honest population open, and that it is byte-unchanged across the
drifted open. There is no forgery anywhere in that test.

So the **incremental** capability the forgery grants is confined to opens where no
valid marker exists for the *current* fingerprint:

1. a workspace whose probe has **never** passed under the current fingerprint,
   including a pre-TC-68 database. (In one sub-case of this the forgery is pointless
   anyway: where the probe table is *empty*, `probe_populate_or_check` baselines it
   against whatever backend is live and the confirm pass then trivially succeeds.
   Pre-existing 0.8.18 behaviour, unchanged here, and nothing to do with the cache.)
2. the open right after a legitimate fingerprint change — a recomputed `mean_vec`, a
   fixture edit, a recipe-tag bump — which an honest open re-verifies, and at which
   the drift *would* be caught;
3. an open after a failing verdict, which clears the marker (§5).

All three are real. **Case 2 is the one that matters**, because it is the only
*recurring* detection opportunity §6 left standing. Case 3 suppresses a repeat of a
signal the caller has already been given — that failing open is what cleared the
marker. Case 1 requires the actor to arrive before the workspace's first verified
open.

**Stated at its honest severity, both halves load-bearing:** in the steady state a
forged marker is a cheaper route to an outcome §6 *already* concedes and already
serves without any forgery; at a fingerprint-changing open it is a genuine loss —
it converts *"caught at the next fingerprint-changing open"* into *"never caught"*,
removing the last recurring detection opportunity §6 left standing. That is the
finding's real weight. It is not "no new attack surface"; nor is it a new class of
exposure, since the actor it requires already owns the file (§8.6).

### 8.6 The boundary, stated plainly

- **In scope — what the probe catches.** *Accidental* backend drift: the same
  declared embedder moved CPU↔CUDA, rebuilt against a new library or driver, a
  re-exported ONNX graph; plus a corrupt, partial or mangled stored baseline. That
  is the ADR's purpose (`dev/adr/ADR-0.8.18-vector-equivalence-self-check.md`).
- **In scope — the accident guarantee.** `R-VEQ-4` holds unchanged: every
  unreadable, absent, garbled or stale cache state runs the probe rather than
  trusting it (§5).
- **OUT of scope — an actor with write access to the database file.** They can
  forge the marker (§8.1, and it is the **cheaper** of the two routes — §8.4), forge
  the baseline (§8.3), or rewrite the corpus and the vectors outright — nothing in
  FathomDB's at-rest state is authenticated: `canonical_nodes`, the `vector_default`
  vec0 rows, `_fathomdb_embedder_profiles.mean_vec` and `_fathomdb_embed_probe` are
  all ordinary tables in the same unprotected file. FathomDB's trust boundary is the
  file: a caller who lets an untrusted party write the database has already lost the
  dense arm, the lexical arm and the corpus. The equivalence probe is a
  **correctness self-check against backend drift, not tamper evidence**, and must
  not be cited as one — in particular `dense_disabled` is not a tamper signal.
- **What forging buys, bounded.** Two bounds, and both matter. *In time:* a digest
  is valid only for the state it was computed over —
  `a_replayed_verdict_marker_is_defeated_by_a_mutated_baseline` and
  `a_replayed_verdict_marker_is_defeated_by_a_rewritten_pinned_mean` show a known
  digest expires at the next change to any fingerprint input, so a forgery must be
  re-applied after every legitimate change. *In capability:* §8.5 — the outcome it
  buys is already granted, forgery-free, by the ruled residual on every open whose
  fingerprint has not moved.
- **What the cache genuinely narrows** is §6 and only §6: same-identity backend
  drift is no longer caught per-open. That is the ruled trade, and it is about
  accident, not attack.

### 8.7 Hardening considered — one deferred, the rest rejected

- **Bounded-staleness re-probe — CONSIDERED, NOT TAKEN; deferred with the trade
  named (fix-2).** Re-run the probe unconditionally after N opens, or once the
  recorded verdict is older than some wall-clock age, regardless of a cache hit.
  Unlike everything below it, this one would actually bite: it bounds the value of a
  forged marker **and** of the ruled residual (§6) to at most N opens (or that age),
  because the drifted backend is eventually asked to embed. It is **not** taken in
  this slice, for two reasons recorded here so a later slice can weigh them with
  numbers in front of it:
  1. it **partially undoes the property TC-68 was ruled to deliver** — a constant,
     predictable `Engine::open` cost. One open in N pays 45 embeds again, and it is
     not predictable *which* one. That is §6.2's objection, unchanged by the threat
     framing;
  2. it needs durable state (a counter or a timestamp) plus a tuning constant — new
     surface and a new correctness question (clock skew, a reset counter, what N
     even means for a process that opens once and runs for a week) — in a slice
     explicitly scoped not to grow surface.

  It should be decided against §6.2's backend-descriptor fingerprint input, which
  **retires** the residual rather than merely bounding it, and which needs the same
  HITL governed-surface decision. Not bolted on here.
- **Salt / MAC / keyed digest.** Rejected: §8.2 — no secret exists to key it with.
- **Obfuscate the marker (encode it, hide the key name, spread it over rows).**
  Rejected: costs real complexity, stops nobody who can read the schema, and leaves
  §8.3's route wide open besides. Theatre.
- **A `DELETE`-the-marker trigger on `_fathomdb_embed_probe`,** so an external
  `UPDATE` of the baseline drops the cached verdict. Rejected twice over: it is DDL,
  so it needs a migration step and a `SCHEMA_VERSION` bump (explicitly out of scope
  for this slice), and it buys nothing — §8.3's forgery *wants* the probe to run,
  because the forged baseline passes it.
- **Hash the marker together with something an external writer would plausibly
  forget to update.** Rejected: there is no such input that is not already a
  fingerprint input, and inventing one (a write counter, a mtime) would make open
  cost non-deterministic — the same objection that killed the TTL in §6.2 — while
  still yielding to anyone who reads this file.

Nothing was implemented. Not because the finding is empty — §8.4 concedes it is not
— but because the only candidate that would genuinely bound it (bounded staleness)
trades away the property this slice was ruled to deliver, and the mechanism that
would genuinely *retire* it (§6.2's backend descriptor) is governed public surface
awaiting an HITL decision. The correct disposition of a `[P1]` whose honest remedy
is out of the slice's scope is to **state the exposure precisely, name the remedy,
and defer it visibly** — which §8.4, §8.5 and §8.7 now do — rather than to ship a
mechanism that merely looks like a fix.

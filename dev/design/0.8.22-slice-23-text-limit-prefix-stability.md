# Slice 23 — Direct FTS limit-prefix stability design

> **Execution status:** landed on `origin/main` through PR #209 at
> `f1ccf2694087e1da4cee2204fe7b80389420a4b0` after CI run #31265399431 passed.
> Slice 20 publication remains held. Slice 23 neither tags nor publishes.

## Problem and evidence

For a fixed corpus and query, `Engine::search_text_only_with_limit(q, 10)`
can return a different top ten from the first ten results of
`Engine::search_text_only_with_limit(q, 50)`. The EARP calibration used a
clean descendant of `e95afd29` with no intervening
`fathomdb-engine/src/lib.rs` change. It found 11 differing queries among
4,472 paired scored queries; the paired strict-evidence-recall@10 delta was
−0.00246 with a 1,000-resample CI of [−0.00380, −0.00112]. The structural
finding, rather than the corpus-specific quality delta, is the release issue.

The current reader limits node-body FTS to the caller's final result limit
when the query vector is absent. Edge-body FTS remains unbounded. Both lists
are concatenated into the text arm, then `fuse_rrf` body-deduplicates them
before final truncation. A node outside the smaller node window can therefore
gain a second contribution from a matching edge body only in the larger call
and enter its top K. The existing comment that this SQL limit is "truthful"
for public ordering is false for the direct text-only result.

## Chosen scope and contract

This slice fixes the explicit direct FTS API only:

- `Engine::search_text_only_with_limit` and
  `Engine::search_text_only_view_with_limit`;
- their existing Python and TypeScript wrappers; and
- corrected contract documentation in the Rust, Python, and TypeScript
  interfaces and public API references.

For the same immutable engine snapshot, query, and effective validity time,
and for `1 <= small <= large <= 100`, the full direct text-only result sequence
at `small` must equal the prefix of length `small.results.len()` of the
sequence at `large`. This is a result-content and order guarantee, not merely
a cardinality guarantee. The `ReadView` form must use the same explicit fixed
`valid_as_of`; `None` resolves to the current time for each request and makes
no across-call prefix promise when it resolves differently. Separate calls
during concurrent writes need not share a snapshot and are outside this
statement.

The contract does not apply to hybrid `search*`, reranked/explained search, or
`search_expand`. Those flows intentionally carry caller-dependent vector
candidate fanout and may add graph/rerank stages. It also does not change
`search_projected_text`, whose single ordered property-FTS query already
bounds after its own filtering path. A 0.8.23 architecture/documentation
follow-up will decide and document the broader hybrid candidate-fanout versus
caller-limit trade-off; Slice 23 must not redesign it.

## Intended implementation

The reader request needs an explicit private discriminator for the direct
text-only public path. It must not infer that path from `query_vector == None`,
because ordinary hybrid search can also lack a usable query vector and is out
of scope.

`search_text_only_view_with_limit` will pass a fixed node-FTS candidate bound
of `MAX_SEARCH_RESULT_LIMIT` (100), independent of the caller's final limit.
The reader will apply that bound only when this discriminator is present. It
will then retain the existing node-ordering, existing unbounded edge candidate
collection, existing text-arm concatenation/RRF body deduplication, and final
`results.truncate(final_limit)`. Since both node and edge input sequences are
then invariant for every public direct-text limit, the fused order is invariant
as well.

Ordinary hybrid/no-vector-fallback requests keep their existing request shape
and candidate behavior. The change adds no SDK spelling, configuration knob,
schema migration, graph behavior, reranker behavior, or fixed edge-FTS cap.
The proposed code shape is deliberately not treated as proved until the RED
fixture fails and the GREEN implementation makes it pass.

## RED-to-GREEN proof

The engine RED fixture must use a real database and include at least 50
matching nodes plus an edge whose body duplicates a node outside the first ten
node matches. It must fail on the baseline by comparing all IDs, order, and
scores of direct-text `limit=10` with the first ten direct-text `limit=50`
results. A second fixture must cover the `ReadView` form with an explicit fixed
`valid_as_of`, never the per-request `None`/"now" default. Simple single-list
fixtures are insufficient because they cannot exercise the node/edge
deduplication mechanism.

Python and TypeScript RED tests must call their existing direct text-only
wrappers against real databases and assert the same prefix equality. They add
no API surface; their purpose is to prove that the public wrappers preserve
the corrected engine semantics.

GREEN is limited to threading the private direct-text candidate-bound marker,
making the RED tests pass, correcting the stale implementation commentary, and
updating contract documentation. The public documentation must replace the
currently false node-body-only/no-fusion description: direct text-only search
does not use embedding, vector, CE, or graph stages, but matching node- and
edge-body candidates enter the text arm and duplicate bodies are deterministically
deduplicated and ranked. Refactoring follows only after all RED tests are green.

## Evidence and risks

The bounded candidate pool is at most 100 nodes, matching the already accepted
public hard maximum; it is not an unbounded FTS scan. It can collect up to ten
times as many node candidates as the default result request, so the slice must
record five paired warm samples of the actual public direct-text path on the
frozen corpus before and after the change, including revision, host, SQLite,
schema, query set, and raw samples. This is evidence for review, not a new
host-specific latency claim or a new performance threshold.

The implementation must preserve the existing edge candidate behavior and must
not turn a direct-text stability repair into a general RRF redesign. If the
RED fixture disproves the intended fixed-bound shape, or the measured path
reveals a material concern that the plan cannot resolve, halt for a scoped
design update rather than silently broadening the slice.

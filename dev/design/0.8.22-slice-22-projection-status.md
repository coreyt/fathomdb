# Slice 22 — Projection-status read API design

## Problem

`read.projections` returns the caller-authored declaration decorated with
readiness. `configure_projections` returns a delta that happens to carry
`vector_unsupported_kinds`, but the delta is not a durable status read and
requires a caller to re-apply configuration to refresh it. Consumers therefore
cannot ask one pure question: “what can this current engine session retrieve
densely, and why not?”

## Chosen shape

Introduce a separate result type rather than growing `ProjectionSpec` or
`ProjectionDelta`:

```text
ProjectionStatus {
  runtime_embedder_available: bool,
  runtime_unavailability_reason:
    none | no_runtime | vector_equivalence_disabled,
  projections: [
    { name, dense_readiness: not_declared | unavailable | embedding | ready }
  ],
  vector_unsupported_kinds: [kind]
}
```

`runtime_embedder_available` means that this open engine session has an
attached embedder that the existing identity and vector-equivalence safeguards
have accepted for dense work. When it is false,
`runtime_unavailability_reason` distinguishes `no_runtime` from
`vector_equivalence_disabled`; when it is true, the reason is `none`. This
does not mean a projection is declared, vectors exist, or an individual
attribute is fully indexed. Those facts stay in their own fields.

The entries are sorted by projection name. There is one entry for each declared
projection; one whose declaration has no vector arm reports `not_declared` for
its dense readiness. Every declared vector projection derives the same
corpus-wide state under the current shared dense pipeline. This deliberate
duplication is more honest than implying the engine has per-attribute embedding
progress it does not track.

`vector_unsupported_kinds` reuses the existing derivation only when at least
one declared projection has a vector arm; it is sorted and deduplicated. The
status read returns `[]` when no vector arm is declared, preserving the
declaration-scoped meaning of the current configuration delta. It is not an
error and not proof that every vector projection has completed.

## Non-mutation and failure behavior

The method reads the registry and current derived facts only. It does not write
the registry, enrol kinds, enqueue rows, call `drain`, or awaken the scheduler.
It has the existing pure-read storage/closed-engine error taxonomy. It does not
need a special SQLite read-only file handle; “read-only” describes its behavior.

## Governance and tests

This is a new C5 `read.*` verb, so the signed governed-surface allowlist gains
both binding spellings before it is considered shipped. RED tests prove pure
read behavior, all four readiness states, both unavailability reasons,
declaration-scoped unsupported-kind freshness, stable ordering, and
cross-binding parity using a real database. Tests must not mock the database or
infer status from a configuration echo.

The slice updates Rust/Python/TypeScript interfaces and public exports in the
same change. It does not expose an evaluator-only seam or add a write-side
convenience API.

# TC-67 — the unsupported-vector-kind report

**Slice 22 (R-20-VC), leg 1.** Declaring a `searchable→vector` projection over a
node kind the vector writer can never commit used to be **silent**. It now
**reports**, per the HITL ruling, option **(c)**.

- **Requirement:** `dev/plans/plan-0.8.20.md` §3, row `R-20-VC` — *"**TC-67** —
  declaring a `searchable→vector` projection over a kind the vector writer cannot
  commit must **REPORT**, per HITL option (c); the `resolve_source_type`
  vocabulary is **NOT grown** and the Pack-1 D3 partition-key lock is **not
  touched**."* DoD: *"a typed report, not silence; readiness semantics
  unchanged."*
- **Baseline:** `17951f05` (branch `orch-0.8.20-s22`; slice baseline `fe85337f`)
- **RED:** `34b13c61` · **GREEN:** `423e5f22` · **X1 parity:** `65017319`
- **Tests:** `src/rust/crates/fathomdb-engine/tests/tc67_unsupported_vector_kind_report.rs`
  · `src/python/tests/test_tc67_unsupported_vector_kind_report.py`
  · `src/ts/tests/tc67-unsupported-vector-kind-report.test.ts`
- **Schema:** unchanged. `SCHEMA_VERSION` stays **24**; the report is derived, so
  there is no migration step and nothing is stored.

## 1. The silence, precisely

`resolve_source_type` (`fathomdb-engine/src/lib.rs`) maps a node `kind` onto the
locked Pack-1 `source_type` partition-key vocabulary — `email, article, paper,
meeting, note, todo, doc, edge_fact` — and returns `Err` for anything else.
`PreparedWrite::Node`, by contrast, accepts **any non-empty `kind`**:
`validate_write` constrains the body, the identity and the validity window, never
the kind. So a corpus can perfectly legitimately hold an `invoice` or an `entity`
node.

Slice 20c fix-2 made enrolment respect that boundary, via
`kind_is_vector_committable`, because enrolling an unmappable kind is a permanent
**liveness wedge**: the scheduler picks the row up, `commit_projection_outcomes`
fails before recording a terminal, the scanner re-enqueues it forever, `drain`
burns its whole timeout, and `dense_readiness` sticks on `embedding` — starving
the rows whose kinds *are* commit-able. That fix is correct and this slice does
not touch it.

What it left behind was a hole in the **reporting**, in
`enqueue_declared_vector_backfill`:

```rust
for kind in kinds.iter().filter(|kind| kind_is_vector_committable(kind)) {
    register_vector_kind(tx, kind)?;
}
```

A kind outside the vocabulary is dropped by that filter with **no enrolment, no
error, and nothing recorded**. Meanwhile the registry row IS persisted and the
projection's name IS pushed onto `ProjectionDelta::deferred`. The caller is
therefore told `deferred`, and cannot distinguish:

| | meaning | duration |
| --- | --- | --- |
| **transient** | no embedder attached this session (Q6a graceful-absent), or an embed still in flight | resolves on its own |
| **permanent** | this kind is outside the locked vocabulary; **no** embedder in **any** session will ever produce a vector for it | forever |

Both arrive as the same `deferred` entry. **That indistinguishability is the
defect.** It is not a data-loss bug and not a false-ready; it is a
tell-the-truth bug, and its cost is a consumer who waits for vectors that are
never coming.

The write path had the same silence at `Engine::vector_kind_needs_enrolment`,
which returns `Ok(false)` for a non-committable kind.

## 2. What was NOT done, and why

Three constraints were ruled, not chosen here:

1. **`resolve_source_type`'s vocabulary is NOT grown.** No match arm was added.
   The vocabulary is the vec0 `source_type` **partition key**; growing it changes
   partition semantics for every stored vector.
2. **The Pack-1 D3 partition-key lock is NOT touched**
   (`dev/design/0.7.0-vector-quant-pack1.md`). Same reason, stated as a lock.
3. **Readiness semantics are unchanged.** An un-enrolled kind is **not
   outstanding work** — nothing will ever be embedded for it, so there is nothing
   to wait for. `dense_readiness` therefore still reports `ready` for a corpus
   made entirely of unsupported kinds, and `drain` still returns promptly. The
   report is additive **information**, not a readiness state and not an error.

Point 3 is the DoD clause most at risk. The tempting "fix" — treating an
unsupported kind as unfinished work so the caller notices — would satisfy any
report-only assertion while wedging every consumer whose corpus contains one. It
has its own test (`readiness_semantics_are_unchanged_by_the_report`, plus the
Py/TS arm of the same name), built on the harshest fixture: a corpus of *only*
unsupported kinds with the dense arm declared.

Also NOT done, and explicitly out of scope: plan §11 ruling item **4** (an
`fts`/`vector` sub-object without the `searchable` role is an invalid spec).
See §7.

## 3. The shape

`Engine::configure_projections` returns `ProjectionDelta`, which before this
slice was the *entire* return surface:

```rust
ProjectionDelta { built: Vec<String>, dropped: Vec<String>, deferred: Vec<String>, unchanged: bool }
```

Three vectors of **attribute names** and a bool. There was no per-kind diagnostic
structure to extend, so the typed report is a **new field**:

```rust
pub vector_unsupported_kinds: Vec<String>,
```

mirrored as `vector_unsupported_kinds` (pyo3 / Python SDK) and
`vectorUnsupportedKinds` (napi / TypeScript SDK).

### 3.1 Why that name

- **`kinds`, said out loud.** The three siblings are lists of projection
  **attribute names**; this is a list of node **kinds**. Two different axes in
  one struct is a category error waiting to happen, so the name carries the axis
  rather than relying on the reader to know. The Rust doc-comment opens with
  "node KINDS, not attribute names", and both SDK suites assert the negative in
  both directions (no attribute name in the report, no kind in `deferred`) so a
  later implementation cannot quietly merge them.
- **`vector_` prefix.** It binds the fact to the dense arm. An unsupported kind
  is **still fully FTS- and lexically searchable**; only vectors are unavailable.
  Without the prefix the field reads as "kinds FathomDB does not support", which
  is false and alarming.
- **`unsupported`, not `skipped`/`ineligible`/`failed`.** "Skipped" implies a
  retry might help; "failed" implies an error occurred (none did, and no
  `projection_failures` row is written — asserted). "Unsupported" is the
  permanent, factual reading.

### 3.2 Why `Vec<String>` and not a richer struct

A `Vec<UnsupportedVectorKind { kind, reason }>` was considered and rejected.
There is exactly **one** reason a kind can appear here — it is outside
`resolve_source_type`'s vocabulary — so a reason field would be a single-variant
enum, i.e. speculative generality. More concretely, a new struct means a new
`#[napi(object)]` type and a new `#[pyclass]`, which is real net-new binding
surface on the slice flagged as most likely to add surface. A `Vec<String>` on an
existing typed struct is already "typed and structured, not a prose string",
which is what the DoD asks for. If a second exclusion reason is ever introduced,
promoting the field to a struct list is a contained change.

### 3.3 Ordering and duplicates

Sorted and de-duplicated, for free, from `SELECT DISTINCT kind … ORDER BY kind`.
The tests write the unsupported kinds out of alphabetical order and write each
one twice, so "sorted and de-duplicated" is a falsifiable claim rather than an
accident of insertion order.

### 3.4 Empty, never absent

The field is always present and is `[]` when there is nothing to report — so a
caller can read it unconditionally. Asserted against `Vec::<String>::new()` (and
`== []` / `deepEqual([])` in the SDKs) rather than `is_empty()`, because that is
the point being pinned.

## 4. Implementation

Three functions, one scan.

- **`vector_eligible_node_kinds(tx)`** — extracted verbatim from
  `enqueue_declared_vector_backfill`, plus an `ORDER BY`:

  ```sql
  SELECT DISTINCT kind FROM canonical_nodes
   WHERE row_kind IN ('leaf', 'coverage')
   ORDER BY kind
  ```

  `row_kind IN ('leaf','coverage')` is the `index_targets_for_row_kind`
  vector-eligibility predicate. `graph` rows are lexically searchable but never
  embedded, and they are excluded on a **row-kind** axis that has nothing to do
  with the `kind` vocabulary — reporting them would be a different, and false,
  statement.

- **`unsupported_vector_kinds(tx)`** — the same list filtered by
  `!kind_is_vector_committable`, i.e. the exact **complement** of the set
  enrolment takes. The two therefore partition ONE list. Two hand-copied queries
  would be the TC-56 drift shape, and the drift here would be silent in the worst
  direction: a report describing a different set from the one actually excluded.

- **`apply_projection_config`** — assigns the report when `vector_declared_after`
  is true.

### 4.1 The two placement decisions

**Scoped to a declared dense arm.** With no `searchable→vector` projection there
is nothing for a kind to be unsupported *for*, so reporting would be noise on
every `filterable`/FTS-only call. Pinned by `no_vector_declaration_means_no_report`,
which also covers the drop direction: once the last dense-arm declaration goes,
the report goes quiet with it.

**NOT gated on `dense_arm_live`.** `enqueue_declared_vector_backfill` only runs
with a live embedder (the Q6a graceful-absent path), and the report sits
deliberately *outside* that branch. `resolve_source_type`'s vocabulary is a
compile-time constant, so "this kind can never be embedded" is equally true with
no embedder attached. Gating it would hide the **permanent** fact behind the
**transient** one — the exact conflation TC-67 exists to end — and a
graceful-absent caller is precisely the one who needs to know that attaching an
embedder later still will not embed these kinds. Pinned by
`the_report_is_the_same_without_an_embedder_and_is_not_the_deferral`, which also
asserts that `deferred` is **identical** across the two sessions, i.e. that it
alone can never carry this information.

### 4.2 A state report, not a diff

It is assigned **after** `delta.unchanged` is computed and does **not** feed it.
`built`/`dropped`/`deferred` describe what *this call changed*;
`vector_unsupported_kinds` describes *the corpus as it stands*. So an idempotent
re-apply returns `unchanged = true` with the three diff lists empty **and the
report populated**. That is deliberate, and §5 depends on it.

### 4.3 Output-only

`configure_projections` accepts `&[ProjectionSpec]`; the new field lives on the
**delta**. There is no inbound direction for it at all, so — unlike
`dense_readiness`, which had to be made accept-inert — it cannot break the
shipped `read.projections` → `configure_projections` round-trip
(`dev/plans/runs/STATUS-0.8.20.md` §14.1). `the_read_configure_round_trip_still_holds`
states that explicitly in all three languages rather than leaving it to
inference.

## 5. The residual: the report is DECLARE-TIME

**Option (a) was taken, deliberately.** The report is computed when
`configure_projections` runs, from the kinds already present in `canonical_nodes`.
**A non-committable kind written *later* will not appear in any report the caller
already holds.**

Option (b) — also surfacing it from `read.projections` so it stays live — was
rejected on cost and on shape. `read_projections` returns `Vec<ProjectionSpec>`,
and `ProjectionSpec` is the **caller-authored declaration type**. Hanging a report
there would either (i) require the same accept-inert round-trip treatment
`dense_readiness` needed, adding a second inert field to a type whose whole
contract is "what you declared", or (ii) change `read_projections`' return type,
which is a larger and more governed change. Neither is warranted for a fact that
is already cheaply refreshable.

**The mitigation, and it only works because of §4.2:** re-apply the same spec.
That is an idempotent no-op — nothing is rebuilt, nothing re-embedded,
`unchanged` comes back `true` — and it returns a **current** report. Stated as an
executable fact in all three suites
(`the_report_is_state_not_diff_so_an_idempotent_reapply_still_carries_it`), which
first asserts that the previously-held delta does *not* learn about the late
kind, then that the no-op re-apply does.

Second residual, smaller: the report describes **node** kinds only. Edge bodies
project under `edge_fact`, which is inside the vocabulary, so there is nothing to
report on that axis today.

## 6. What this tells a consumer

This is the consumer-visible point of TC-67 and it belongs in the release notes,
not only here.

A consumer whose entity kinds sit outside the locked vocabulary — **Memex** is
the concrete case — declares `searchable→vector` and, before this slice, saw
`deferred` and nothing else. It now also sees, by name, which of its kinds will
**never** be embedded. Those rows still get **FTS and lexical search**; they will
simply never participate in dense/vector retrieval, in this session or any future
one. The actionable options are: use one of the mapped kinds, or accept
lexical-only retrieval for those rows. Waiting is not one of them, and that is
exactly what the old `deferred`-only signal implied.

## 7. Explicitly out of scope

`dev/plans/plan-0.8.20.md` §11 ruling item **4** — *"an `fts`/`vector` sub-object
without the `searchable` role is an **invalid spec**; implement the rejection at
the next `configure_projections` slice"* — is a ruled HITL decision gated at a
`configure_projections` slice, and Slice 22 is one. It is **not** in the R-20-VC
four-leg scope and was **not** implemented here; the placement question is with
the Steward.

**This work makes it no harder, and marginally easier.** The rejection belongs in
`apply_projection_config`'s up-front validation loop, alongside the existing
empty-roles and duplicate-name refusals — the same loop, a fourth `if`, before
any write. TC-67 added nothing to that loop and nothing to `ProjectionSpec`; it
only appended a field to the returned delta, on a code path (`vector_declared_after`)
that runs long after validation. The one small assist: the invalid shape is a
`vector` sub-object with no `searchable` role, and this slice's tests already
build both spec shapes (`vector_spec` / `filterable_only_spec`) with helpers a
rejection suite can lift verbatim.

# 0.9.0 readability refactor — proposal

> **Purpose.** Make the repository understandable and hygienic for **both human
> and agentic consumption**. Candidate scope for 0.9.0, placed by HITL.
>
> **Evidence base.** A four-phase background check run on branch
> `refactor-background-check`: web research into file-size heuristics
> (adversarially verified), a deterministic scan of every tracked file, a
> per-file review of all 66 violators, and a cross-file reconciliation.
>
> **Grounding.**
> `dev/plans/refactor-background-check/engine-decomposition.md` ·
> `dev/plans/refactor-background-check/refactor-proposals.md` ·
> `dev/plans/refactor-background-check/horizontal-reconciliation.md` ·
> ledger `dev/ledger/refactor-background-check-ledger.jsonl` (seq 1–113)

## The proposal

**The evidence says this is not a splitting campaign, and the scope should say
so out loud.** Fifty-nine of sixty-six flagged files are settled LEAVEs: a
73-entry release log, a frozen measurement pipeline, a 100-test suite for one
tool. They are long because their work is long, and the research is explicit
that shortening them buys nothing — El Emam et al. found no threshold effect of
file size on defects, Yamashita et al. found larger files have *lower* defect
density, and Hatton found components get measurably worse below ~200–400 lines.
A 0.9.0 that shatters files would therefore spend real effort to make the repo
worse by its own stated goal. What survives scrutiny is narrow and concrete: one
genuine structural defect, four duplication or embedded-language defects, and a
navigation layer that is missing rather than broken. Framing 0.9.0 that way also
protects it politically — the deliverable is "the repo is navigable", not "the
line counts came down", and those are different targets that a line-count
framing would quietly conflate.

**The engine is the release.** `impl Engine` is a single 5,008-line block
carrying 140 methods — but median method length is 20 lines and only two exceed
200, so the methods are fine and one *type* is doing 140 jobs. That is the one
defect in this repo that genuinely obstructs both audiences at once: a human
cannot hold 140 responsibilities in their head, and an agent cannot answer a
question about one capability without ingesting 17,910 lines. The decomposition
into ~16 capability modules requires **zero public API change** — verified by
compiling it, including the predicted `E0616` failure when the struct leaves the
crate root — so this is a navigability change, not an API event, and it should
be scoped and communicated as such. Two things gate it and neither is
negotiable: the public-symbol baseline tooling the plan depends on does not exist
yet and must be built or vendored first, and the engine steps need a quiet window
that 0.8.20 currently occupies. Everything else is independent and can land in
any order.

**The durable half is the navigation layer, and it is where the two audiences
actually diverge.** Three artifacts already built should become permanent rather
than one-off: the structure maps (an agent orienting in a large file should read
a 40-line outline, not the file), the advisory scanner, and the ledger of settled
verdicts — which is what stops the next review from re-deriving all 66
conclusions from scratch. The genuinely unresolved tension is
`dev/plans/runs/STATUS-0.8.0.md`: 2,087 lines is ~32,000 tokens, which the
documentation literature says to leave intact and the context literature says is
already past where retrieval reliably works. Splitting it destroys the
chronological spine humans need; leaving it makes it unreadable to the agents
that read it mid-session. **Archive-and-link resolves it** — freeze the closed
portion, link forward, keep the spine intact and the live surface small. That is
proposed as the pattern for every append-only record in the repo, and it is the
clearest example of why "readable" has to be defined per-audience rather than as
a single line count.

## Provenance and staleness — read before acting on any line number

**Every line range in this proposal and in the three grounding documents is
pinned to `ff4f07a0`** (branch point of `refactor-background-check`). They are
already stale, and measurably so.

Within roughly two days of active 0.8.20 work, `main` advanced 70 commits and
`fathomdb-engine/src/lib.rs` grew from **17,910 to 18,867 lines** (+1,002
insertions, −45 deletions). `impl Engine` moved from L4110 to L4184.

Two consequences, in opposite directions:

- **Re-anchor before execution.** Do not feed these line ranges to an
  implementer as-is. Re-run
  `dev/plans/refactor-background-check/scan_file_sizes.py` against the target
  commit to regenerate `structure/` maps first. The scanner is deterministic, so
  this is cheap and exact.
- **The structural claim survives, and the drift strengthens the case.**
  `struct Engine` is still at the crate root (L274 → L281) and there is still
  exactly one top-level `impl Engine` block, so the zero-API-change mechanism is
  intact. Meanwhile the file accreted ~950 net lines in two days *while nobody
  was refactoring it* — which is the argument for doing this work, and also the
  reason the quiet-window prerequisite is real rather than procedural.

These are the results a per-file review structurally cannot produce.

- **`_fathomdb.pyi` citation goes stale.** The stub earned a LEAVE on its own
  merits, but its header cites *"Mirrors the surface emitted by
  `src/rust/crates/fathomdb-py/src/lib.rs`"* — the file proposed for a 7-way
  split. No gate checks that citation, so nothing fails red; the doc just
  quietly becomes false. Land the header edit **in the same change** as the
  split.
- **76 LOC duplicated verbatim** between `eu7_real_corpus_ac.rs` and
  `support/corpus_harness.rs` (`SplitMix64`, `synth_query`, `lead_sentence`,
  `LEAD_MAX_CHARS`).
- **CI setup repeated 7×** across `ci.yml` and `perf-canonical.yml` (TMPDIR,

- **~40 LOC of test harness** duplicated across 3 shell test suites; and
  `read_crate_version` / `registry_has_version` duplicated across 2 release
  scripts. Both are real but modest — recorded, not scheduled.

## What this review did NOT establish

Stated plainly so nobody reads more into it than it earns.

- **Statuses, not correctness.** The engine module tree is a *proposal* reviewed
  on paper plus a compiled visibility probe. No engine code was moved, and no
  test was run against a decomposed tree.
- **The compile proof is narrow.** It confirms Rust's inherent-impl and
  private-field-visibility rules behave as the plan requires, and that the
  predicted failure mode reproduces. It does not prove the *specific* 20-module
  boundary is the right one.
- **Thresholds are a convention.** Every per-file number in `thresholds.json` is
  an attention-allocation device. Six of fifteen classes were calibrated against
  this repo's own distribution, which bakes in the fact that this repo runs far
  above the empirical central tendency (Herraiz et al. measured a median of 63
  SLOC per file across 1.36M files).
- **Three classes have no literature backing at all** (`doc-other`, `py-stub`,
  `ci-workflow`) and are labelled as such in the ledger.
- **No effort estimate.** Nothing here has been sized in time or risk beyond the
  sequencing and prerequisites above.

# TC-91 Projection Commit Hardening

## Status and scope

This is a code-grounded, implementation-ready design for the narrow TC-91
Option 2 remedy. It is not an implementation, release assignment, scheduler
redesign, or change to the public binding surface.

It addresses two coupled faults in the projection worker:

1. `commit_projection_outcomes` begins a deferred SQLite transaction, reads
   before it writes, and can therefore fail an un-retryable read-to-write
   promotion while another connection owns the WAL writer lock.
2. `run_projection_jobs` discards that function's `Result`; the panic recovery
   helper `commit_projection_panic_failures` does the same. The work stays
   non-terminal and is eventually redispatched, but neither the host nor a
   test can distinguish that loss from an ordinary successful run.

The characterization establishes that a held external WAL writer lock makes
the second failure mode observable as duplicate embeds while both terminal and
`projection_failures` counts remain zero. It does not establish that every
baseline duplicate has that cause. This design must not claim otherwise.

Authoritative background:

- [TC-90/TC-91 characterization](0.8.20-tc90-tc91-characterization.md),
  especially sections 5.4--5.6 and remedies R-B through R-D.
- [Projection model ADR](../adr/ADR-0.6.0-projection-model.md): projection
  work is post-commit, terminal state advances the cursor, and exhausted
  *embed* failures are recorded in `projection_failures`.
- [Projection subsystem design](projections.md): a missing terminal is pending
  work; `projection_failures` is an audit record, not a work queue.
- [Lifecycle design](lifecycle.md): SQLite-internal diagnostics must use the
  host subscriber path; the public counter key set is locked.

## Current mechanism

The worker obtains jobs from the runtime queue, calculates
`ProjectionOutcome`s, then calls `commit_projection_outcomes`.

- `commit_projection_outcomes` takes `commit_gate`, but currently calls
  `Connection::transaction()`, which is `BEGIN DEFERRED`.
- It reads the mean profile and terminal state before the first vector/terminal
  write. A competing engine writer can therefore make its promotion fail with
  `SQLITE_BUSY` or `SQLITE_BUSY_SNAPSHOT`; the busy timeout does not repair a
  promotion failure.
- `run_projection_jobs` evaluates that result as `let _ = ...`. After the
  worker returns, normal state cleanup removes its cursors from `in_flight` and
  sets `pending_scan`. The dispatcher then finds the still-non-terminal rows
  and embeds them again.

The retry is therefore already implicit in the durable source of truth, but it
is invisible and needlessly recomputes a successful embedding. It is not an
embedder failure: the embed succeeded, while the later SQLite transaction did
not become durable.

There is a second transactional concern. On a mean-centering-required identity,
the current transaction mutates `shared.mean_accumulator` before `tx.commit()`.
If the transaction rolls back, the accumulator can claim a vector was counted
or the mean was pinned even though the database did neither. Error handling
must make that in-memory state commit-atomic too.

## Invariants

The implementation and tests must preserve all of these properties.

1. A projection cursor advances only after a durable `up_to_date` or `failed`
   terminal, never after a failed worker commit.
2. A worker commit failure writes neither an `up_to_date` nor a `failed`
   terminal, creates no vector row, and creates no `projection_failures` row.
3. `ProjectionOutcome::Failure` remains exclusively the result of exhausted
   embedder work. It retains the existing terminal plus audit-row behavior.
   A SQLite commit failure must never be converted into that outcome.
4. The worker failure is observable through the existing lifecycle subscriber
   path. A SQLite error yields its existing `SqliteInternal` diagnostic; a
   non-SQLite `rusqlite::Error` yields the existing engine `StorageError`
   diagnostic. No new public event shape or counter key is introduced.
5. After a failed commit, the current jobs are released from `in_flight` and
   the dispatcher is woken only through the established state-cleanup path.
   The pending canonical rows are the source of truth for redispatch; there is
   no second queue, terminal rewrite, or direct mutation of the caller's write.
6. A normal competing writer cannot cause a read-to-write promotion: the
   worker obtains writer intent before it reads. If contention resolves within
   the existing SQLite busy timeout, that same computed outcome commits. If the
   timeout is exhausted, the transaction rolls back, the error is observable,
   and durable redispatch recomputes the outcome; it is not silently discarded.
7. The mean accumulator and `MeanVecPinned` event are published only after the
   same transaction has committed. A failed transaction leaves both precisely
   as they were before that commit attempt.
8. A worker panic remains an embedder/worker failure whose successful terminal
   commit uses the existing `ProjectionPanic` behavior. If that *terminal
   commit* fails, it is a commit failure: it must be reported and redispatched
   non-terminally under rules 1--5, rather than be swallowed or invented as a
   durable `ProjectionPanic` record.

## Proposed implementation

### 1. Acquire worker writer intent up front

Inside `commit_projection_outcomes`, retain the existing `commit_gate` and
replace `connection.transaction()` with
`connection.transaction_with_behavior(TransactionBehavior::Immediate)`.

`BEGIN IMMEDIATE` acquires the WAL writer reservation before the mean and
terminal reads. If the engine writer is briefly active, SQLite's existing busy
handler can wait. This is deliberately the worker-side analogue of the
already-landed TC-57 writer correction, not a global scheduler lock.

It does not serialize an embed with a write: only the short projection-commit
transaction is inside this writer-intent window. The two projection workers
remain ordered by `commit_gate`, as required by the mean-pin ordering rule.

### 2. Return and report a failed commit

Make both `run_projection_jobs` and `commit_projection_panic_failures` return
`rusqlite::Result<()>` rather than discard their commit results. In
`projection_worker_loop`, select the ordinary or caught-panic terminal commit,
then handle either helper's `Err` before ordinary state cleanup:

- dispatch one lifecycle failure through a subscriber registry carried in
  `ProjectionRuntimeShared` (the registry already exists before the runtime is
  constructed);
- use the existing SQLite code classifier and `SqliteInternal` source when a
  SQLite extended code is present; otherwise dispatch the existing engine
  `StorageError` failure form;
- do not write an audit row, terminal state, or replacement projection outcome;
- then follow the existing cleanup exactly: decrement `active_jobs`, remove
  each cursor from `in_flight`, set `pending_scan` unless stopping, and notify.

That last step is the explicit requeue rule. On the next scan the dispatcher
reconstructs jobs from canonical rows whose terminal is still absent. It is
correct across process restart because it depends on durable pending state, not
on an in-memory retry list. It can re-embed after an exceptional exhausted
commit failure, but no successful result is ever silently lost.

No change is made to `CounterSnapshot`: its key set is contractually locked.
The lifecycle event is the operational observation required to diagnose a
failure without treating it as an embed error.

### 3. Make mean-pinning commit-atomic

While holding `commit_gate`, clone the optional `MeanAccumulator` into a local
candidate before processing outcomes. Apply all `add`, threshold, and pin
decisions to that candidate, not to `shared.mean_accumulator`. Keep the shared
accumulator locked while the transaction executes so no other commit can
interleave its state transition.

Only after `tx.commit()` succeeds:

1. replace the shared accumulator with the candidate;
2. append staged `MeanVecPinned` events.

On any error, transaction drop/rollback and dropping the candidate leave the
shared accumulator and pending-event queue unchanged. A redispatched row is
therefore counted once, in the one commit that becomes durable. This is needed
even if the common lock-contention case disappears under `BEGIN IMMEDIATE`:
disk, schema, cancellation, and test-injected commit failures retain the same
all-or-nothing obligation.

### 4. Test-only fault control

Add a debug-only one-shot projection-commit fault seam on the projection
runtime, not on the caller's writer. It must inject a synthetic SQLite failure
after the transaction has prepared its candidate mean state and immediately
before `tx.commit()`. The seam exists solely to prove rollback behavior; it is
not exported through bindings or used by production code.

The fault seam has two named variants: a SQLite-busy variant, which proves
`SqliteInternal` classification, and a non-SQLite `rusqlite::Error` variant,
which proves the engine `StorageError` classification. A separate test-only
post-report barrier may pause cleanup after a forced failure; it is necessary to
prove that stopping before redispatch leaves a durable pending row for reopen.

The existing `Engine::force_next_commit_failure_for_test` is unsuitable: it
only faults the primary caller commit before projection work exists.

## Failure semantics

| Failure point | Terminal/audit result | Observation | Next action |
| --- | --- | --- | --- |
| Embed retry budget exhausted | Existing `failed` terminal plus one `projection_failures` audit record | Existing behavior | Cursor may advance; operator recovery is unchanged |
| No configured embedder for an enrolled node kind | No terminal or audit row | Existing readiness/drain behavior | Later live-embedder session dispatches it |
| Projection SQLite commit fails | No terminal, vector row, or `projection_failures` record | One lifecycle error event | Release `in_flight`; dispatcher rescans the durable pending row |
| Projection worker panics and its terminal commit succeeds | Existing `ProjectionPanic` terminal plus audit record | Existing behavior | No change in this design |
| `ProjectionPanic` terminal commit fails | No terminal, vector row, or `projection_failures` record from that failed transaction | One lifecycle error event | Release `in_flight`; dispatcher rescans the durable pending row |

The third row is intentionally non-terminal. Recording it as an embed failure
would violate the projection model and hide a still-recoverable row behind a
terminal cursor. Making it fatal to the original `Engine::write` is impossible
and incorrect: that write already committed before post-commit projection work
started.

## TDD and acceptance tests

Tests are written and committed before the production change. The existing
characterization test that asserts blindness must be rewritten, not merely
rerun: its old green result encodes the defect.

1. Add a non-ignored deterministic TC-91 test using the SQLite-busy one-shot
   seam. It writes an enrolled row, forces the next projection commit to fail,
   and asserts: a `SqliteInternal` lifecycle error was received; no failed
   terminal or `projection_failures` row exists; `drain` eventually succeeds;
   and the row eventually has exactly one durable vector. The recording
   embedder must show the expected redispatch rather than a silent disappearance.
2. Add
   `tc91_projection_commit_failure_at_mean_pin_is_rollback_safe`. Commit 255
   deterministic mean-centering-required rows, arm the failure seam, then write
   row 256. The first threshold-crossing commit must roll back; its redispatch
   must produce one durable mean pin, one `MeanVecPinned` event, and correctly
   centered vectors for every row. This test fails if the shared accumulator
   advances before commit.
3. Rewrite the external-lock TC-91 arm as an acceptance test for writer intent:
   while a second connection holds `BEGIN IMMEDIATE` for less than the existing
   busy timeout, the worker waits and commits. It must reach idle with no
   duplicate ingest embeds, no failed terminal/audit row, and no worker commit
   error event. Keep this timing-sensitive pressure test ignored; run it
   explicitly in the evidence sequence.
4. Change the two 200-row TC-91 duplicate-rate arms and the tight/spaced
   cadence arm from characterization-red to acceptance-green: every arm must
   report zero duplicates while preserving `ingest_distinct == rows`,
   `vector_rows == rows`, and `probe_calls == 0`. Their concurrency sensitivity
   keeps them as explicit evidence runs, not default merge-gate tests.
5. Preserve the pure TC-57 mechanism pins in
   `tc57_governed_write_race.rs`: they establish the caller-side promotion
   mechanism and must not be diluted by this worker correction. Tighten
   `tc57_worker_commit_pressure.rs`, however: delete its stale baseline prose
   that calls roughly 50% duplicate dispatch ordinary and replace its
   `repeat_embeds <= ROWS` acceptance with zero duplicate embeds in both arms.
   The pressure target remains a worker-commit acceptance test, not an
   embed-failure test. Keep embed-failure/`ProjectionPanic` terminal semantics
   covered by `eu5f_production_pin.rs` and add the commit-failure test below.
6. Add
   `tc91_projection_commit_storage_error_is_reported_and_redispatched` using
   the non-SQLite fault variant. It asserts one `Engine`/`Error` lifecycle event
   with `StorageError`, no terminal or audit row from the failed attempt,
   successful redispatch, and no `SqliteInternal` event substituted for it.
7. Add
   `tc91_projection_panic_terminal_commit_failure_is_reported_and_redispatched`.
   The embedder panics on its first call, so the worker attempts the existing
   `ProjectionPanic` terminal; force that terminal commit to fail, assert the
   SQLite lifecycle event and absent terminal/audit row, then let redispatch
   run. The recovered embed must commit normally, proving that a failed
   panic-terminal commit is neither swallowed nor falsely durable.
8. Add `tc91_projection_commit_failure_survives_stop_and_reopen` using a
   race-free, two-phase shutdown latch around the post-report barrier:

   1. Force a commit error. The worker reports it, signals that it is held
      before cleanup, and waits on the barrier.
   2. Start `Engine::close` on a separate test thread. The runtime's test-only
      stop acknowledgement signals only after `state.stopping` is true and
      before `close` can join the held worker. The test must wait for that
      acknowledgement; observing only that the close thread was spawned is
      vacuous.
   3. Release the worker cleanup barrier only after the stop acknowledgement,
      then join the close thread. Because cleanup sees `stopping`, it must not
      request a new scan; because the barrier is released before joining, the
      test cannot deadlock.
   4. Reopen with the same embedder and drain. The reopened engine must create
      the vector without a prior terminal/audit row. This proves durable
      pending-state recovery rather than an accidental dependence on the
      original runtime queue.

## Non-goals and decision boundaries

- No durable retry queue, lease protocol, scheduler ownership redesign, or
  exactly-once promise is added.
- No change is made to primary-write transaction policy, TC-90, or the
  unrelated whole-workspace CI serialization work.
- No new `projection_failures` schema or public SDK/API surface is added.
- This does not assert that every historic duplicate is a failed worker commit.
  The new event supplies evidence for future measurements instead.
- If a bounded direct retry of the already-computed outcomes is desired after
  this fix, it is a separate decision. It must first show that immediate writer
  intent plus durable redispatch leaves a material residual; it must also retain
  the mean-state rollback property specified here.

## 1. Why this exists

The manual loop this replaces is `dev/plans/prompts/LIBRARY-BUMP-STEWARD.md` §1–2: build the
backlog from "*union of open Dependabot PRs, a fresh `cargo upgrade --dry-run` / `npm outdated` /
equivalent, and `gh api …/dependabot/alerts`*", then run a five-question triage per candidate
(tracked? direct or transitive? already satisfied? security-driven? otherwise `DO`).

That loop is a search → review → check → reason cycle executed by an agent, once per candidate,
across five ecosystems. The HITL's ruling is that it must be **~90% mechanical and automated**.
Every one of those five triage questions is answerable from data the repository already tracks:

| LBS §2 triage question | Mechanized by |
|---|---|
| Is the target manifest **tracked** on `main`? | `git ls-files`-derived discovery (§5.1) |
| Is it **direct** or transitive-only? | `depth` tag on every component (§5.5) |
| Is the locked version **already at/past** target? | `status` in the staleness report (§5.4) |
| Is it **security-driven**? | out of scope here — advisories stay a `gh api` call; the SBOM supplies the exact locked version each advisory must be matched against |
| Otherwise `DO`, with a blast estimate | `edit_sites` — the exact manifest paths a bump must touch (§5.8) |

**And the sixth thing every sweep owes.** LBS's own Definition of Done includes
"**`dependabot.yml` reconciled**" — *"so its coverage matches real manifests (stops orphan PRs being
generated)"*. That reconciliation is a set-difference between *tracked manifests* and *configured
Dependabot directories*, and it is exactly what this tool's discovery output makes computable
(§5.3). `.github/dependabot.yml` is therefore not a bystander here: it is the **existing tracked
ruling** this tool's tiering must reconcile with rather than re-derive, and the first thing a
reconciliation surfaces on this repo is a real gap (§5.3).

## 2. Scope, and the hard guardrails that bind every leg

**In scope.** A small, isolated Python mini-project under `scripts/sbom-survey/` that:

1. discovers every **tracked** dependency manifest and lockfile on `main`;
2. tags each component with a tier — `shipped` / `dev-tooling` / `eval-only`;
3. emits a **CycloneDX 1.6 JSON** SBOM including the **library↔library** dependency graph;
4. diffs **used (locked) versus published (registry latest)** and reports `current` / `outdated` /
   `ahead` / `unknown`.

**Out of scope, permanently.**

- **No leg applies a dependency bump. No manifest and no lockfile changes inside 0.8.20.** The
  survey is an **INPUT to 0.8.22**, which already owns `napi 2→3`, `rusqlite 0.31→0.40 +
  sqlite-vec`, the `sqlite-vec 0.1.9` bump (`seq-151`) and the six Dependabot advisories
  (`seq-152`).
- **Not CI-gating.** Recurring by design, **informational**. Wiring it into
  `.github/workflows/ci.yml` or `scripts/agent-test.sh` is explicitly out of scope (§7).
- **Not a vulnerability scanner.** It produces the SBOM an advisory feed is matched *against*; it
  does not fetch advisories.
- **Not an upgrade applier.** It never edits a manifest, and it has no write path outside its own
  gitignored output directory.

**Isolation.** The mini-project's own manifest (`scripts/sbom-survey/pyproject.toml`, a **Slice 32**
artifact) is a standalone project: it is **not** a member of the Cargo workspace, **not** referenced
by `src/python/pyproject.toml`, and **not** a dependency of the root `package.json`. It can
therefore never enlarge the published dependency graph or the advisory backlog. Its own dependencies
are surveyed *by* the tool, tagged `dev-tooling` — the tool appears in its own SBOM, which is the
correct answer, not an accident.

## 3. Requirements

| Req | Statement |
|---|---|
| **REQ-1 Discovery** | The candidate manifest set is derived from `git ls-files` — the set of paths **tracked on `main`** — never from a filesystem walk. |
| **REQ-2 Completeness** | Every tracked path whose basename is a recognized manifest or lockfile name is discovered. Nothing tracked is silently missed. |
| **REQ-3 Tiering** | Every emitted component carries exactly one tier from the ruled vocabulary `{shipped, dev-tooling, eval-only}`, assigned from a **tracked data file**. |
| **REQ-4 Loud gaps** | A tracked manifest with no tier assignment is a **hard error naming the path**. It is never emitted untagged and never silently dropped. |
| **REQ-5 Fixture exclusion** | Deliberately fake test-fixture manifests are excluded from the BOM by a **data-driven, auditable** rule — never by a hardcoded special case in code. |
| **REQ-6 CycloneDX** | Output is schema-valid **CycloneDX 1.6 JSON**, with a closed `dependencies` graph and a `purl` per component. |
| **REQ-7 Resolved versions** | A component's `version` is the **locked/resolved** version, not a manifest range. The declared constraint is preserved alongside it. |
| **REQ-8 Direct vs transitive** | Every component is tagged `direct` or `transitive`. LBS §2's triage turns on this distinction. |
| **REQ-9 Injectable registry** | The published-version lookup is behind an injectable seam. The test suite **never** requires network. |
| **REQ-10 Honest degradation** | An unavailable, erroring or unparseable "latest" is reported **`unknown`**. It is **never** reported `current`. This is the single worst failure this tool can have. |
| **REQ-11 Gitignored reports** | Generated reports land in a **gitignored** directory. Slice 33's *findings* have a separate **tracked** home. |
| **REQ-12 Not CI-gating** | The tool declares its own non-gating status, and that declaration is cross-checked against the actual CI wiring. |
| **REQ-13 Determinism** | Two runs over identical inputs produce byte-identical artifacts, so a re-run diffs cleanly. |
| **REQ-14 Slice-33 consumer** | The staleness report carries every field Slice 33 needs to answer "what is stale" and "would a surgical ~1–5 SLOC change land it", without re-deriving anything. |

## 5. Design — the eight points this will be probed on

### 5.1 Discovery is `git ls-files`-derived, not a filesystem walk

`discover_manifests(repo_root, *, ls_files=None)` obtains its candidate paths by running
`git ls-files -z` at `repo_root` (injectable for tests), filters by basename against the recognized
manifest table, and returns `ManifestRef(path, ecosystem, kind)`.

**Why not a walk.** A walk sees `target/`, `node_modules/`, `.venv/`, `site/` and every gitignored
scratch tree; on this repo that is tens of thousands of vendored manifests, none of which the
project owns. Worse, it sees precisely the class of file the LBS charter §2 warns about — *"noise
against gitignored dev/eval lockfiles"* — and would manufacture a backlog of dependency bumps for
artifacts that do not exist on `main`.

**The tracked manifest set at `cbb56212` — 28 paths, enumerated.** Reproduce with:

**`python/pyproject.toml` is OUT OF SCOPE, and this is the trap.** `.gitignore` line 88 ignores
`/python/` **in its entirety** (root-anchored; the comment there explains it is a sourceless
recovered binding kept on disk for Memex). Verified at `cbb56212`:

```text
$ git check-ignore -v python/pyproject.toml
.gitignore:88:/python/    python/pyproject.toml   <- (TAB in real output)
$ git ls-files python/

```

The directory does not even exist in this worktree. It is cited elsewhere in the program's records
as if it were a real manifest; it is not tracked, so it is not in BOM scope, and a filesystem-walk
discovery on a developer machine that *does* have it would silently pull a pinned `0.1.0` shim into
the SBOM. This is the exact "noise against gitignored dev/eval lockfiles" case LBS §2 names.
`git ls-files` makes it structurally impossible.

**Recognized basenames — the table, and its mirror in the test oracle.** Twelve exact basenames plus
one glob, in two groups:

| Group | Names | Tracked matches at `cbb56212` |
|---|---|---|
| Matches today | `Cargo.toml`, `Cargo.lock`, `package.json`, `package-lock.json`, `pyproject.toml`, `uv.lock`, `setup.py`, and the glob `requirements*.txt` | the 28 paths above |
| Recognized, forward-looking | `yarn.lock`, `pnpm-lock.yaml`, `poetry.lock`, `Pipfile`, `setup.cfg` | **none** — verified: `git ls-files \| grep -E '(^\|/)(setup\.cfg\|Pipfile\|poetry\.lock\|yarn\.lock\|pnpm-lock\.yaml)$'` exits `1` with no output |

The second group is present so that adding one of those files to the repo is *discovered* (and then
fails REQ-4 tiering loudly) rather than silently ignored. Because none of them matches anything
today, the group is a pure forward guard: it changes no discovered path and leaves §5.1's 28-path
enumeration exact.

⚠ **This table is mirrored 1:1 by `MANIFEST_BASENAMES` in `scripts/sbom-survey/tests/conftest.py`,
and the two must be kept in lockstep.** That tuple is the oracle `AC-SBOM-03` grades against, so a
name that appears here but not there is a manifest the implementation may silently skip *while the
suite still reports green* — the design would state a requirement the tests do not enforce.
`setup.cfg` was exactly that divergence (codex §9 round 1, fix-1 finding 1); the whole table was
re-diffed against the helper when it was closed, and `poetry.lock` / `Pipfile` / `yarn.lock` /
`pnpm-lock.yaml` were confirmed already present on both sides.

### 5.2 Fixture manifests — excluded by a data rule, and audibly so

`dev/release/fixtures/cargo-skew/**` (4 × `Cargo.toml`) and `dev/release/fixtures/pip-skew/**`
(4 × `setup.py`) are **deliberately fake, deliberately skewed** manifests that exist to make the
release version-skew gates demonstrate their catch. A naive "everything tracked" scope emits them as
real dependencies, and every downstream consumer then sees phantom packages at wrong versions.

**This is not a fresh decision — it re-states a ruling already on disk.** `.github/dependabot.yml`'s
header carries an explicit *"Deliberately NOT covered (do NOT add — adding any of these reintroduces
noise/orphans)"* list, and its third entry is verbatim:

```text
#   - dev/release/fixtures/cargo-skew/**  (intentional mock crates for release-skew tests).
```

The repository has therefore **already ruled**, under the reconciliation that closed Library Sweep #1
(`0.8.11.1`, `R-SW-5`), that these manifests are out of dependency scope — and it ruled it for the
same stated reason (noise / orphans). Excluding them here is *reconciling with* that ruling, not
re-litigating it, which is what makes the decision cheap. The tool extends it in one direction the
Dependabot config could not: `dev/release/fixtures/pip-skew/**` (the 4 `setup.py`) is not named
there only because no `pip` directory was ever configured near it, so no orphan PR could be
generated; it is the identical class of artifact and takes the identical rule.

**Decision.** They are **excluded from the BOM**, by an `action = "exclude"` rule in the tracked
`tiers.toml`, with `reason = "fixture"` — and the excluded set is **carried in the survey output**
(`survey.excluded`, mirrored into the CycloneDX `metadata.properties` as
`fathomdb:excluded-manifest`) so the exclusion is auditable rather than invisible.

**Why exclusion and not a fourth tier.** §3a ruled the tier vocabulary as
`shipped` / `dev-tooling` / `eval-only`. Adding `fixture` would silently re-litigate a HITL ruling
and, worse, would put non-existent packages in the component list where a vulnerability feed or a
`purl` consumer would treat them as real. Exclusion-with-a-record is the honest shape: they are
manifests, they are tracked, they are knowingly not dependencies.

**Why data-driven.** The rule lives in `scripts/sbom-survey/tiers.toml` next to the tier rules, in
the same first-class rule list, so:

- it is reviewable in one file rather than grep-able out of a code path;
- a future fixture directory is added by editing data, with no code change;
- `AC-SBOM-06` can *prove* it is data-driven — the test loads a tier map with the rule removed and
  asserts the fixture manifests then flow through (and trip REQ-4), which a hardcoded `if
  path.startswith("dev/release/fixtures/")` could not satisfy.

**Free consequence.** Because the only tracked `setup.py` files are the four excluded pip-skew
fixtures, the tool needs **no `setup.py` execution or AST parsing** — the single most fragile parser
in the Python packaging space is never written. If a real `setup.py` is ever tracked it is
discovered, hits no tier rule, and fails loudly (REQ-4) rather than being mis-parsed.

### 5.3 Tier assignment, and the loud failure for a new manifest

**The tier partition is derived from `.github/dependabot.yml`, not invented here.** That file is a
tracked source of record whose header already partitions this repository along the same axis the
tier vocabulary does — it names the entries that *"cover every SHIPPED/tracked manifest"*, and then
names, explicitly, what is *"Deliberately NOT covered (do NOT add …)"*. Deriving `tiers.toml` from it
means `shipped` / `dev-tooling` / `eval-only` reconcile with an existing ruling instead of a second
opinion drifting away from it:

| `dependabot.yml` entry / exclusion | Verbatim rationale in that file | Tier rule it yields |
|---|---|---|
| `pip /src/python` | "shipped Python package" | `src/python/` → `shipped` |
| `cargo /` | "workspace root — covers all `src/rust/crates/*` members" | `Cargo.` + `src/rust/crates/` → `shipped` |
| `npm /src/ts` | "TypeScript binding" | `src/ts/` → `shipped` |
| `npm /` | "root markdown dev tooling — see `R-DEP-2` note" | `package` → `dev-tooling` |
| `github-actions /` | "all `.github/workflows/*`" | **out of BOM scope** — no ecosystem in `{cargo, npm, pypi}`, no manifest basename; recorded here so its absence is deliberate, not an omission |
| NOT covered: `/python` | "uv-managed **EVAL ENV**; `python/uv.lock` is gitignored, not shipped … the source of the idna/torch security-alert noise — keeping it uncovered is intentional" | out of scope by **untracked-ness** (§5.1), which is the stronger mechanism: `git ls-files` cannot reach it at all |
| NOT covered: `dev/research/**`, `data/corpus-data/**` `requirements*.txt` | "eval/corpus fetch artifacts" | the `eval-only` tier exists for exactly these; all are gitignored today, which is why it currently matches nothing |
| NOT covered: `dev/release/fixtures/cargo-skew/**` | "intentional mock crates for release-skew tests" | the `action = "exclude"` / `reason = "fixture"` rule (§5.2) |

Two things fall out of reading it, and both are worth stating plainly.

**(a) The fixture exclusion is the already-ruled position** (§5.2), which strengthens it
considerably: this design is not asking for a new carve-out, it is honouring one that has been on
disk since `0.8.11.1`.

**(b) `dev/tools/mermaid/package.json` is a real, tracked npm manifest covered by NO Dependabot
directory** — the configured `npm` entries are `/src/ts` and `/` only. That is a genuine coverage
gap of the **same class as the `R-DEP-2` note** in that file, which records that the root
`package-lock.json` carried two live advisories (`markdown-it` GHSA-6v5v-wf23-fmfq, `js-yaml`
GHSA-h67p-54hq-rp68) while sitting under no configured directory, so its security PRs never
auto-opened. `dev/tools/mermaid/` is in that position today.

This design **rules nothing** about it — no manifest and no config is edited in 0.8.20 (§2), and
`.github/**` is out of bounds for every leg. What matters here is that **the tool surfaces it
mechanically**: `dev/tools/mermaid/package.json` and `dev/tools/mermaid/package-lock.json` are two of
the 28 discovered paths, they tier as `dev-tooling`, and the set-difference against the five
configured Dependabot directories is a one-line consumer of that output. Since LBS's own Definition
of Done includes "`dependabot.yml` reconciled" (§1), that is a concrete, already-cashable
demonstration of the tool's value: the manual sweep had this gap and did not report it. It is

**Matching is longest-prefix-wins, not first-match-wins.** File order is then irrelevant, so
reordering the rules can never change the answer — a property worth having in a file that will be
edited by whoever adds the next manifest. Duplicate prefixes are a load-time error.

**There is deliberately NO catch-all / default rule.** A tracked manifest matched by no rule raises
`UntieredManifestError(path)`; `run_survey` propagates it and the CLI exits `2` with the path on
stderr. A default would convert "somebody added a manifest and nobody classified it" — the exact
event this tool exists to catch — into a silent mis-tag. This is `AC-SBOM-07` (unit) and
`AC-SBOM-21` (CLI), and it is the failure mode that gets its own named test per §5 item 3.

**`eval-only` currently matches nothing.** The eval/corpus trees (`data/corpus-data/**`,
`dev/research/**` and `eval/**` lockfiles) are gitignored today, so no tracked manifest is
eval-only — and those are precisely the trees `dependabot.yml` lists as deliberately uncovered. The
value stays in the vocabulary because if one ever *becomes* tracked it must be taggable as eval-only
rather than silently absorbed into `shipped`; the file's own note that `/python` "is the source of
the idna/torch security-alert noise" is the concrete record of what mis-tagging an eval tree costs.

### 5.4 The published-version seam — injectable, and honest when offline

```python
class PublishedVersionSource(Protocol):
    def latest(self, ecosystem: str, name: str) -> str | None: ...
```

| Implementation | Behaviour | Used by |
|---|---|---|
| `OfflineSource()` | always returns `None` | default posture, `--offline`, whole test suite |
| `StaticSource({(eco, name): version})` | returns the mapping, `None` if absent | tests (`AC-SBOM-17`) |
| `HttpRegistrySource(timeout=…)` | `urllib.request` GET against crates.io / npm registry / PyPI JSON; **any** exception → `None` plus a recorded `lookup_error` | Slice 33 online run only |

`run_survey(repo_root, *, published: PublishedVersionSource, …)` takes `published` as a
**required keyword-only argument with no default**. There is therefore **no code path that reaches
the network implicitly** — an online run is an explicit act of construction by the caller.
`AC-SBOM-14` proves it by monkeypatching `socket.socket` to raise for the whole survey.

**Status derivation — the safety property.** `status` is computed *only* as:

```text
latest is None                  -> "unknown"
locked is None (unpinned req)   -> "unknown"
version parse fails, either side-> "unknown"   (+ parse_error recorded)
locked == latest                -> "current"
locked <  latest                -> "outdated"
locked >  latest                -> "ahead"
```

`"current"` is reachable **only** from a successfully parsed pair on both sides. There is no
fallback, no default-to-current, and no "assume current if we could not check". A false
`up-to-date` is the single worst output this tool can produce — it would let a real advisory be
closed as `CLOSE-satisfied` in LBS §2 triage — so it is `AC-SBOM-15` (offline) and `AC-SBOM-16`
(raising source) as two separate named tests. `staleness.md` additionally prints the unknown count
in its header, so an offline run cannot be mistaken for a clean run at a glance.

**Version comparison.** `cargo` and `npm` versions are semver → `semver.Version`. `pypi` versions
are PEP 440 → `packaging.version.Version`. Mixing the two comparators is deliberate: PEP 440 rejects
`1.2.3-rc.1` and semver rejects `1.2.3.post1`, and silently coercing either would produce wrong
orderings, which lands back in the false-`current` failure mode. Unparseable → `unknown`.

### 5.5 library↔library edges — lockfiles, no subprocess

**Edges come from lockfiles; constraints and direct-ness come from manifests.**

| Ecosystem | Component + edge source | Direct-ness + constraint source |
|---|---|---|
| cargo | `Cargo.lock` — `[[package]]` `name`/`version`/`dependencies` (TOML, `tomllib`) | `[dependencies]`, `[dev-dependencies]`, `[build-dependencies]` of the 10 tracked workspace `Cargo.toml` files |
| npm | `package-lock.json` v3 — the `packages` map (`node_modules/<name>` keys → `version`, plus per-entry `dependencies`) | `dependencies`/`devDependencies`/`optionalDependencies` of the tracked `package.json` files |
| pypi (locked) | `src/python/uv.lock` — `[[package]]` `name`/`version`/`dependencies` (TOML) | `project.dependencies` + `project.optional-dependencies` of `src/python/pyproject.toml` |
| pypi (unlocked) | `tools/docs/requirements.txt` — no lock exists | the file itself; `==` pins give a locked version, anything looser yields `locked_version=None` → `status="unknown"` |

**Why lockfile parse and not `cargo metadata` / `npm ls`.** Three reasons, in order of weight:

1. **Hermeticity.** `cargo metadata` and `npm ls` need the toolchain installed, a populated
   registry cache, and frequently the network. That would make the acceptance suite non-hermetic
   and violate REQ-9 at its root.
2. **Fidelity to the question.** "What version are we *using*?" is answered by the tracked lockfile,
   by definition. A subprocess can resolve differently from the committed lock (different feature
   set, `--offline` cache state, a newer index) and would then report something the repository does
   not actually contain.
3. **Cost.** The whole point of the re-scope is a fast mechanical run; a cold `cargo metadata` on
   this workspace is minutes.

**Direct vs transitive.** `depth = "direct"` iff the package name appears in a dependency table of
at least one **tracked, non-excluded** manifest; otherwise `"transitive"`. This is exactly LBS §2's
second triage question ("*transitive bump usually moot*"), so Slice 33 filters on it.

**Honest limitation, recorded rather than papered over.** Cargo lockfile `dependencies` lists are
already feature-resolved and do not distinguish normal / dev / build edges. The tool therefore tags
lock-derived edges `fathomdb:edge-kind = "resolved"`, and only manifest-derived direct edges carry
the real `normal` / `dev` / `build` kind. An npm `package-lock` v3 `packages` key can also carry
nested `node_modules/a/node_modules/b` paths for conflicting versions; those are emitted as distinct
components with distinct `bom-ref`s, so the graph stays closed (`AC-SBOM-12`).

**`bom-ref`** is `<purl>` (e.g. `pkg:cargo/serde@1.0.219`), which is unique per (ecosystem, name,
version) and stable across runs — a prerequisite for REQ-13. Every component therefore carries a
`purl`, it equals the `bom-ref`, its type is one of `cargo` / `npm` / `pypi`, and its `@version`
segment is the component's own locked version. Schema validity does **not** imply any of this —
CycloneDX 1.6 accepts a component with only `name` + `version` — so `AC-SBOM-10` asserts it
per-component and additionally requires the document's purl-type set to be *exactly*
`{cargo, npm, pypi}`: this repo tracks manifests in all three, so a missing type means a whole
ecosystem was dropped, and a fourth type means something leaked in.

**What "closed" means here, stated so it cannot be satisfied vacuously.** The `dependencies` array
is closed in **both** directions:

1. every `dependsOn` target resolves to a declared component `bom-ref` (no dangling refs), **and**
2. every declared component appears as a `ref` entry — a leaf takes an entry with an empty
   `dependsOn`. This is CycloneDX's own guidance ("dependencies should be provided for every
   component") and it is the half that carries the weight: direction 1 alone is *trivially* true of
   an empty array, so an implementation could emit 400 components and zero edges and still be
   "closed".

Two further live-repo assertions make the graph non-vacuous (`AC-SBOM-12`):

- **At least one library→library edge** — an entry whose `ref` is a component rather than the
  `metadata.component` root, with a non-empty `dependsOn`. Without this the BOM is a flat list, and
  library↔library enumeration is a core reason this tool exists (REQ-8, §3a).
- **At least one known lockfile-only crate arrives tagged `transitive`.** The suite pins a small
  sentinel set — `proc-macro2`, `quote`, `syn`, `unicode-ident`, `serde_derive` — each present in the
  tracked `Cargo.lock` and declared by **no** dependency table of any tracked, non-excluded
  `Cargo.toml` at `cbb56212` (378 of the 410 locked crates are in that position). They can only
  reach the BOM by walking the lock's edges, so their absence proves the walk never happened. The
  assertion needs only **one** survivor, which is the drift allowance: if a future slice adopts, say,
  `syn` directly, the crate legitimately leaves the set and the other four still hold the line. If
  *all five* ever become direct, the set must be re-picked — the test says so in its failure message.

### 5.7 Named external libraries

§3a requires them named. The dependency set is kept deliberately small: this is a tool whose subject
is dependency hygiene, so a bloated dependency set would be self-refuting.

| Distribution | Constraint | What for | Why stdlib is insufficient |
|---|---|---|---|
| `cyclonedx-python-lib[json-validation]` | `>=8.0,<9.0` | Build and serialize the CycloneDX 1.6 document; the `json-validation` extra supplies the bundled normative schemas used by `AC-SBOM-10`. | CycloneDX is a versioned spec with normative JSON schemas and `bom-ref` semantics. Hand-rolling the JSON produces a document no consumer will validate, and pins us to re-implementing the schema on every spec bump. |
| `packageurl-python` | `>=0.15,<1.0` | Construct `pkg:cargo/…`, `pkg:npm/…`, `pkg:pypi/…` purls (the component identity and `bom-ref`). | purl has non-obvious encoding rules (namespaces, qualifiers, percent-encoding). Declared **direct** because the tool imports it, even though it also arrives transitively via `cyclonedx-python-lib`. |
| `packaging` | `>=24.0,<26.0` | PEP 440 version ordering for the pypi arm, and `Requirement` parsing for `requirements.txt`. | No stdlib version comparator exists. `pkg_resources` is deprecated and string comparison is wrong (`"1.10" < "1.9"`). |
| `semver` | `>=3.0,<4.0` | Semver ordering for the cargo and npm arms. | `packaging.version` rejects semver pre-release spellings such as `1.2.3-rc.1`; coercing them would silently mis-order and could produce a false `current` (§5.4). |
| `pytest` | `>=8.0,<10.0` | Test runner. **Dev-only extra**, not a runtime dependency. | — |

**Deliberately NOT taken.**

- **No HTTP client** (`requests`, `httpx`). Three GET-JSON endpoints are handled by stdlib
  `urllib.request`. Adding an HTTP stack to a dependency-hygiene tool for three calls is exactly the
  bloat this tool is meant to expose.
- **No TOML library.** Python ≥ 3.11 ships **`tomllib`** in the stdlib, which reads `Cargo.toml`,
  `Cargo.lock`, `uv.lock`, `pyproject.toml` and `tiers.toml`. `tomli`/`toml`/`tomlkit` are not
  needed. The project therefore requires **`python >= 3.11`** (the host runs 3.12.3).
- **No `jsonschema`.** The `cyclonedx-python-lib[json-validation]` extra already brings a validator
  bound to the correct schema version; a second, separately-pinned validator would drift.
- **No `GitPython`.** One `git ls-files -z` via `subprocess` is the whole git surface.
- **No `setup.py` / AST tooling** — see §5.2.

### 5.8 Forward compatibility with Slice 33 — make the consumer cheap

Slice 33 answers exactly two questions and stops: **(1)** what is actually stale, and **(2)** would
a **surgical ~1–5 SLOC** change *likely* land each upgrade — **ASCERTAIN, NEVER IMPLEMENT**.

`staleness.json` is a JSON object `{"generated": …, "source": "offline"|"http", "summary": {…},
"rows": [...]}`. Each row (`AC-SBOM-22`):

| Field | Type | Why Slice 33 needs it |
|---|---|---|
| `ecosystem` | `"cargo"｜"npm"｜"pypi"` | groups the survey |
| `name` | str | the candidate |
| `tier` | tier | `shipped` outranks `dev-tooling`; drives priority |
| `depth` | `"direct"｜"transitive"` | LBS §2: transitive bumps are usually moot |
| `locked_version` | str｜null | "what are we using" |
| `latest_version` | str｜null | "what is published" — `null` ⇒ `unknown` |
| `status` | `current｜outdated｜ahead｜unknown` | question (1), answered directly |
| `lookup_error` | str｜null | why a row is `unknown`, so §5 of the findings doc writes itself |
| `declared_in` | list of `{path, constraint, kind}` | which tracked manifests declare it, with the range and `normal`/`dev`/`build` |
| `edit_sites` | list of str | **the input to question (2)** — the exact manifest paths a bump must touch |
| `edit_site_count` | int | a one-line proxy for "surgical?": one version string per site |

Question (2) is a **judgement** — a major with an API break is not surgical even at one edit site.
The tool supplies the *inputs* (`edit_site_count`, `depth`, the constraint strings) and states no
verdict. **No part of Slice 33 is built here.**

**Determinism (REQ-13).** Rows are sorted by `(tier, ecosystem, name, locked_version)`; JSON is
written with sorted keys and a trailing newline; the CycloneDX `serialNumber` is a **UUIDv5 over the
sorted `bom-ref` set** (not `uuid4`), and `metadata.timestamp` comes from `SOURCE_DATE_EPOCH` or an
explicit `--now`, defaulting to a fixed epoch rather than wall-clock. A re-run therefore diffs to
nothing when nothing changed — which is what makes this a *recurring* tool rather than a one-off.

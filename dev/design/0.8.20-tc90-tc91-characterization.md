## 1. TC-90 — the claim, and what the code actually says

### 1.1 The shape IS there — PROVEN

`Engine::transition` (`lib.rs:8190`):

```rust
lib.rs:8221   let tx = connection.transaction().map_err(|_| EngineError::Storage)?;   // BEGIN DEFERRED
lib.rs:8227   let current: Option<(String, i64, String)> = tx
lib.rs:8228       .query_row(
lib.rs:8229           "SELECT state, write_cursor, body FROM canonical_nodes \
lib.rs:8230            WHERE logical_id = ?1 AND superseded_at IS NULL",              // READ  -> read lock
                      ...
lib.rs:8258   tx.execute(
lib.rs:8259       "UPDATE canonical_nodes SET state = ?1, reason = ?2 \
lib.rs:8260        WHERE logical_id = ?3 AND superseded_at IS NULL",                  // WRITE -> PROMOTE
```

`connection.transaction()` is rusqlite's `TransactionBehavior::Deferred`. The first statement in
the transaction is a **SELECT**, the second is an **UPDATE**. That is structurally identical to
`commit_batch`'s pre-TC-57-fix shape. **The ledger claim is correct on the code.**

### 1.2 What TC-90 has that TC-57 did not — and why it matters

Two mitigations exist at this call site and at no equivalent point in `commit_batch`:

1. **`lib.rs:8217` — `self.drain(LIFECYCLE_DRAIN_TIMEOUT_MS)?`** before the transaction is
   opened. `wait_for_idle` (`lib.rs:1246-1273`) requires `active_jobs == 0 && queued_jobs == 0`
   **and** the on-disk `database_has_pending_projection_work` predicate to be false. So at the
   instant `drain` returns, no worker commit is in flight and none is pending.
2. **`lib.rs:8219` — `self.connection.lock()`.** `write_inner` takes the **same** mutex
   (`lib.rs:5051`), so while `transition` holds its transaction open no in-process
   `Engine::write` can commit, and therefore no new projection job can be enqueued.

Consequently the in-process race window is **not** "the whole transaction", as it was for
TC-57. It is the **gap between `drain` returning and the connection mutex being acquired**: a
competing `Engine::write` that wins the mutex in that gap commits, wakes the dispatcher, and can
have a worker holding the WAL write lock by the time `transition` promotes.

That window is narrow, and its width is governed by one thing above all: **how long after the
competing write's commit the worker reaches its own commit** — i.e. the embed latency.

## 2. Repro protocol — TC-90

### 2.1 Commands

From the repository root. All four **loop** arms are `#[ignore]`d at baseline (they are
measurements, not merge-gate invariants, and `cargo test --workspace` is not a stable signal for
concurrency tests — ledger TC-72), hence `--ignored`. The three `tc90_mechanism_*` pins are
**not** ignored; §3.4 states that decision and its evidence.

**What every arm asserts before it measures anything** (`assert_protocol_ran`). The first draft
of the stress arms asserted only `attempted > 0`, which is far too weak for the protocol this
section documents: a run that issued **one** transition, or truncated at its wall-clock budget,
or was dominated by `Scheduler` drain timeouts, would have satisfied §4's green bar without ever
measuring the 40-transition promote race. All four arms now pin the whole protocol —
`attempted == transitions`, `truncated == false`, `competing_writes > 0`,
`scheduler_errors == 0`, `other_errors == 0` — plus their own independent variable
(`embed_calls > 0` on repro arms, `== 0` on controls). **An acceptance bar is only as good as
what it refuses to accept.**

A consequence worth stating: `ArmConfig::budget` is now a **safety valve whose use is a
failure**, not a licence to measure less. An arm that hits it has not run the protocol and says
so loudly.

### 2.3 What the arms hold constant

Within each pairing the **only** difference is `Engine::configure_vector_kind_for_test("doc")`
— i.e. whether the projection worker ever produces a `Success` outcome and therefore whether a
**second writer exists at all**. Embedder, seed rows, competing-write threads, burst size,
pacing, transition loop and subject set are identical. This is the same isolation TC-57 §4.2
performed.

**Non-vacuity, both directions.** Every arm asserts the state of its own independent variable
rather than assuming it: repro arms assert `embed_calls > 0` (a second writer *did* exist),
control arms assert `embed_calls == 0` (it did *not*), and all four run
`assert_protocol_ran` (§2.1) for the rest. A run in which the worker never ran cannot report a
clean pass for the wrong reason; a control that silently lost its load cannot masquerade as a
clean comparison; and an arm that measured 1 transition instead of 40, or spent the run in drain
timeouts, now fails instead of passing quietly.

**One harness detail that is load-bearing, not cosmetic.** The loop tracks each subject's state
from **observed outcomes**, never from the loop index. A failed `transition` rolls back, so the
subject keeps its previous state; deriving the next target from the index would then aim a flip
at the state the row is already in — a self-loop, correctly refused with `IllegalTransition`.
That refusal is a **cascade artifact of the harness**, and in the first draft of this
measurement it contaminated the very counter under test (an early run reported
`storage_errors=1 other_errors=1`, where the second was pure artifact). Advancing only on
success removes it; `other_error_kinds` is reported so a future recurrence is visible rather
than silent.

### 2.4 The negative that was nearly filed — read this before trusting any 0/10

The paced arm is the direct analogue of TC-57's repro: one writer, one row per write, 3 ms
pacing, 2 ms embed. It is **0/10**, 1200 transitions, with a live worker and ~175 embeds per run.

It does not reproduce because of arithmetic, not luck. The worker cannot hold the write lock
until *at least* one embed latency after the competing write released the connection mutex,
whereas `transition` travels from acquiring that same mutex to its promoting `UPDATE` in
microseconds. At a 2 ms embed the worker is simply never there yet.

Setting the embed delay to **0 ms** — plus a burst larger than `PROJECTION_COMMIT_BATCH` (16),
so the worker's commit transaction is as long as it ever gets, and two writer threads matching
`PROJECTION_WORKERS` — collapses that offset and the defect appears **10/10**.

> **The general lesson, for the next agent to characterize a concurrency defect here: a 0/10 at
> one load shape is not evidence of absence.** Name the parameter that governs the window and
> vary *that*, or do not report a negative.

### 2.5 A second, distinct finding: `transition` becomes UNAVAILABLE under saturating load

**MEASURED — `Engine::transition` only.** The first stress attempt used `writer_pace_ms: 0`
(fully saturating, 2 threads × 24-row bursts). In **181 seconds** the loop issued **5**
transitions, of which **4 failed with `EngineError::Scheduler`** — each having burned the full
`LIFECYCLE_DRAIN_TIMEOUT_MS` (30 s) because `transition`'s own `drain` never reached idle.
596,928 competing rows landed in that window.

This is **not** the promote race. It is a separate availability property of the
drain-then-act design: under sustained write pressure a lifecycle verb can be starved
indefinitely, one 30-second timeout at a time, and the caller sees an opaque
`EngineError::Scheduler`.

> **PRESUMED, NOT MEASURED — the three sibling call sites.** `configure_projections`
> (`lib.rs:8332`), `purge` (`lib.rs:8441`, `8443`) and the verb at `lib.rs:8646-8648` take the
> same `drain`-first path **by code reading**. **No arm in this slice exercised any of them.**
> Nothing here is evidence about their behaviour under load; the shared shape is a reason to
> triage them, not a characterization of them. Whoever picks this up measures them — they do not
> inherit the `transition` numbers above.

Recorded here because it was found; **out of scope for a fix in this slice**, and it should be
triaged separately rather than folded into a TC-90 fix. See §8 "What I am unsure about" item 2 —
this may well be the more important defect of the two.

The measured arms therefore use `writer_pace_ms: 1`, which is near-saturating but still lets
`drain` reach idle — hence `scheduler_errors == 0` across all 10 stress runs.

## 3. Mechanism — what SQLite ACTUALLY returns

### 3.1 The error is not merely opaque here — it is never produced

`transition` maps every rusqlite error through `.map_err(|_| EngineError::Storage)` and, unlike
`write_inner` (which at least calls `emit_sqlite_internal_error`, `lib.rs:5097`), **emits no
lifecycle event at all**. `EngineError::Storage` is a unit variant with no payload and no
`source()`. So on this path the numeric code is not just unrecoverable through the public API —
it is never emitted to anything, including a subscriber. TC-57's harness could at least capture
`"SQLITE_BUSY"` from the lifecycle sink; this one cannot.

The mechanism is therefore pinned **deterministically** instead, by *holding* the write lock
from a second connection rather than racing for it. All three pins below are **not**
`#[ignore]`d: they assert what SQLite does, and they pass at baseline.

### 3.2 Pin 1 — `transition`'s own SQL, on a real `canonical_nodes`

`tc90_mechanism_transition_sql_shape_on_real_schema_is_busy_5` builds a real engine database,
seeds one governed `active` row, closes it, and then replays the two statements **copied
character-for-character** from `lib.rs:8229-8230` and `lib.rs:8259-8260` on a connection that
has a 5 s busy timeout **and** a counting busy handler installed, while a second connection
holds the write lock uncommitted.

```text
TC90-MECH sql_shape primary=DatabaseBusy extended=5 handler_calls=0 elapsed_ms=0
```

| observable | measured |
|---|---|
| primary code | `DatabaseBusy` |
| **extended code** | **5** — plain `SQLITE_BUSY`, **not** `SQLITE_BUSY_SNAPSHOT` (517) |
| **busy-handler invocations** | **0** |
| wall time | **0 ms**, against a 5 000 ms timeout |

This is TC-57's **Exit B**, exactly. SQLite skips the busy handler when promoting a read
transaction, by design — per the `sqlite3_busy_handler` documentation, *"if SQLite determines
that invoking the busy handler could result in a deadlock, it will go ahead and return
SQLITE_BUSY"*. **No `busy_timeout` value could ever retry this**, and the handler is instrumented
to always request a retry so "called zero times" cannot be explained away.

§0 of the TC-57 characterization exists because every prior write-up named 517. This measurement
says the same thing about TC-90 that TC-57's did about `commit_batch`: **a fix scoped to
retrying 517 would ship inert.**

**Is 517 reachable here?** Not observed in any run. It requires the worker to *commit* inside
the microseconds between `transition`'s SELECT and its UPDATE, whereas Exit B only requires the
worker to be *holding* the lock at that instant. Treated as **reachable-but-unobserved**, same
as TC-57 §2.4. A fix must cover both.

### 3.3 Pins 2 and 3 — and the answer to "does `BEGIN IMMEDIATE` transfer?"

The brief's standing instruction was not to assume TC-57's remedy transfers. It was measured.
Both pins apply the **identical** contention — one external connection holding the WAL write
lock — and differ only in which engine entry point is called.

| pin | engine call | transaction behaviour | result | wall time |
|---|---|---|---|---|
| 2 | `Engine::transition` | `BEGIN DEFERRED`, read-then-upgrade (`lib.rs:8221`) | **`Err(Storage)`** | **0 ms** |
| 3 | `Engine::write` | `BEGIN IMMEDIATE` (`lib.rs:18637`, the TC-57 fix) | **`Ok`** | **834 ms** |

Pin 3's blocker holds the lock for 900 ms and then releases. The writer **waited** for it and
then succeeded — which is the positive proof that the busy handler *was* consulted on that path,
in direct contrast to pin 1's zero invocations on the promoting path.

**So the answer is: yes, empirically, on this engine, at this baseline.** The remedy is not
being transferred by analogy — the very same database, the very same contention, and the very
same 5 000 ms default busy timeout produce a hard 0 ms failure for the DEFERRED promoting
transaction and a successful 834 ms wait for the `IMMEDIATE` one. That is as direct as this
evidence gets without implementing anything.

**What it does NOT establish** is listed in §8. In particular it says nothing about throughput,
nothing about `transition`'s interaction with its own preceding `drain`, and nothing about the
worker side — which §5 shows is the *other* half of the same problem and which an `IMMEDIATE`
`transition` would make **worse**, not better.

### 3.4 Test profile — exactly which of these targets run in the default gate, and why

This slice adds **13 test functions across two targets. 9 are `#[ignore]`d; 4 run in the default
`cargo test` profile.** The decision was taken per target, not by reflex, and the gating question
is ledger **TC-72**: roughly 1 workspace run in 3 already fails on plain `main`, so anything
timing-sensitive added to the default profile makes that worse and has to earn its place.

| target | default profile | why |
|---|---|---|
| the 4 `tc90_*` loop arms | **`#[ignore]`d** | race a live worker against live writer threads; results are RATES, and §2.2 shows the per-run count is not even stable session to session |
| the 5 `tc91_*` concurrency arms | **`#[ignore]`d** | same — live worker vs live writer, measured rates |
| `tc90_mechanism_transition_sql_shape_on_real_schema_is_busy_5` | **LIVE** | two connections, **one thread**, no sleeps; the lock is HELD, not raced |
| `tc90_mechanism_engine_transition_under_held_write_lock_fails_immediately` | **LIVE** | blocker held on the calling thread; no outstanding `drain` work |
| `tc90_mechanism_control_engine_write_under_held_write_lock_survives` | **LIVE** | the one target with a thread — see below |
| `tc91_probe_embed_cost_per_open_at_head` | **LIVE** | sequential; 3 opens, 1 write, every `drain` awaited; no thread, no wall-clock assertion |

Running the mechanism pins live is the same posture TC-57's own `tc57_mechanism_*` pins have.
None of them races for anything: the contending write lock is **taken and held** by a second
connection across the whole measured call, so the outcome is decided by SQLite's documented
promotion behaviour rather than by scheduling.

The one deliberate call is **pin 3**, the only target here that spawns a thread. Its assertions
are one-sided bounds with large margins, and the margins were **measured, not asserted from the
armchair — 20 consecutive default-profile runs**:

| observable | assertion | measured across 20 runs | margin |
|---|---|---|---|
| `Engine::write` succeeds | `is_ok()` | ok in 20/20 | blocker holds 900 ms against a 5 000 ms busy timeout ⇒ ~4.1 s slack |
| it WAITED for the lock | `>= 450 ms` | **832–838 ms** (spread of **6 ms**) | the holder *sleeps* 900 ms, so an early release is impossible by construction |

Pin 3 is kept live because it is the load-bearing evidence that TC-57's R1 remedy transfers
(§3.3), and a 0.8.21 fix scoped against **R-A** would otherwise be reasoning from a test nobody
runs. **If it ever does flake, gate it — do not widen the bound**, which is the assertion that
makes it mean anything.

`tc91_probe_embed_cost_per_open_at_head` is a **measurement** and is nonetheless live, which is
the one place the "characterization arms are all gated" shorthand does not hold. That is
deliberate: since §5.2 it pins `0 / 90 / 0` **exactly**, and gating it would put the corrected
figure this document publishes behind a flag nobody runs. It measured identically in **20/20**
default-profile runs.

## 5. TC-91 — the duplicate embeds and the discarded worker commit

### 5.1 The measurement trap, disarmed FIRST

`run_vector_equivalence_probe` (`lib.rs:15309`) embeds the 45-probe fixture at **open**. Two
figures are on the record and **both are true, of different opens** — 90 on the population open,
45 on every open thereafter. Ledger `seq-125` (the TC-71 close) states the consequence plainly:
*absolute embed counts are unusable as an oracle across a reopen*; every embed assertion must be
a **delta from a post-open snapshot**.

Two separate defences are used here, and both are **verified rather than assumed**:

- **Single-open measurement.** Every duplicate arm runs in one open of a fresh workspace whose
  embed log starts empty. `_fathomdb_vector_kinds` is empty at open, so the probe returns early
  (`lib.rs:15348-15353`) having embedded nothing; the kind is enrolled *after* open.
- **Text-level separation.** Every body this fixture writes carries the marker `tc91marker`,
  which no probe text contains. Ingest and probe embeds are counted **separately and never
  summed**, and **every duplicate arm asserts `probe_calls == 0`** — so if the separation ever
  breaks, the arm fails rather than quietly reporting a contaminated number.

### 5.2 The probe's cost at HEAD — the ledger figure is STALE

`tc91_probe_embed_cost_per_open_at_head` (not `#[ignore]`d; deterministic and fast) measures
three consecutive opens of one workspace as deltas:

```text
TC91-PROBE open1_no_vector_kind=0 open2_populate_then_check=90 open3_after_tc68_cache=0
```

| open | state | probe embeds |
|---|---|---|
| 1 | fresh workspace, no vector kind registered | **0** |
| 2 | vector kind present, `_fathomdb_embed_probe` empty ⇒ populate 45 + check 45 | **90** |
| 3 | probe table populated, TC-68 fingerprint verdict cache live | **0** |

**TC-68 landed in Slice 22 (`572475f2`) and took the steady-state reopen probe cost to zero, not
merely reduced it.** The ledger note describing the 45 re-embeds as something TC-68 "is
scheduled to cache away" predates that landing and is now stale: **do not inherit 45 as a
constant for any open after the population open.** The 90 on the population open is unchanged
and still must be subtracted.

**All three opens are asserted EXACTLY** — `open1 == 0`, `open2 == 90`, `open3 == 0` — and
measured identically in **20/20** runs, with zero variance. The first draft asserted only
`open3 < open2`, on the reasoning that the load-bearing property was "the cache works" and an
exact pin would make an unrelated fingerprint change look like a defect. **That was wrong, and
it is worth saying why**, because it is the same error in miniature that §0 of the TC-57
document warns about: this section does not merely observe a property, it **publishes a
correction** to a figure other agents subtract. Under `open3 < open2`, a regression back to 45
would have passed silently (`45 < 90`) while this document still said **0**. A wrong correction
is worse than the stale figure it replaces.

The exact pins are also not fragile in the way that reasoning assumed. `90 = 45 + 45` is
`PROBE_FIXTURE_SIZE * 2`, derived from the **checked-in** `vector_equivalence_probes.txt`, so it
has no run-to-run variance at all — only a deliberate fixture edit moves it, and such an edit
*should* be forced to update the figure quoted here. The test's failure text says so.

If `open3 == 0` ever fails, the "45 every open" figure is live again and every embed oracle in
the repo must re-subtract it.

### 5.3 (a) The baseline duplicate rate — MEASURED, both arms

**Definition of "duplicate" used throughout:** every row this fixture writes carries a **unique**
body, and the embedder records the exact `text` of every `embed()` call. `ingest_duplicates` is
the number of embed calls **beyond the first** for any single text. A text embedded twice is a
row that was dispatched twice — i.e. a projection outcome that was computed and then never
became durable. This is a count, not an inference from a total.

Protocol: 200 single-row `Engine::write` calls 1 ms apart, live 1 ms embedder, `doc` enrolled as
a vector kind, `drain`, then count. N = 10 per arm.

```bash
for arm in tc91_duplicate_embed_rate_governed tc91_duplicate_embed_rate_anonymous; do
  f=0
  for i in $(seq 1 10); do
    cargo test -p fathomdb-engine --test tc91_duplicate_embeds_and_silent_commit_loss -- \
      --ignored --exact --nocapture "$arm" > "/tmp/${arm}_$i.log" 2>&1
    rc=$?
    if [ "$rc" -ne 0 ]; then f=$((f+1)); fi
  done
  echo "FAILURES $arm: $f/10"
done
```

| arm | runs | duplicates / 200 rows | rate | probe contribution |
|---|---|---|---|---|
| governed (`logical_id: Some`) | 10 | 102–106, mean **104.0** | **52.0 %** | **0** |
| anonymous (`logical_id: None`) | 10 | 103–110, mean **105.0** | **52.5 %** | **0** |

In all 20 runs: `ingest_distinct == 200`, `vector_rows == 200`, `up_to_date_terminals == 200`,
`failed_terminals == 0`, `failure_audit_rows == 0`, `drain_ok == true`.

**The ledger claim is confirmed in full.** The rate is ~52 %, it is **indistinguishable between
the governed and anonymous arms** (0.5 pp apart, inside run-to-run spread), and the anonymous
arm has no read-then-upgrade window at all — so it is **not** the governed-write race TC-57
fixed. Harm class is exactly as filed: **wasted embed work**, invisible to every correctness
test, because a duplicate embed produces the right answer twice.

### 5.4 (b) The silently discarded worker commit — the call site, and the proof of BLINDNESS

```text
lib.rs:12711   let _ = commit_projection_outcomes(connection, &outcomes, shared);   // run_projection_jobs
lib.rs:12824   let _ = commit_projection_outcomes(connection, &outcomes, shared);   // commit_projection_panic_failures
```

Both discard a `rusqlite::Result<()>`. No error, no log, no telemetry, no counter.

**The durable point — state it once, plainly, because it invalidates a whole class of future
measurement.** A `'failed'` terminal and a `projection_failures` audit row are written by the
`ProjectionOutcome::Failure` arm (`lib.rs:13962-13984`), which represents an **embed** failure. A
**commit** failure never reaches that arm at all: the transaction rolls back, the row keeps
`terminal IS NULL`, the worker loop sets `pending_scan = true` (`lib.rs:12663`), the dispatcher
re-fetches the row and it is embedded again.

> **Counting `'failed'` terminal states is STRUCTURALLY INCAPABLE of seeing this failure class.**
> The failure never reaches a terminal state at all. Any future attempt to quantify worker
> reliability by counting failed terminals — or `projection_failures` rows — will report a
> **falsely clean zero**, no matter how many commits are being lost, until this is fixed.

**Forced-failure experiment.** `tc91_forced_commit_failure_is_invisible_to_terminal_counting`
writes one 96-row governed batch with a 15 ms embedder, then takes and **holds** the WAL write
lock from an ordinary second connection (`BEGIN IMMEDIATE`) for 1 500 ms. That is precisely the
contention §3.2 characterizes, applied in the opposite direction: `commit_projection_outcomes`
(`lib.rs:13809`) opens rusqlite's DEFERRED default and reads (`lib.rs:13813`, `lib.rs:13828`)
before it writes (`lib.rs:13863`), so its promotion is refused and `let _ =` throws the outcome
away.

| observable | blocked arm (N=10) | unblocked control (N=10) |
|---|---|---|
| duplicate embeds / 96 rows | 80–96, mean **86.4** (**90 %**) | **0** |
| distinct rows re-embedded | **32** in every run | 0 |
| **`'failed'` terminals** | **0** | **0** |
| **`projection_failures` rows** | **0** | **0** |
| `up_to_date` terminals | 96 | 96 |
| `vector_rows` | 96 | 96 |
| `drain` reached idle | 10/10 | 10/10 |

Both arms passed 10/10 — because the test **asserts the blindness**: it requires the two
counters to stay at **zero** while the re-embed count is **non-zero**. A green run therefore
means *real work was computed, thrown away and recomputed, and the terminal-state census
reported a perfectly clean run.* The control's job is to show the same two counters read zero
for the **ordinary** reason (nothing failed) — which is exactly why they cannot discriminate,
and exactly why a future agent must not use them.

Note also: **`vector_rows == 96` in the blocked arm.** This is a **wasted-work / observability**
defect, not data loss. The system self-heals; it just does so silently and at up to double the
embed cost.

### 5.5 The mechanism — what is MEASURED, and where the evidence structurally stops

`tc91_mechanism_duplicate_rate_versus_write_cadence` runs the same 60 governed rows twice,
varying **only** the spacing between `Engine::write` calls.

| arm | write spacing | runs | duplicates / 60 |
|---|---|---|---|
| tight | 1 ms | 10 | 31–33, mean **32.5** (**54.2 %**) |
| spaced | 25 ms | 10 | **0** in all 10 |

#### 5.5.1 MEASURED — two results, and they are the deliverable

1. **The duplicate rate is CADENCE-SENSITIVE under this 1 ms embed / 1 ms write shape.** 32.5/60
   at 1 ms spacing; **exactly 0/60 at 25 ms**, 10/10; and **0/96** for the §5.4 control, one
   batch with no concurrent writer. So the ~50 % is a property of the write **cadence**, not a
   constant of the scheduler, and **quoting "~50 %" without the cadence it was measured at is
   not meaningful.**
2. **An externally held WAL write lock makes discarded worker commits INVISIBLE.** §5.4: 86.4/96
   duplicate embeds while `'failed'` terminals and `projection_failures` rows both read **zero**,
   in all 10 runs.

#### 5.5.2 HYPOTHESIS — strongly implicated, NOT confirmed

The tempting third claim is *"TC-91 (a) **is** TC-91 (b)"* — that a duplicate **requires** a
second writer holding the WAL write lock across the worker's commit, and that the engine's own
writer is that holder in the baseline arms. An earlier draft of this document stated it flatly.
**It is not proven, and it must be carried forward as a hypothesis with its gap named** (codex
§9 round 4).

The reason it cannot be closed here is worth stating precisely, because it is not an oversight
in the harness — it is a property of the defect:

> **There is NO direct instrumentation of worker commit failures in the baseline duplicate arms,
> because the defect under study is precisely that those failures are discarded** by
> `let _ = commit_projection_outcomes(..)` (`lib.rs:12711`, `lib.rs:12824`). Every counter that
> could confirm the mechanism at baseline is the counter §5.4 proves is structurally blind.
> **TC-91 (b) is the reason TC-91 (a) cannot be closed by measurement.**

So what the two results above jointly support is: *removing writer/worker overlap removes the
duplicates, and forcing that overlap externally reproduces them at ~90 % while the failure stays
invisible.* What they do **not** support is that this is the only route to a duplicate, or that
every one of the ~104/200 baseline duplicates arose this way. The forced-lock arm supplies the
lock holder **externally**; it demonstrates the mechanism and the observability blind spot, but
it cannot attribute the baseline population.

The supporting code reading is real and points the same way — `commit_batch` holds
`BEGIN IMMEDIATE` (`lib.rs:18637`, the TC-57 fix) for the duration of every write, while
`commit_projection_outcomes` (`lib.rs:13809`) is a DEFERRED read-then-upgrade, so an overlap
refuses the worker's promotion with plain `SQLITE_BUSY` and `let _ =` throws the outcome away.
But it is a **reading**, and §0 of the TC-57 characterization is the standing warning about
confident readings on this exact code path: every prior write-up named 517, and a fix scoped
against it would have shipped inert. **Do not scope a 0.8.21 fix against an identity claim this
slice did not establish.**

#### 5.5.3 What would close it

**R-C** (§7 — stop discarding the worker commit result) converts the hypothesis into a
measurement: with a counter on the discarded commit, the baseline duplicate arms would show
directly whether each duplicate was preceded by a refused promotion, and no forced-lock proxy
would be needed. That is the principal reason R-C is recommended to land **first**.

#### 5.5.4 What this does say about TC-57 §7 uncertainty 3

TC-57 §8.2 measured worker-side pressure *relatively* — before vs after the caller-side fix —
found no increase, and correctly declined to act. What it could not see, having no
no-concurrency baseline to compare against, is that the ~104/200 it recorded as "pre-existing"
was **already a defect** rather than a floor. §5.3's absolute baseline plus §5.5.1's zero at
25 ms spacing supplies that comparison. This narrows TC-57's uncertainty 3 rather than closing
it, on the same evidentiary limit as §5.5.2.

### 5.6 Acceptance bar for the TC-91 fix at 0.8.21

1. Remove the `#[ignore]` attributes from the TC-91 measurement arms as a RED→GREEN step.
2. `tc91_duplicate_embed_rate_governed` and `_anonymous`: **0 duplicates / 200 rows** (were
   ~104 and ~105).
3. `tc91_mechanism_duplicate_rate_versus_write_cadence`: **tight arm 0**, spaced arm 0
   (unchanged). Because the fix must remove the *cadence sensitivity*, not merely shift it, the
   tight arm is the load-bearing assertion here.
4. `tc91_control_unblocked_worker_commits`: unchanged at 0 duplicates.
5. **`tc91_forced_commit_failure_is_invisible_to_terminal_counting` must be RE-READ, NOT
   RE-RUN.** Its assertions encode the *defect*: they require `failed_terminals == 0` while
   duplicates are non-zero. A fix that surfaces lost commits will make it fail, and that failure
   is the **success signal**. Whoever lands the fix must rewrite this test to assert the new
   contract (a lost commit is observable) and must say so explicitly in the commit message. It
   is deliberately worded that way in the test's own failure text so this cannot be missed.
6. `tc91_probe_embed_cost_per_open_at_head` stays green and unmodified, including its exact
   `0 / 90 / 0` pins. It runs in the default profile, so a regression surfaces without `--ignored`.
7. Non-vacuity must survive: `ingest_distinct == rows` and `vector_rows == rows` in every arm.
   A "fix" that reduces duplicates by dropping rows is a regression, and these assertions are
   what catch it. `probe_calls == 0` likewise — a duplicate count contaminated by probe embeds is
   not a duplicate count.
8. **Whoever lands this must resolve §5.5.2's hypothesis rather than inherit it.** If R-C lands
   first (as §7 recommends), the instrumentation exists to say directly whether each baseline
   duplicate followed a refused promotion — so *report that*, and correct §5.5 in either
   direction. Do not carry "(a) is (b)" forward as though this slice had established it.

## 6. What this characterization did NOT establish

Stated separately from §8 because these are gaps in the *measurement*, not open design
questions.

1. **Multi-process contention.** Every arm here is in-process. `transition`'s connection-mutex
   mitigation (§1.2) does nothing against a second OS process on the same file, and the drain
   mitigation does nothing about *that* process's workers. The exposure is presumed strictly
   worse and was **not measured**.
2. **The other `drain`-first verbs.** `configure_projections`, `purge` and the verb at
   `lib.rs:8646` share `transition`'s shape **by code reading** and are presumed to share both
   TC-90 and the §2.5 starvation. **No arm exercised any of them — NOT MEASURED.** They do not
   inherit `transition`'s numbers.
3. **Whether 517 is reachable from `transition`.** Never observed; not proven unreachable.
4. **Edge bodies.** `edge_fact` jobs are exempted from the no-embedder `Deferred` return, so an
   embedder-less deployment writing edge bodies is a second route to a concurrent worker commit.
   Flagged in TC-57 §4.2, still **not characterized**.
5. **Any throughput number.** No arm here measures the cost of a candidate remedy.
6. **That TC-91 (a) IS TC-91 (b).** §5.5.2. The cadence sensitivity and the observability
   blindness are measured; the identity is a hypothesis, and the reason it could not be closed is
   that the discarded-commit defect destroys the only signal that would confirm it. **This is the
   single most important line in this section** — it is the one an 0.8.21 fix is most likely to
   scope against by mistake.
7. **That the per-run TC-90 failure count is ~14.8 %.** §2.2: two sessions on the same commit and
   machine gave means of 5.9 and 3.8. **The 10/10 reproduction rate replicated; the rate did
   not.** Quote 1–10 failures per 40 transitions, or quote nothing.

## 7. Candidate remedies — enumerated, NONE implemented

Per `seq-136` nothing below was built. The style follows TC-57 §7.

### R-A — `BEGIN IMMEDIATE` for `Engine::transition`

`lib.rs:8221` becomes `transaction_with_behavior(TransactionBehavior::Immediate)`.

- **Pro:** removes the promotion by construction — closes both Exit A and Exit B. One line.
- **Pro:** **measured to work under the exact contention**, via pin 3 (§3.3): the engine's
  already-`IMMEDIATE` writer survives what kills `transition` in 0 ms.
- **Pro:** consistent with the shipped `commit_batch` remedy; makes the *whole* engine writer
  path `IMMEDIATE` rather than one path of two.
- **Con — the direction is measured, the magnitude is not:** it makes the engine the lock holder
  **more often**, and §5.5.1 measured that writer/worker overlap is exactly what drives the
  duplicate rate (0 at 25 ms spacing, 32.5/60 at 1 ms). So R-A could reduce TC-90 caller errors
  while **increasing** TC-91 (a) duplicates. TC-57 §8.2 measured no increase from the analogous
  change, but it had no absolute baseline; §5.3 now supplies one. **This must be re-measured, not
  assumed** — see §4 bar item 7. Note that **R-A and R-B point in opposite directions on TC-91**;
  see R-B's *Interaction* bullet.
- **Con:** `transition` already holds the connection mutex plus a completed `drain`; adding a
  third serialisation may be redundant for the in-process case and only buy the multi-process
  case (§6.1) — which is real, but unmeasured.

### R-B — `BEGIN IMMEDIATE` for `commit_projection_outcomes` (the worker side)

`lib.rs:13809` becomes `transaction_with_behavior(Immediate)`.

- **Pro:** this is the one that targets **TC-91 (b) directly, and (a) if §5.5.2's hypothesis
  holds**. A worker that takes the write lock at `BEGIN` goes through the busy handler instead
  (pin 3's measured behaviour) and waits, absorbing the contention within the existing 5 000 ms
  default rather than losing the outcome. Note the conditional: §5.5.2 did **not** establish that
  every baseline duplicate traces to a refused worker promotion, so R-B's effect on the ~104/200
  is predicted, not measured. Landing R-C first is what turns that prediction into a reading.
- **Pro:** it also makes the `lib.rs:8205-8216` and `lib.rs:8327+` comments true as *originally*
  written — those comments claimed the worker used `BEGIN IMMEDIATE`; TC-57 §5 proved them false
  and Slice 21a-2 corrected the prose rather than the code.
- **Con:** the worker now holds the write lock across its whole commit, including the mean-vec
  read and the per-row `terminal_state_for_cursor` checks. Under a live writer this serialises
  the two more strongly; throughput **not measured**.
- **Con:** `commit_gate` (`lib.rs:13808`) already serialises workers against each other, so this
  changes only worker-vs-engine. That is the axis that matters, but it means the change is not
  as small as it looks — it interacts with the gate's ordering guarantees for the at-pin
  re-quantize.
- **Interaction:** R-A and R-B point in **opposite** directions on TC-91. R-A alone plausibly
  makes duplicates worse. R-B alone fixes duplicates and does nothing for TC-90. **Doing both is
  the combination that is coherent**, and it is the combination whose throughput nobody has
  measured.

### R-C — stop discarding the worker commit result

Replace `let _ = commit_projection_outcomes(..)` (`lib.rs:12711`, `lib.rs:12824`) with something
that at minimum emits a lifecycle event and increments a counter, and ideally records a distinct
non-terminal audit row.

- **Pro:** it is the **observability** half, and it is independently valuable regardless of which
  locking remedy lands. Without it, "how reliable is the projection worker?" is unanswerable —
  §5.4 shows the only counters that exist report zero by construction.
- **Pro:** strictly additive; changes no transaction semantics; cannot regress TC-90.
- **Pro:** it is what makes any *future* claim about worker reliability checkable at all. This
  characterization needed a forced-failure experiment and a unique-body embed census to see
  something the engine should simply have reported.
- **Con:** requires deciding what a lost commit *is* in the taxonomy — it is not an embed
  failure and it must not be recorded as one (that would corrupt the `projection_failures`
  contract, and `dev/design/errors.md` is locked). A new observable, not a reuse of an old one.
- **Con:** must not turn a transient, self-healing loss into a hard failure. The row genuinely
  does get re-embedded and does land; making this fatal would be a regression.
- **Recommended to land FIRST**, before either locking remedy, precisely so R-A/R-B can be
  measured against something other than a re-embed census assembled by hand.

### R-D — retry the worker commit in place

Wrap the `commit_projection_outcomes` call in a bounded retry on the busy codes.

- **Pro:** contained; no transaction-semantics change; would eliminate most duplicates.
- **Con:** it is the **symptom**. The transaction still promotes; the window still exists; an
  unlucky worker still loses outcomes after the retry budget.
- **Con:** the embed has already been paid for by the time the commit is attempted, so a retry
  is cheap here — which makes this *more* attractive than R2 was for TC-57, where a retry re-ran
  the whole batch. Worth noting as a genuine asymmetry.
- **Con:** needs R-C first to know whether the retry budget is ever exhausted.

### R-E — TC-57's **R2**, bounded retry on the busy codes in the caller path

**Carried forward, unchanged in priority.** TC-57 §7 R2 remains **unimplemented**, pending the
error-path restructuring it depends on (`commit_batch`'s `rusqlite::Error` is discarded at
`lib.rs:5096-5099`, so there is nothing to branch on). R1 shipped and closed the measured defect,
so **R2 is an option, not an obligation** (TC-57 §8.4).

TC-90 does not change that verdict, but it does add one data point: `transition`'s error path is
**worse** than `commit_batch`'s (§3.1 — no lifecycle event at all, not merely an opaque
variant), so if the error-path restructuring is ever undertaken, `transition` should be included
in its scope. **Lower priority than R-A/R-B/R-C. Not recommended for 0.8.21 on its own.**

### R-F — `PRAGMA busy_timeout`

Closed out for completeness: **proven inert** (§3.2 — handler invoked 0 times; a 5 000 ms default
is already present). **Reject.**

### Recommendation

**R-C first** (observability, additive, cannot regress anything, and — per §5.5.3 — it is what
converts §5.5.2's hypothesis into a measurement, so everything after it can be judged on
evidence rather than prediction), then **R-B** (the remedy aimed at the mechanism §5.5.1
measured), then **R-A** with the §4 bar item 7 re-measurement in place to catch the interaction.
R-D only if R-C shows residual loss after R-B. R-E stays parked. R-F rejected.

**This ordering is an ENUMERATION, not a schedule, and nothing in it was implemented**
(`seq-136`). It is also not independent of the open question: if R-C's instrumentation refutes
§5.5.2, R-B's priority changes. Re-derive the order from what R-C reports; do not inherit it.

### What I am unsure about

1. **Whether TC-91 (a) really IS TC-91 (b).** §5.5.2. Promoted to the top of this list, because
   it is the one an 0.8.21 fix is most likely to scope against by mistake, and because an earlier
   draft of this document asserted it outright. The cadence sensitivity and the observability
   blindness are measured; the identity is not, and it structurally **cannot** be at this
   baseline — the counters that would confirm it are the ones `let _ =` destroys. R-C is what
   resolves it.
2. **Whether R-A alone makes TC-91 worse, and by how much.** §5.5.1 gives the direction; nothing
   here gives the magnitude. It is the reason §4's bar demands the tight-cadence duplicate count
   be re-measured rather than assumed.
3. **Whether the §2.5 `Scheduler` starvation is the more important defect.** A ~12 % failure rate
   under stress is bad; a verb that returns after 30 s of nothing, four times in five, may be
   worse for a host. I found it while bounding an arm and did not characterize it — and I did not
   touch `configure_projections` / `purge` / `lib.rs:8646` at all, which is where a host would
   most likely meet it. It is p1 material and I am not confident it should queue behind TC-90.
4. **Whether `transition` needs `IMMEDIATE` at all in-process.** It already has `drain` plus the
   connection mutex; the stress arm shows those are insufficient, but I did not isolate *which*
   of the two is leaking — i.e. whether the failures come from the drain/mutex gap I theorised
   in §1.2 or from some other path. The repro is real either way, but a fix aimed at the wrong
   half would pass §4's bar for the wrong reason.
5. **Whether the ~90 % blocked-arm duplicate rate saturates.** 32 distinct rows repeated in
   every single run, at both 80 and 96 total duplicates, looks like a structural boundary
   (`PROJECTION_INFLIGHT_LIMIT` is 32) rather than a coincidence. I did not chase it, and it may
   mean the loss is bounded by the in-flight window in a way that matters for R-D's budget.
6. **Whether a multi-process host already sees TC-90 constantly.** §6.1. If so, the priority
   ordering above is wrong.
7. **Why the TC-90 per-run failure count moved between sessions** (§2.2, mean 5.9 → 3.8 on the
   same commit and machine). The reproduction was 10/10 both times, so it does not affect any
   verdict here, but I do not know what varied and I did not chase it. It is a reason to treat
   any future *rate* comparison on this arm with suspicion unless both sides were measured in one
   session.

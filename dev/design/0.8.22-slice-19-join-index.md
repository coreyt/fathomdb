# Slice 19 — Canonical join-index design

> **Execution status:** landed on `origin/main` in PR #207 at `e95afd29`.
> Publication remains explicitly held.

## Problem

The body-, edge-, and property-FTS readers hydrate a canonical row by
`write_cursor`. `canonical_edges` has no such lookup index. `canonical_nodes`
has only the partial `canonical_nodes_state_active_idx`, which does not express
the full node-FTS join contract. Consequently SQLite can scan a canonical table
for each FTS match while it prepares the ranked result set.

This is a retrieval-path performance defect, not an EARP feature. The reported
large-corpus timings are useful motivating evidence, but the implementation
must prove planner shape rather than encode a host-specific latency threshold.

## Chosen design

Append schema step 26 with two non-unique, unconditional B-tree indexes:

```sql
CREATE INDEX IF NOT EXISTS canonical_nodes_write_cursor_idx
    ON canonical_nodes(write_cursor);
CREATE INDEX IF NOT EXISTS canonical_edges_write_cursor_idx
    ON canonical_edges(write_cursor);
```

The indexes preserve every query's rows, ordering, and visibility predicates.
They accelerate equality lookup after an FTS candidate is selected; they do not
make FTS ranking bounded and do not alter vector retrieval.

The migration is index-only. It requires no migration-accretion exemption,
does not recreate a table, and must remain part of the existing migration
transaction so a crash cannot expose a bumped schema version without its
indexes.

## Correctness proof strategy

The RED tests establish two independent facts:

1. Schema tests create a fresh database and a step-25 fixture, run migration,
   and inspect the index catalog for both exact index names.
2. Engine tests construct representative body-FTS, edge-FTS, and property-FTS
   fixtures and run the corresponding `EXPLAIN QUERY PLAN`. The body-FTS plan
   pins `canonical_nodes_write_cursor_idx`, the edge-FTS plan pins
   `canonical_edges_write_cursor_idx`, and the active-only property-FTS plan
   retains `canonical_nodes_state_active_idx`. They do not assert unrelated
   planner rows, a particular FTS implementation detail, or wall-clock time.

Existing search tests remain the semantic regression proof. The design makes
no query-text change apart from whatever test-only SQL construction is needed
to obtain the plan.

## Performance evidence protocol

The closure note records, separately from CI:

- revision, schema version, SQLite version/build flags, hardware, and cache
  treatment;
- fixture or corpus identity and row count;
- migration/index-build time and an ingest comparison with and without the
  indexes; and
- affected-query timings before and after, with raw samples retained.

The claim is limited to the measured corpus and query mix. A raw FTS statement
without visibility joins is a diagnostic baseline, not a semantically identical
production query.

## Rejected rider

The earlier proposal to add `LIMIT` directly to edge FTS is rejected from this
slice. Edge candidates are filtered after SQL and can participate in fusion; a
fixed SQL limit can consume its budget on filtered rows or omit a candidate
that becomes visible after fusion. Any future edge-bound work must prove
post-filter, final-result equivalence across filters and retrieval modes.
